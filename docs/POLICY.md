## 0. 이 정책 전체를 지배하는 세 문장

**(1) 권한은 조직 지위에서 유도되지 않는다.**
직급·역할·부서 소속 중 어떤 것도 문서 접근권을 만들지 않는다. 문서 접근권의 원천은 오직 두 개다 — 소유자이거나, 소유자가 발급한 것이거나.

**(2) 막을 수 없는 것은 비싸게 만들고 반드시 들키게 만든다.**
IT 관리자의 계정 가장(假裝), 링크 전달, 스크린샷은 기술적으로 완전 차단이 불가능하다. 못 막는 것을 막았다고 말하지 않는다. 대신 흔적이 소유자에게 남고, 그 흔적을 아무도 지울 수 없게 만든다.

**(3) 조용한 실패보다 시끄러운 실패를 택한다.**
D-004(Tab 들여쓰기 폐기)의 논리를 정책 전체에 확장한다. 권한이 조용히 넓어지는 설계(부서 자동 공유, 재공유 체인, 소급 적용)를 전부 기각하는 근거가 이것이다.

# 1. 권한 모델

## 1.0 구조 — 두 개의 독립된 축

현재 스키마는 `documents.orgId` + `document_members(role)` 하나의 축뿐이다. 이걸 **두 축으로 쪼갠다.**

```
축 A. 조직 역할 (org_members.role)     — 조직을 운영하는 권한
축 B. 문서 권한 (document_members +    — 문서를 여는 권한
                 share_links)

★ A에서 B로 가는 함수가 존재하지 않는다.
★ 코드 레벨: resolveDocumentAccess(user, doc)는 org_members를 조회하지 않는다.
   (인자로 받지도 않는다 — 실수로 참조할 수 없게 시그니처에서 뺀다)
```

**근거** — 대부분의 B2B SaaS는 `if (user.role === 'admin') return true`를 권한 함수 어딘가에 두고, 그 한 줄이 6개월 뒤 "관리자니까 볼 수 있게 해달라"의 착지점이 된다. 함수가 `org_members`를 **인자로도 받지 않으면** 그 요구는 코드 변경 없이 수용할 수 없고, 코드 변경은 리뷰에 남는다.

**반대 논거** — "긴급 상황에 관리자가 못 여는 건 위험하다."
→ 긴급 상황의 실체는 대부분 **퇴사자 문서**다. 그건 §6의 봉인 이전(2인 승인 + 로그 공개)으로 처리한다. 재직자 문서에 대한 긴급 열람은 6개월 안에 "긴급"의 정의가 넓어진다. 예외는 퇴사자 하나만 둔다.

여기에 **역할이 아닌 부가 권한** 두 개를 붙인다. 역할에 자동으로 딸려오지 않고 개별 배정한다.

| 부가 권한 | 무엇 | 왜 역할과 분리했나 |
|---|---|---|
| **분석 좌석** | 집계 대시보드·자동화 후보·집계 export | 사람을 초대하는 일과 집계를 보는 일은 다른 일이다. 최소 권한 원칙이자, 유료 좌석 경계(§10)와도 일치한다 |
| **지정 창구** | 신고·개인정보 요청 접수 (§4, §5) | 인사팀·개인정보 담당자는 조직 관리자가 아닌 경우가 많다. 관리 권한 없이 이 권한만 받을 수 있어야 한다 |

## 1.2 조직 관리자의 정확한 경계

**결정** — 조직 관리자는 **사람과 구조와 돈**을 다루고, **내용**은 다루지 않는다.

| 할 수 있다 | 할 수 없다 |
|---|---|
| 초대·비활성화·역할 부여 | 문서 열람 (예외 없음) |
| 부서 구조·명칭·계층 | 문서 목록·제목·개수 조회 |
| 도구 카탈로그 추가·표시명·숨김 | 도구 연결성 등급·n8n 매핑 |
| 외부 공유 on/off, 기본 만료(7~90일) | 개인이 만든 링크 강제 회수 (◐ 아래) |
| 근무시간 창 (8시간 이내, 22–08시 불가) | 알림 상한 상향 |
| 분석 좌석 배정·회수 | 5인 차단 해제·k-익명 파라미터 |
| 집계 export (좌석 보유 시) | 임의 기간·임의 필터 조합 |
| 조직 공지 월 1건 (부서 전원 또는 전원) | 개인 지목 발송 |
| 지정 창구 지정 | 신고 내용 열람 (창구 있으면) |
| 데이터 보존 기간 (법정 하한~우리 상한) | 개인 메모의 집계 포함 |
| 퇴사자 문서 봉인 열람 요청 | 재직자 문서 열람 (어떤 사유로도) |
| 시드 도입 패키지 요청 | 직원 화면 문구 |

**개인 링크 강제 회수** ◐ — **개별 회수는 불가, 일괄 정지만 가능하다.** 조직 관리자가 외부 공유를 끄면 기존 외부 링크는 **30일 유예 후 일괄 정지**되고 소유자 전원에게 통지된다. 특정 사람의 특정 링크를 지목해 끊는 기능은 없다. 근거: 지목 회수가 가능하면 "그 링크 왜 만들었냐"는 대화가 성립하고, 그 대화가 한 번 있으면 아무도 공유하지 않는다.

**반대 논거** — "관리자가 조직 데이터에 대해 아무 통제권이 없는 건 도입 결재가 안 난다."
→ 통제권은 충분히 준다. **사람(누가 들어오고 나가는가), 경계(밖으로 나갈 수 있는가), 구조(부서·카탈로그), 보존(얼마나 남기는가)** 네 가지가 전부 관리자 손에 있다. 통제하지 못하는 것은 **내용** 하나뿐이고, 그건 보안 실사에서 오히려 강점으로 읽힌다 — 관리자 계정이 털려도 문서가 안 새기 때문이다.

## 1.3 시스템 관리자 문제 — 계정을 만드는 사람은 가장할 수 있다

**정직한 출발점: 완전히 막을 수 없다.** IdP를 쥔 사람은 어떤 SaaS에서도 남의 계정으로 들어갈 수 있다. 이건 이 제품의 결함이 아니라 사내 시스템 전체의 조건이다. **막았다고 말하지 않는다.** 대신 일곱 겹으로 비싸게 만들고 반드시 흔적을 남긴다.

| # | 장치 | 무엇을 바꾸나 |
|---|---|---|
| 1 | **가장 기능을 만들지 않는다** | "이 사용자로 로그인" / "지원 모드" 엔드포인트가 존재하지 않는다. 우리 지원팀에도 없다. 가장하려면 IdP를 건드려야 하고, 그건 제품 밖에 흔적을 남긴다 |
| 2 | **IdP 경유 강제** | 조직 기본값은 SSO 전용. 제품 자체 비밀번호가 없으므로 "몰래 비밀번호를 바꿔 들어가기"가 불가능하고, 자격증명 변경은 IdP 감사 로그에 남는다 |
| 3 | **역할 분리** | 시스템 관리자는 **역할을 바꿀 수 없다**(표 B-7). 자기를 조직 관리자로 승격하거나 분석 좌석을 자기에게 붙일 수 없다. 계정을 만드는 사람과 권한을 주는 사람을 분리한다 |
| 4 | **새 세션 통지** | 새 기기·새 위치에서 세션이 열리면 소유자에게 즉시 통지(상한 예외). *"어제 저녁 8시에 처음 보는 기기에서 열렸어요."* |
| 5 | **열람 로그의 기기 구분** | 소유자의 열람 로그는 계정이 아니라 **세션 지문** 단위로 남는다. 본인 계정이어도 낯선 기기면 별도 행으로 보인다. 로그는 append-only, 관리자도 못 지운다 |
| 6 | **2인 규칙** | 계정 재활성화, 인증 수단 변경, 퇴사자 문서 봉인 열람, 소유권 강제 이전은 **두 번째 관리자의 확인**을 요구한다(관리자 2인 이상 조직에서 기본 on). 혼자서는 못 한다 |
| 7 | **이득을 낮춘다** | 가장에 성공해도 얻는 건 **그 사람 문서 하나**다. 개인별 집계가 없으므로 100명을 보려면 100번 가장해야 하고, 그 100번이 전부 로그에 남는다. 대량 감시의 단위 비용이 1:1이다 |

**직원에게 하는 정직한 고지** (설정 > 개인정보에 그대로):

> **IT 담당자에 대해서는 이렇게 되어 있어요**
> IT 담당자는 계정을 만들고 없앨 수 있지만, 문서를 열 수 있는 경로는 이 도구 안에 없어요. 다른 사람으로 로그인하는 기능도 만들지 않았어요.
> 다만 회사 계정 자체를 쥔 사람이 마음먹으면 메일함이든 여기든 못 여는 곳은 없어요. 그건 이 도구가 해결할 수 있는 문제가 아니에요. 대신 처음 보는 기기에서 열리면 알려드리고, 그 기록은 아무도 지울 수 없게 해뒀어요.

**반대 논거** — "정직하게 못 막는다고 쓰면 사람들이 안 쓴다."
→ 반대다. "완벽하게 안전합니다"는 검증 불가능한 주장이고, 사내 IT를 아는 사람 한 명이 회의에서 뒤집으면 신뢰가 통째로 무너진다. **못 막는 것을 먼저 말하는 쪽이 막은 것에 대한 신뢰를 산다.** 그리고 이 문단은 "우리가 만들 수 있는데 만들지 않은 것"(가장 기능)을 자연스럽게 보여주는 자리이기도 하다.

## 1.4 문서 단위 공유 권한 — 3단계에서 멈춘다

| 등급 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| **읽기** | 열람, 아웃라인 복사, PDF·PNG 내보내기 | 편집, 댓글, 재공유 |
| **댓글** | 위 + 단계별 댓글, `저 아니에요`·`제 일이긴 한데 다르게 해요` 응답 | 편집, 재공유 |
| **편집** | 위 + 단계 추가·수정·삭제, 조직 내 링크 생성 | 문서 삭제, 소유권 이전, 외부 링크 생성, 개인 메모 열람 |

**결정** — 3단계에서 멈춘다. 4단계 이상(내보내기 금지, 복사 금지, 워터마크)을 만들지 않는다.

**근거**
- "내보내기 금지"는 스크린샷 한 장으로 무력화된다. **지킬 수 없는 약속을 UI에 인쇄하지 않는다.** 지켜지는 줄 알고 민감한 걸 적게 만드는 것이 더 위험하다.
- 비개발자에게 권한 등급 5개를 고르게 하면 공유 다이얼로그에서 이탈한다. M1 가설이 공유율 30%다.
- **댓글을 별도 등급으로 둔 이유가 이 제품에는 특별히 있다.** 불일치 리포트(PRD §4.9)의 원재료가 "B가 A의 문서에 이의를 다는 것"인데, 편집권을 주면 B가 A의 문서를 고쳐버려서 **불일치 자체가 사라진다.** 불일치는 버그가 아니라 산출물이므로, 이의는 남되 내용은 안 바뀌는 등급이 반드시 필요하다.

**편집자가 개인 메모를 못 보는 것**이 중요하다. "실제로는 이렇게 합니다" 노트와 개인 메모는 편집 권한으로도 열리지 않는다(§4.2, §6.4).

**반대 논거** — "읽기 전용인데 PDF로 뽑아 돌리면 통제가 안 된다."
→ 통제되지 않는다. 그래서 **모든 내보내기 산출물에 작성자·마지막 확인일·출처 문구가 찍힌다**(§5.3). 유통을 막는 대신 유통되는 물건에 유통기한을 찍는 쪽을 택했다.

## 1.5 부서 단위 공유 — 만들지 않는다

**결정** — "우리 팀은 서로 다 볼 수 있게"라는 부서 자동 공유를 **허용하지 않는다.** 대신 **팀 서재**를 준다.

**근거 세 겹**

1. **부서장은 그 부서 소속이다.** 부서 공유를 켜는 순간 부서장이 팀원 전원의 문서를 열 수 있고, 이건 D-002가 막으려던 상태와 결과가 동일하다. 이름만 다른 관리자 열람권이다.
2. **조직에서 옵트인은 실질 강제가 된다.** D-002에서 이미 기각된 논리다. 팀 공유가 켜지면 안 켠 사람이 눈에 띈다.
3. **권한이 조용히 확장된다.** 인사이동으로 어제 남이던 사람이 오늘 내 3년치 기록을 본다. 소속이 권한을 만들면 조직 개편이 권한 개편이 되고, 아무도 그 순간을 통지받지 못한다. 지배 원칙 (3) 위반이다.

**대안: 팀 서재 (공개 서가)**

| | 부서 자동 공유 (기각) | 팀 서재 (채택) |
|---|---|---|
| 권한의 원천 | 부서 소속 | 소유자의 문서 단위 행위 |
| 조직 개편 시 | 조용히 넓어짐 | 아무 변화 없음 |
| 새 문서 | 자동 포함 | 자동으로 안 올라감 |
| 부서 이동 시 | 이전 팀 접근 소실 + 새 팀 전체 노출 | 올려둔 것은 그대로, 새 팀엔 안 올라감 + 소유자에게 1회 안내 |
| 내리기 | 부서장이 가능 | 소유자만 가능 |

마찰은 클릭 1회로 고정한다 — 공유 다이얼로그 첫 화면에 `[우리 팀에 열어두기]` 버튼을 링크 만들기와 나란히 둔다.

> 팀이 바뀌었어요. 영업 1팀에 열어둔 흐름 3개는 그대로 있어요.
> `[그대로 두기]` `[내려놓기]`

**반대 논거** — "매번 눌러야 하니 결국 아무도 안 올린다."
→ 한 번의 클릭이 팀 전체 열람권을 만든다. **그 한 번이 신뢰의 전부다.** 그리고 마찰은 클릭 수가 아니라 결정의 무게에서 오는데, 팀 서재는 "이 문서 하나"라는 좁은 결정이라 오히려 누르기 쉽다. 부서 전체 공유는 결정이 무거워서 아무도 안 켠다.
게이지는 계측한다 — 팀 서재 게시율이 8주 후 10% 미만이면 UI 위치를 재검토한다. **정책이 아니라 위치를 고친다.**

## 1.6 조직 전체 공개 문서 — 필요하다. 단, 별도 객체로

**결정** — 개인 문서를 "전사 공개"로 전환하는 스위치를 두지 않는다. **공용 흐름**이라는 별도 문서 종류를 만들고, 개인 문서에서 **복제해 승격**하는 경로만 제공한다.

**근거**

1. **정책이 다르다.** 개인 문서는 소유자가 지우면 사라져야 하고, 사내 SOP는 그러면 안 된다. 신선도 주기도, 아카이브 조건도, 퇴사 처리도 전부 다르다. 한 테이블에 두면 정책이 서로를 오염시킨다.
2. **의미가 다르다.** 이 제품은 "규정대로가 아니라 실제대로 적어주세요"라고 요청한다. 그 문서가 전사 공개로 승격되는 순간 **"회사가 인정한 규정"으로 읽히고**, 그러면 다음부터 아무도 실제대로 안 적는다. 제품의 핵심 요청과 정면 충돌한다.
3. 복제 승격이면 원본은 개인 것으로 남는다. 승격했다고 자기 기록을 잃지 않는다.

**공용 흐름 규격**

| 항목 | 값 |
|---|---|
| 소유자 | 부서 계정 (개인 아님) |
| 열람 | 조직 전원 |
| 편집 | 개별 지정된 편집자만 |
| 검색 | 노출됨 (개인 문서는 본인 것만 검색됨) |
| 신선도 주기 | 180일 |
| 자동 아카이브 | **대상 아님.** 대신 `확인이 필요해요` 표시 |
| 관리자 열람 | ✔ 가능 — **원칙 1 위반이 아니다.** 애초에 전원 공개 문서다 |
| 짜증 플래그 | 없음 (개인 신호이므로 공용 문서에 붙지 않는다) |
| 개인 메모 | 승격 시 **따라오지 않는다** |

> 이 흐름을 우리 부서 공용으로 만들까요?
> 사본이 만들어져요. 지금 문서는 그대로 내 것으로 남아요.
> 공용으로 만들면 회사 사람 누구나 볼 수 있고, "실제로는 이렇게 합니다" 메모는 빠져요.

**반대 논거** — "복제하면 원본과 사본이 갈라져서 관리가 안 된다."
→ 갈라지는 게 맞다. 개인이 실제로 하는 방식과 조직이 공표한 방식은 **원래 다르고, 그 차이가 이 제품이 파는 물건**이다(불일치 리포트). 억지로 하나로 묶으면 둘 중 하나가 거짓이 된다.

## 1.7 휴가 대체자 위임

**결정** — 소유자만 발급하는 **기간 한정 열람권**. 최대 30일, 자동 만료, 연장은 소유자만. 관리자 개입 경로 없음.
**근거** — 이 요구는 실재하고(휴가 대체자 가이드는 PRD의 핵심 가치 중 하나), 막으면 사람들은 계정을 빌려준다. 계정 대여가 위임 기능보다 훨씬 위험하다.

# 2. 공유 정책

## 2.1 링크 종류

| | 로그인 | 대상 | 최대 만료 | 기본 |
|---|---|---|---|---|
| **A. 조직 안 사람만** | 필요 | 같은 조직 전원 | 만료 없음 가능 | **★ 기본값** |
| **B. 링크를 아는 사람 누구나** | 불필요 | 누구나 | **90일** | |
| **C. 지정한 사람만** | 필요 또는 1회용 코드 | 지정 이메일 | 90일 | |

한 문서에 **여러 링크를 동시에 발급**할 수 있고, 각 링크에 이름표를 붙인다(`재무팀 김선영에게`). 개별 회수가 가능해야 하기 때문이다.

## 2.2 기본값 — 안전과 마찰의 실제 최적점

**결정** — **A(조직 안 사람만) + 읽기 전용 + 30일 만료.**

**근거** — 가장 안전한 것은 C지만, C를 기본으로 하면 공유 다이얼로그가 "누구를 넣지?"라는 인지 부담부터 시작한다. A는

- 클릭 1회로 링크가 나온다 (C와 달리 입력이 없다)
- 회사 밖으로 새지 않는다 (B와 달리 경계가 있다)
- **실패가 시끄럽다** — 조직 밖 사람이 열면 *"이 문서는 회사 계정으로 로그인해야 볼 수 있어요"*가 뜬다. 링크가 잘못 흘러간 것을 **보낸 사람이 즉시 안다.** B는 잘못 흘러가도 조용히 열린다.

지배 원칙 (3)의 적용이다. D-004에서 Tab 들여쓰기를 기각한 것과 정확히 같은 이유로 B를 기본값에서 뺀다.

**반대 논거 1** — "B가 제일 편하다. 받는 사람이 로그인 안 해도 되니까."
→ 만드는 사람의 편의는 같다(둘 다 클릭 1회). 다른 건 **잘못 갔을 때**뿐이다. 그리고 실제로 조직 밖에 보낼 일이 있는 사람은 그때 B를 고르면 되고, 그 선택은 1초 걸린다. **드문 경우를 위해 기본값을 열어두지 않는다.**

**반대 논거 2** — "로그인 요구하면 열람률이 떨어져 F2 퍼널이 죽는다."
→ 조직 내 열람은 SSO가 이미 통과돼 있어 체감 마찰이 0에 가깝다. 실제 마찰은 **조직 밖 열람**에서만 생기고, 그건 B로 해결한다. 이 가정은 계측한다 — `doc_viewed` 대비 링크 종류별 열람 도달률을 보고, A의 도달률이 B보다 15%p 이상 낮으면 기본값을 재검토한다.

## 2.3 만료

| 선택지 | A | B | C |
|---|---|---|---|
| 7일 | ✔ | ✔ | ✔ |
| **30일 (기본)** | ✔ | ✔ | ✔ |
| 90일 | ✔ | ✔ | ✔ |
| 만료 없음 | ✔ | **✗** | **✗** |

**근거** — 조직 밖으로 나간 무기한 링크는 회수 불가능한 유출이다. 90일이면 협력사 인수인계에 충분하고, 더 필요하면 재발급하면 된다. **재발급은 새 토큰이라 이전 링크가 부활하지 않는다** — 이게 만료의 실제 가치다.

만료 7일 전 소유자에게 **인앱 알림 1건**(외부 채널 아님 — 알림 예산을 여기 쓰지 않는다).

> **만료 화면 (열람자)**
> 이 링크는 기간이 지났어요. 만든 분에게 다시 요청하시면 됩니다.
> `[만든 사람에게 요청 보내기]`

> **만료 화면 (소유자)**
> 이 링크는 닫혔어요. `[다시 열기]`

**반대 논거** — "만료 때문에 나중에 안 열리면 민폐다."
→ 만료 화면에 요청 버튼이 있고, 요청은 소유자에게 알림 1건으로 가며 1클릭 재발급이다. 그리고 **닫힌 링크는 그 자체로 유용한 신호**다 — 누가 아직 이 문서를 필요로 하는지가 드러난다.

## 2.4 외부 공유 — 허용한다

**결정** — 허용한다. 조직 관리자가 조직 단위로 끌 수 있고, 켜져 있어도 기본값은 아니다.

**근거** — 인수인계 문서를 회계사무소·3PL·용역업체에 보내는 시나리오가 실재한다(TOOLS.md의 세무·물류 항목이 전부 그 증거다). **막으면 사람들은 PDF로 뽑아 메일로 보낸다.** 그러면 만료도, 회수도, 로그도 사라진다. **제품 안에서 하게 두는 쪽이 실제로 더 안전하다.**

외부 링크의 추가 조건:

- 최대 90일, 만료 없음 선택지 부재
- 열람 로그에 **이메일 도메인 표시**, 로컬파트는 마스킹 (`k***@partner.co.kr`)
- 생성 시 1회 사실 진술 — 경고가 아니다:
  > 이 링크는 회사 밖에서도 열려요. 90일 뒤에 닫혀요.
- **워터마크를 넣지 않는다.** 불신의 표시이고, 실효도 없으며, 받는 사람이 이 도구를 처음 보는 화면(/s/[id])의 인상을 망친다

**반대 논거** — "기밀 유출 위험이 크다."
→ 위험은 실재한다. 다만 이 제품의 문서는 대개 *"누가 뭘 어떤 순서로 하는가"*이지 단가표나 고객 명단이 아니고, §4가 그런 값을 문서에 넣지 말라고 말한다. 유출 위험을 낮추는 실질 수단은 링크 금지가 아니라 **내용 정책 + 짧은 만료 + 열람 로그**다. 그리고 정말 못 나가게 해야 하는 조직은 관리자가 조직 단위로 끄면 된다 — 이건 조직의 판단이지 제품의 기본값이 아니다.

## 2.5 회수·재발급·열람 로그

| 동작 | 규칙 |
|---|---|
| 회수 | 즉시 토큰 무효화. 회수 시 *"이 링크를 3명이 열었어요"*를 사실로 표시(경고 아님) |
| 재발급 | 항상 새 토큰. 이전 링크는 부활하지 않는다 |
| 일괄 정지 | 아카이브 시 자동(§7), 외부 공유 조직 차단 시 30일 유예 후 |
| 열람 로그 노출 | **소유자만.** 공유 다이얼로그 안 별도 탭(`누가 열어봤어요`) |
| 로그 위치 | **문서 화면 상시 노출 금지.** SCREENS.md의 "조회자 아바타 스택 없음" 규칙 유지 |
| 보존 | 90일 (TRUST.md §7과 일치) |
| 역방향 | 열람자에게 *"누가 내 열람 기록을 봤다"*를 표시하지 않는다 (TRUST.md §2.4) |
| 삭제 | 소유자도 자기 문서의 열람 로그를 지울 수 없다 (append-only) |

**소유자가 자기 로그를 못 지우는 이유** — 지울 수 있으면 §1.3의 7번 장치(가장 흔적)가 무력화된다. 계정을 가장한 사람이 첫 번째로 하는 일이 로그 삭제다.

## 2.6 재공유 — 불가

**결정** — 읽기·댓글 권한자는 링크를 만들 수 없다. 편집 권한자는 **조직 내(A) 링크만** 만들 수 있고, 외부(B·C)는 소유자만.

**근거** — 원칙 5("소유자가 누가 열람했는지 볼 수 있다")는 **열람 목록의 완전성**에 걸려 있다. 재공유 체인이 생기면 소유자는 1차 수신자만 알고 그 뒤를 모른다. 완전하지 않은 로그는 안심을 주지 못하고, 안심을 못 주면 원칙 5가 하는 일이 없다.

**대안: 열람 요청 버튼**

> **(열람자 화면 하단)**
> 이 흐름을 봐야 할 다른 분이 있어요? `[만든 분께 요청하기]`

> **(소유자에게 가는 알림)**
> 김선영 님이 '견적서 발행'을 박지훈 님도 볼 수 있게 해달라고 하셨어요.
> `[확인했어요]` `[지금은 아니에요]`

마찰이 소유자의 클릭 1회로 옮겨지고 로그의 완전성은 지켜진다. 그리고 이 요청 자체가 **"누가 이 문서를 필요로 하는가"라는 조직 조립 신호**라서, 버리는 마찰이 아니라 회수하는 데이터다.

**반대 논거** — "링크를 복사해서 카톡에 붙여넣으면 어차피 재공유된다."
→ 맞다. 그래서 **A(로그인 필요)를 기본값으로 둔 것이 실질 방어**다. A 링크는 붙여넣어도 조직 밖에서 안 열리고, 조직 안에서 열리면 **누가 열었는지 로그에 실명으로 남는다.** 재공유 기능을 안 만드는 것과 A를 기본으로 하는 것은 같은 정책의 앞뒤다.

# 3. 알림 정책

> 사내 도구는 기능이 부족해서 죽지 않는다. **알림 총량으로 죽는다.**

## 3.1 전역 상한

```
외부 채널(슬랙 DM + 이메일) 합산     주 3건
같은 종류의 알림                     2주 1건   (WRITING.md §13-5)
인앱 소식함                          상한 없음  (가지러 오는 것이므로)
```

**상한 예외는 셋뿐** — 되돌릴 수 없는 일(소유권 이전 예정·삭제 예정), 계정·보안(새 기기 로그인), SCIM 동기화 실패(관리자 한정).

**예산 초과 시 우선순위**

1. 되돌릴 수 없는 일
2. **사람이 나를 지목한 것** (멘션·초대·인계 요청·열람 요청)
3. 시스템 발신 (신선도·아카이브·요약)

**밀린 시스템 발신은 쌓지 않고 버린다.** 다음 주기에 다시 오면 된다. 쌓아두면 다음 주에 몰려 나가 같은 문제를 반복한다.

**근거** — 주 3건은 "무시 학습"이 생기지 않는 경계값이다. 개별 알림의 품질을 아무리 올려도 총량이 넘으면 채널 전체가 무시 대상이 된다. 그리고 이 제품에서 무시당하는 것은 알림이 아니라 **화자**다 — 옆자리 동료가 일주일에 다섯 번 말을 걸면 그는 더 이상 동료가 아니라 시스템이다.

**반대 논거** — "3건은 너무 적어서 제품이 성장을 못 한다."
→ 이 제품의 성장 루프는 알림이 아니라 **공유**다(PRD §7: 열람자/작성자 3:1). 알림을 늘리면 단기 응답률은 오르고 6주 뒤 전 채널 무시가 온다. 그리고 신선도 응답률 목표(40~60%)는 빈도가 아니라 **20초짜리 마이크로 확인의 품질**에서 나온다(D-기각: 날짜 기반 갱신 알림).

## 3.3 묶어 보내기

**결정** — 주간 다이제스트를 만들지 않는다. **이벤트 기반 지연 묶음**을 쓴다.

```
발신 대상 발생 → 최대 4시간 대기(근무시간 안에서만) → 같은 사람 앞으로 온 것을 1건으로 병합
```

- 4시간 창에 여러 건이면 *"세 가지가 기다리고 있어요"* 형태의 1건
- **멘션(#1)은 묶지 않는다.** 사람이 사람을 부른 것을 4시간 지연시키면 관계가 상한다
- 4시간인 이유: 오전에 생긴 일이 오후에, 오후에 생긴 일이 다음 날 오전에 도착한다. 하루에 두 번 이상 울리지 않는다

**근거** — 월요일 아침 다이제스트는 사내 도구 알림의 전형적 무시 대상이다. "정기적으로 오는 것"은 정기적으로 지워진다. 이벤트 기반은 **올 때마다 이유가 있다.**

**반대 논거** — "4시간 지연이면 급한 걸 놓친다."
→ 이 제품에 4시간 안에 답해야 할 일이 없다. 있다고 느껴진다면 그건 제품이 사용자의 하루에 끼어들고 있다는 뜻이고, 그 자체가 고쳐야 할 신호다.

## 3.4 끄기 — 어디까지 허용하는가

| | 끌 수 있나 |
|---|---|
| 신선도·아카이브·링크 만료·요약·공유받음 | ✔ 전부 |
| 슬랙 DM 전체 (채널 단위) | ✔ |
| 이메일 전체 | ✔ |
| **나를 지목한 것** (멘션·초대·인계 요청·열람 요청·신고) | 외부 채널만 ✔ / **인앱은 ✗** |
| **되돌릴 수 없는 일** (소유권 이전·삭제 예정) | ✗ |
| **계정·보안** | ✗ |
| **"전부 끄기" 스위치** | ✔ 제공한다 |

**"전부 끄기"의 정확한 의미** — 외부 채널(슬랙·이메일) 전면 차단. **인앱 소식함은 남는다.** 즉 이 제품이 사용자를 찾아가는 경로는 완전히 닫을 수 있고, 사용자가 오면 알려주는 경로만 유지된다.

**근거** — 못 끄게 하면 사용자는 채널 자체를 뮤트한다(슬랙 앱 알림 끄기, 메일 필터). 그러면 우리는 통제권을 **완전히** 잃고 그 사실조차 모른다. 끌 수 있게 하면 최소한 **누가 껐는지 안다.**

**끄기율을 제품 건강 지표로 삼는다** — 외부 채널 끄기율이 **15%를 넘으면 알림 설계가 틀린 것**이지 사용자가 틀린 게 아니다. 이 수치를 §9 경보 대상에 넣는다.

**반대 논거** — "다 끄면 신선도가 죽고 문서가 썩는다."
→ 신선도의 주 경로는 애초에 알림이 아니라 **체크리스트 재사용**이다(PRD §4.10: *"읽을 이유 없는 문서는 반드시 썩는다"*). 알림은 보조 경로다. 그리고 끈 사람에게는 **문서를 열었을 때 인앱 확인 카드**를 띄운다 — 찾아가는 대신 올 때 묻는다. 이쪽이 응답률도 더 높다.

## 3.5 근무시간 외 발송

```
발송 창    평일 09:30 ~ 17:30
그 밖에 생긴 알림은 다음 발송 창의 시작에 보낸다.
```

| 규칙 | 근거 |
|---|---|
| **09:30 시작** | 09:00 정각은 출근 직후 메일 폭탄과 겹친다. 시업 전 도착은 *"출근 전에 봐야 하나"*를 만든다 |
| **17:30 종료** | 18시 이후 도착은 *"퇴근 후 처리 요청"*으로 읽힌다. 17:30이면 답할 여유가 남는다 |
| **금요일 15시 이후 시스템 발신 금지** | 신선도·아카이브는 월요일로. 사람이 보낸 것(#1~#6)은 금요일도 17:30까지 |
| **주말·공휴일 전면 금지** | 예외 없음. 국내 공휴일 캘린더 반영 |
| **조직 조정 가능** | 교대·현장 조직을 위해 창을 옮길 수 있다 |
| **조정 상한** | 창 길이 **8시간 초과 불가**, **22:00~08:00 구간은 어떤 설정으로도 열리지 않는다** |
| **개인 조정** | 자기 발송 창을 **좁힐 수만** 있다. 넓힐 수 없다 |
| **예외** | 계정·보안(#13)만 즉시 발송. 사용자를 보호하는 알림이므로 |

**근거** — 국내 기업 문화에서 밤 10시 알림은 정보가 아니라 **"이 도구는 나를 쫓아다닌다"의 증거**다. 이 제품에서 그 인상 하나가 §1~§2의 모든 장치를 무효화한다. 그리고 조직 설정으로도 야간을 못 열게 막은 이유는, **열 수 있으면 반드시 여는 조직이 있기 때문**이다.

**반대 논거** — "우리 회사는 야근이 일상이라 밤에 보내는 게 자연스럽다."
→ 자연스러운 것과 좋은 것은 다르다. 그리고 이 정책은 조직이 아니라 **개인을 보호**하기 위한 것이고, 이 제품이 개인 편에 서 있다는 몇 안 되는 가시적 증거 중 하나다. 야간 발송을 허용하는 순간 §12의 약속 카드에서 한 줄을 지워야 한다.

## 3.6 관리자의 "작성 독촉" — 만들지 않는다

**결정** — 관리자가 직원 개인에게 작성을 독촉하는 알림을 **제품에 만들지 않는다.** 기능이 없다.

**근거 세 겹**

1. **전제가 이미 위반이다.** 독촉하려면 "누가 안 썼는지"를 알아야 한다. 미작성자 명단은 MEASUREMENT.md §5의 절대 금지 목록에 있고, 원칙 2("사람이 등장하지 않는다")의 직접 위반이다. **기능의 입력값 자체가 존재하지 않는다.**
2. **숫자는 오르고 값은 떨어진다.** TRUST.md가 이미 판정한 경로다 — 부서장 압박으로 3개월간 작성률이 오르고, 그 다음 데이터가 방어적으로 왜곡되고, 자동화 후보 목록이 쓰레기가 된다. **작성률은 우리가 파는 물건이 아니다.**
3. **화자가 무너진다.** 이 제품의 화자는 옆자리 동료다. 그 동료가 부서장의 독촉을 대신 전달하는 순간 화자는 관리 시스템이 되고, 한 번 그렇게 읽히면 되돌릴 수 없다.

**관리자에게 대신 주는 것 — 조직 공지 (월 1건)**

| 조건 | 이유 |
|---|---|
| 대상은 **전원 또는 부서 전원**만 | 개인 지목이 기술적으로 불가능하게 |
| 작성 여부를 수신자 조건으로 쓸 수 없다 | "안 쓴 사람에게만"이 성립하지 않게 |
| 월 1건 | 공지 자체가 독촉의 우회로가 되지 않게 |
| **발송 사실이 전 직원 공지함에 남는다** | 조용한 압박이 불가능하게 |
| 본문에 개인 이름 금지 | |

그리고 관리자에게 **작성률을 올리는 실제 경로**를 문서로 제공한다 — 시드 콘텐츠, 인수인계 이벤트 결합(PRD 롤아웃 2단계), 챔피언. 이 셋이 검증된 경로이고 독촉은 아니다.

**반대 논거** — "돈 내고 도입했는데 작성률을 못 올리면 어떡하나."
→ **계약서에 작성률을 넣지 않는다.** 우리가 파는 것은 "6개월 내 자동화 후보 30건, 5건 착수"이지 작성률이 아니다(PRD §3.2). 작성률 40%면 반복업무 지형도의 80%가 드러나고, 그걸로 약속한 숫자가 나온다. **작성률을 KPI로 삼는 순간 이 제품은 KPI 달성 도구가 되고 데이터는 죽는다.**

# 4. 콘텐츠 정책

## 4.1 문서에 쓰면 안 되는 것

| # | 금지 | 감지 | 처리 |
|---|---|---|---|
| 1 | 주민등록번호·계좌번호·카드번호 | 클라이언트 정규식 | 인라인 제안 |
| 2 | 비밀번호·인증 정보 | 클라이언트 정규식 (`비밀번호는`, `pw:`, `계정정보`) | 인라인 제안 |
| 3 | 고객·거래처 개인 연락처 원문 | 클라이언트 정규식(휴대폰·이메일 형식) | 인라인 제안 |
| 4 | 조직이 지정한 기밀 등급 정보 (단가 실값, 계약 조건, 미공개 재무) | **감지하지 않음** | 안내만 |
| 5 | 타인에 대한 인신공격·모욕·차별 표현 | **감지하지 않음** | §4.2 |
| 6 | 외부 저작물 전재 | **감지하지 않음** | 신고 시 처리 |

**결정 — 차단하지 않는다. 서버가 본문을 스캔해 분류하지 않는다.**

패턴 감지는 **전부 클라이언트에서** 돌고, 결과가 서버로 가지 않는다. 감지 이벤트도 계측하지 않는다(MEASUREMENT.md 금지 속성 목록에 본문이 이미 있다).

> 여기 주민번호 같은 게 보여요. 지워둘까요?
> `[지우기]` `[그대로 둘게요]`

**근거**
- 하드 차단은 오탐 시 작성이 그 자리에서 멈춘다. 이 제품에서 작성 중단은 데이터 소실이다.
- **서버 스캔은 그 자체로 감시다.** "이 도구가 내 글을 읽고 있다"는 인상 하나가 §1~§3의 모든 장치를 무효화한다. 클라이언트 정규식은 "내 브라우저가 내 글을 보는 것"이라 성질이 다르다.
- `[그대로 둘게요]`를 반드시 남긴다. 실제로 주민번호를 적어야 하는 업무 단계가 존재하고(4대보험 취득신고), 그걸 못 적게 하면 그 단계가 통째로 빠진다.

**4번(기밀)을 감지하지 않는 이유** — 기밀의 정의는 조직마다 다르고, 우리가 판정하려면 본문 의미를 읽어야 한다. 대신 **온보딩과 공유 시점에 안내만** 한다.

> 단가나 계약 조건 같은 건 값을 그대로 적기보다 *"단가표에서 확인한다"*처럼 적어두시면 나중에 이 문서를 밖으로 보낼 때 편해요.

## 4.2 동료에 대한 부정적 서술 — 이 정책에서 가장 어려운 문제

문제의 실체: `김 과장님은 오전에 연락하면 잘 안 받으세요`는

- **실제로 가장 유용한 인수인계 정보다.** WRITING.md §8 Q4의 placeholder가 정확히 이 문장이다 — 우리가 직접 유도하는 정보다
- **동시에 험담이다.** 김 과장이 이 문장을 보면 관계가 상한다

**결정 — 삭제하지 않고, 신고 대상으로도 삼지 않고, 감지해서 차단하지도 않는다. 대신 네 겹으로 다룬다.**

### (1) 기본 그릇을 비공개 노트로 만든다

TRUST.md 공포 3의 **"실제로는 이렇게 합니다" 노트**가 이 내용의 기본 자리다.

| | 값 |
|---|---|
| 보이는 사람 | **소유자만.** 편집 권한자도 못 본다 |
| 공유 링크 | 포함 안 됨 |
| 내보내기 | **기본 미포함.** 내보낼 때 별도 선택 |
| 집계 | 들어가지 않음 (P0→P2는 구조화된 값만) |
| 소유권 이전 | 따라가지 않고 **삭제됨** (§6.4) |
| 퇴사 | 자동 삭제 |

> **(내보내기 다이얼로그)**
> "실제로는 이렇게 합니다" 메모가 3개 있어요. 같이 보낼까요?
> `[빼고 보내기]` `[같이 보내기]`
>
> 기본은 빼고 보내는 거예요.

### (2) 주어를 사람에서 상황으로 옮기는 리라이트 제안

사람 이름 + 부정 서술 패턴이 감지되면 인라인 제안 **1회**. 강제 아님, 무시가 기본, 3초 후 소멸.

> 이렇게 적으면 받는 분이 덜 곤란해요:
> `오전에는 연락이 잘 안 닿아요. 급하면 메일이 빨라요.`
> `[이렇게 바꾸기]` `[그대로 둘게요]`

**이게 이 정책의 핵심 장치다.** 두 문장을 비교하면:

| | 정보량 | 위험 |
|---|---|---|
| `김 과장님은 오전에 연락하면 잘 안 받으세요` | 대처법 + **사람 평가** | 높음 |
| `오전에는 연락이 잘 안 닿아요. 급하면 메일이 빨라요.` | 대처법 | 낮음 |

**정보량은 같고 위험만 다르다.** 인수인계 받는 사람이 필요한 건 "어떻게 해야 하는가"이지 "그 사람이 어떤 사람인가"가 아니다. 그래서 이건 검열이 아니라 **더 나은 인수인계 문서를 만드는 제안**이고, 그렇게 프레이밍해야 사용자가 받아들인다.

### (3) 이름 언급 알림을 만들지 않는다

**결정** — "누가 나에 대해 썼어요" 알림이 존재하지 않는다.

**근거** — 만드는 순간 (a) 모든 인수인계 문서가 정치가 되고 (b) 작성자가 사실을 못 적는다. *"김 과장님은 오전에 연락이 안 닿는다"*를 적을 때마다 김 과장에게 알림이 간다면 아무도 안 적는다. 그러면 §8의 예외 프롬프트 뱅크 전체가 빈 칸으로 돌아온다.

**반대 논거** — "당사자가 모르는 채로 험담이 돌아다닌다."
→ 유통 범위가 구조적으로 좁다. 그 문서를 볼 수 있는 사람은 **소유자가 링크를 준 사람뿐**이고, 조직 집계에는 사람이 등장하지 않으며(원칙 2), 재공유가 불가능하다(§2.6). 그리고 링크를 받은 사람은 신고할 수 있다(§4.5). 즉 **"모르는 채로"의 범위가 소수 몇 명**이고, 이건 카톡 인수인계보다 훨씬 좁다.

### (4) 집계로는 애초에 못 간다

본문 텍스트는 P2 집계 마트에 존재하지 않는다. 집계로 가는 것은 `duration_band`·`pain_flag`·`assignee_id` 같은 구조화된 값뿐이고, 그마저 5인 미만은 계산되지 않는다.

## 4.3 짜증 플래그가 특정 사람을 향할 때

**결정 — 짜증은 단계에 붙는 것이지 사람에 붙는 것이 아니다. 이걸 데이터 모델과 렌즈로 강제한다.**

| 층위 | 장치 |
|---|---|
| **스키마** | `pain_flag`는 `items`의 boolean. 사람에 붙는 컬럼이 아니다 |
| **쿼리 (금지 조인 목록)** | `pain_flag × assignee_id` 조인이 **집계 뷰에 존재하지 않는다.** MEASUREMENT.md §3의 5인 차단과 같은 급의 하드 룰로 등록하고, CI 퍼즈 테스트 대상에 포함 |
| **계측** | `pain_flag_toggled`는 **행위자 없는 이벤트**로 전송 (MEASUREMENT.md에 이미 확정) |
| **렌즈** | **짜증 렌즈와 담당자 렌즈는 동시에 켜지지 않는다** (상호 배타) |
| **집계 출력** | 프로세스 **단계 유형별**로만. 예: *"승인 기다리는 구간에 짜증이 몰려 있어요"* |

**렌즈 상호 배타가 왜 필요한가** — 두 렌즈를 겹치면 **사람 얼굴 위에 고통이 얹힌 그림**이 나온다. D-025가 짜증을 렌즈 전용으로 격리한 이유가 여기서 한 겹 더 필요해진다. 렌즈 전환은 CSS 변수 교체라 상호 배타 구현 비용이 사실상 0이다.

### 다른 부서 담당 단계에 짜증이 몰릴 때

가장 가치 있는 신호(부서 간 접합부 병목)이면서 부서 갈등의 씨앗이다.

**결정 — 집계 출력에서 한쪽 부서를 지목하지 않는다. 접합부 단위로만 표기한다.**

| ✗ 만들지 않는 출력 | ✔ 만드는 출력 |
|---|---|
| `재무팀 담당 단계에서 짜증 12건` | `영업 → 재무 인계 구간에서 짜증 12건` |
| `구매팀이 가장 오래 걸림` | `요청 쪽과 처리 쪽 기록이 2일 / 5일로 다름` |

**근거** — 접합부 문제는 대부분 **양쪽 규칙의 불일치**이지 한쪽의 태만이 아니다. 그리고 지목당한 부서는 다음 분기부터 데이터를 왜곡한다. 한 부서만 왜곡돼도 접합부 분석은 통째로 못 쓰게 된다.

**반대 논거** — "원인 부서를 알아야 고칠 수 있다."
→ 접합부를 알면 두 부서가 마주 앉는다. 원인 부서를 지목하면 한 부서가 방어한다. **고쳐지는 건 전자다.**

## 4.4 삭제·수정 요구 — 제3자가 "내 이름 빼주세요"

**결정 — 이름 삭제 요구는 무조건 수용한다. 다만 처리 방식은 "삭제"가 아니라 "역할명 치환"이고, 개별 문서 요청이 아니라 조직 전역 옵트아웃이다.**

### 전역 이름 옵트아웃

> **(설정 > 개인정보)**
> 다른 분들 문서에 제 이름이 나오지 않게 할래요
>
> 켜두면 회사 안 모든 흐름에서 제 이름 대신 *"재무팀 담당자"*처럼 역할로 나와요.
> 이미 적혀 있는 문서에도 바로 적용돼요. 언제든 끌 수 있어요.

| 항목 | 처리 |
|---|---|
| 표시명 | `김선영` → `재무팀 담당자` (전 문서·전 내보내기·공유 페이지) |
| `assigneeId` FK | **유지된다.** 조직 조립·인계 지도의 근간(D-009)이라 지울 수 없다 |
| 적용 범위 | 소급 적용 (기존 문서 포함) |
| 소요 시간 | 즉시 (표시 레이어 처리) |
| 되돌리기 | 언제든 |
| 통지 | 문서 소유자에게 **통지하지 않는다** |

**소유자에게 통지하지 않는 이유** — 통지하면 "왜 뺐냐"는 대화가 성립한다. 그 대화 한 번이 이 기능을 아무도 못 쓰게 만든다.

**개별 문서 지목 요청을 만들지 않은 이유** — 개별 요청이 가능하려면 요청자가 **"내가 어느 문서에 등장하는지"를 알아야 하고**, 그 목록을 제공하는 순간 부서장이 팀원 문서 목록을 얻는 우회로가 된다. 전역 옵트아웃은 **문서의 존재를 알지 못한 채 권리를 행사**할 수 있는 유일한 형태다.

### 문서 자체의 삭제 요구

**결정 — 수용하지 않는다.**
**근거** — 문서는 작성자의 업무 기록이고, 제3자가 등장한다는 이유로 타인의 기록을 지울 권한은 없다. 대신 세 단계 경로를 준다: ① 이름 옵트아웃 ② 사실 정정 요청(§5.1) ③ 개인정보·기밀·괴롭힘이면 §4.5 신고 → §5.5 에스컬레이션.

## 4.5 신고 기능 — 필요하다. 최소형으로

**결정 — 문서를 볼 수 있는 사람(소유자 제외)에게만 노출. 1차 수신자는 관리자가 아니라 소유자.**

> **(공유받은 문서 하단, 눈에 띄지 않게)**
> 이 내용, 저와 관련이 있어요
>
> - 제 이름이 잘못 적혀 있어요
> - 사실과 달라요
> - 여기 있으면 안 되는 정보예요

| 항목 | 규칙 |
|---|---|
| 1차 수신자 | **소유자.** 알림 1건 + 문서에 인라인 표시 |
| 관리자 전달 | **자동으로 가지 않는다** |
| 익명성 | 소유자에게 신고자를 알리지 않는다 |
| 남용 방지 | 동일인·동일 문서 1회 |
| 에스컬레이션 조건 | ① 소유자가 7일 무응답, 또는 ② 사유가 `여기 있으면 안 되는 정보예요` |
| 에스컬레이션 대상 | **지정 창구** (미지정 조직에서만 조직 관리자 대행) |
| 넘어가는 것 | **문서 전문이 아니라 신고된 구절 + 앞뒤 1단계** |

**"발췌만 넘긴다"가 이 설계의 핵심이다.** 원칙 1(관리자 자동 열람권 없음)을 지키면서 개인정보 위반 신고를 처리하는 방법은 이것 하나뿐이다. 문서를 넘기는 순간 "신고가 있었다"가 열람의 사유가 되고, 6개월 뒤 그 경로로 다른 것들이 지나간다.

발췌 열람도 감사 로그에 남고 분기 공개 요약에 건수가 들어간다.

**반대 논거** — "신고 기능이 생기면 서로 신고하는 문화가 된다."
→ 이 신고는 고발 채널이 아니라 **정정 요청 채널**이다. 볼 수 있는 사람 자체가 소수이고, 1차 수신자가 소유자이며, 관리자에게 자동으로 가지 않는다. 고발 도구가 되려면 **관리자에게 직행하고 익명이며 대상이 넓어야** 하는데, 셋 다 아니다.

# 5. 분쟁 처리

## 5.0 지배 원칙

> **이 제품은 누가 옳은지 판정하지 않는다. 두 진술을 나란히 보이게 만든다.**

**근거** — 불일치는 버그가 아니라 최고의 산출물이다(PRD §4.9). 그리고 판정을 시작하는 순간 제품이 심판이 되고, 심판이 있으면 사람들은 심판을 의식하며 적는다. **심판을 의식하며 적은 문서는 규정 문서이지 실제 문서가 아니고, 우리가 파는 것은 실제 문서다.**

## 5.1 문서 내용에 대한 이견

상황: A가 *"이 단계는 B가 한다"*고 적었는데 B가 *"내 일 아니다"*라고 한다.

| 단계 | 처리 |
|---|---|
| B는 A의 문서를 **편집할 수 없다** | 댓글 등급으로 응답만 (§1.4) |
| B의 응답 선택지 | `저 아니에요` / `제 일이긴 한데 다르게 해요` / `맞아요` |
| A의 문서에 남는 것 | 주석: *"박서연 님은 '이 단계는 저희 팀이 아니에요'라고 하셨어요."* |
| 주석의 성질 | **삭제되지 않는다.** A가 문서를 고치면 자동으로 해소 표시 |
| 조직 지도에서 | *"두 사람이 다르게 말하는 구간"*으로 표시. **어느 쪽도 정답으로 표시하지 않는다** |
| 해소 기한 | **없다** |

**해소 기한을 두지 않는 이유** — 기한은 압박이고, 압박은 아무 말이나 적게 만든다. 그리고 30일 안에 합의를 강요하면 대개 목소리 큰 쪽으로 정리된다.

> **(A에게 가는 알림 — #3 인계 요청과 같은 예산)**
> 박서연 님이 '거래처 코드 발급' 단계에 대해 "제 일이 아니에요"라고 하셨어요.
> 흐름은 그대로 두셔도 되고, 고치셔도 돼요.
> `[열어보기]` `[그대로 둘게요]`

**반대 논거** — "그럼 영원히 안 맞는 문서가 남는다."
→ 남는다. **그리고 그게 사실이다.** 조직에 실제로 존재하는 불일치를 문서가 감추는 것보다 드러내는 게 낫고, 드러난 불일치가 경영진에게 파는 물건이다(PRD §4.9: Celonis conformance checking의 저비용 대체물). 문서가 깨끗해 보이는 것은 목표가 아니다.

## 5.2 불일치 리포트가 부서 간 갈등을 유발할 때

**결정 — 네 가지 규칙으로 리포트 자체를 갈등이 붙지 않는 형태로 만든다.**

**(1) 주어를 부서로 두지 않는다**

| ✗ | ✔ |
|---|---|
| `구매팀이 견적 3개를 요구한다` | `견적서 개수가 요청 쪽 기록과 처리 쪽 기록에서 다르게 적혀 있어요 (2개 / 3개)` |
| `재무팀이 5일 걸린다고 함` | `같은 구간을 2일과 5일로 다르게 적었어요` |

**(2) 양쪽이 동시에 본다.** 불일치 리포트는 한쪽 부서장에게 먼저 가지 않는다. 조직 지도에 동시 게시된다. 선공개는 정치를 만든다.

**(3) 원인을 추정하지 않는다.** 제품이 "누가 틀렸을 가능성이 높다"를 계산하지 않는다. 그 추정이 나오는 순간 그게 근거가 되어 회의에 들어간다.

**(4) 해소는 회의가 아니라 문서 갱신으로 한다.** 각자 자기 흐름을 고치면 리포트에서 사라진다. **합의를 요구하지 않는다** — 둘 다 맞을 수 있다(케이스가 다른 경우). 케이스가 다르면 갈래로 적으면 되고, 그게 오히려 정확한 문서다.

**관리자가 보는 범위** — 불일치 건수와 목록을 보되, **관여한 개인은 보지 않는다.** 부서 단위까지만. 그리고 5인 미만 부서가 한쪽이면 그 셀은 억제된다.

## 5.3 잘못된 문서를 보고 사고가 났을 때 — 책임 소재

**결정 — 이 제품의 개인 문서는 규정이 아니라 개인의 업무 기록이다. 문서를 근거로 한 업무 처리의 책임은 문서에 있지 않다.**

이 문장을 세 곳에 인쇄한다: ① 이용약관 ② 공유 페이지 하단 ③ 인수인계 내보내기 문서 첫 장.

> **(공유 페이지·내보내기 문서 하단 — 그대로)**
> 이건 지수 님이 2026년 8월 12일에 적어둔 기록이에요. 마지막으로 확인한 건 2026년 10월 3일이고요.
> 그 사이에 달라졌을 수 있어요. 확실하지 않은 건 적은 분께 한 번 물어봐 주세요.

**모든 내보내기·공유 산출물에 "마지막으로 확인한 날"이 반드시 찍힌다.** 이게 책임 정책의 실질 구현이다 — 면책 문구는 안 읽히지만 날짜는 읽힌다.

### 책임 있는 문서가 필요하면 공용 흐름으로

| | 개인 문서 | 공용 흐름 |
|---|---|---|
| 성격 | 개인의 업무 기록 | 조직이 공표한 절차 |
| 관리 책임자 | 없음 | **지정 필수** |
| 확인 주기 | 30/90/180일 | 180일 고정 |
| 책임 | 지지 않음 | 조직이 진다 |

**객체 타입으로 책임을 분리한 것**이 §1.6에서 공용 흐름을 별도로 만든 두 번째 이유다.

### 회사가 직원 개인에게 책임을 묻는 것

**결정 — 도입 계약서 필수 조항으로 금지한다. 이 조항이 없으면 계약하지 않는다.**

> **(계약서 조항)**
> 갑은 본 도구에 기록된 내용을 근거로 임직원 개인에게 징계·인사평가상의 불이익을 부과하지 않는다.

**근거** — 이 제품은 직원에게 *"규정대로가 아니라 실제대로 적어주세요"*라고 요청한다. 즉 **"나는 규정을 안 지키고 있다"를 자백하라고 요구하는 제품**이다. 그 자백이 징계 근거가 될 수 있으면 아무도 적지 않고, 적더라도 규정대로 적는다. 그러면 이 제품이 존재할 이유가 사라진다. **이건 배려가 아니라 작동 조건이다.**

원칙 4(인사평가 미사용)와 같은 급으로 다루며, 계약 거절 사유다.

**반대 논거** — "면책 조항으로 회사가 리스크를 떠안는다."
→ 리스크는 이미 존재한다. 지금도 카톡 인수인계와 구두 전달로 같은 사고가 나고 있고, **기록조차 없어서 원인을 못 찾는다.** 문서에 작성자와 날짜가 찍히는 것은 리스크를 만드는 게 아니라 보이게 하는 것이고, 보이면 고칠 수 있다.

## 5.4 조직 프로세스 뷰에 대한 이의 제기

조직 뷰는 읽기 전용이고(PRD §4.9) 개인 흐름의 조립 결과다. **조직 뷰 자체를 고칠 수 없다.** 이의는 두 갈래로 나뉜다.

### (i) 조립이 잘못됐다 — 내 흐름이 엉뚱한 곳에 붙었다

> 이 연결, 제 일이 아니에요 `[연결 끊기]`

- 자기 흐름이면 즉시 해제
- 남의 흐름이면 그쪽 소유자에게 확인 요청 (알림 #3 예산)
- 해제 이력은 남는다 — **매칭 알고리즘의 오탐률 데이터**가 된다

### (ii) 원본 내용이 틀렸다

§5.1과 동일 경로. 조직 뷰에서 바로 원본 소유자에게 정정 요청을 보낼 수 있다.

### 조직 지도에서 빼달라고 할 수 있는가 — 가능하다

> **(문서 설정)**
> 이 흐름은 회사 지도에 넣지 않을래요
>
> 넣지 않아도 흐름은 그대로 쓸 수 있어요. 언제든 다시 넣을 수 있어요.

**근거** — 강제로 조립하면 사람들은 **조립되지 않을 방식으로 적는다** — 외부 상대를 안 적고, 산출물 이름을 흐리게 적는다. 그러면 조인 키(핸드오프)가 통째로 오염되고 조직 지도 전체가 못 쓰게 된다. **빼는 선택지가 있어야 솔직하게 적는다.**

**반대 논거** — "다 빼면 조직 지도가 안 만들어진다."
→ 기본값은 포함이고 빼는 것이 명시적 행위다. 그리고 **제외율이 10%를 넘으면 그건 사용자 문제가 아니라 우리가 신뢰를 못 얻은 것**이고, 그때 봐야 할 것은 이 옵션이 아니라 원인이다. 제외율을 계측 지표로 등록한다.

## 5.5 에스컬레이션 경로와 최종 결정권자

```
1. 당사자 간          문서 주석 · 정정 요청 · 이름 옵트아웃
   ↓ (대부분 여기서 끝난다)
2. 부서 챔피언        조정. 판정이 아니라 "어디서 갈리는지" 정리
   ↓
3. 지정 창구          개인정보 · 기밀 · 괴롭힘 성격
   (기본: 인사팀 또는 개인정보 담당자)
   ↓
4. 조직 관리자        계정 · 권한 · 플랜
   ↓
5. 공급자(우리)       정책 해석
```

**부서 챔피언이 판정하지 않는 이유** — 챔피언은 임명된 사람이 아니라 로그에서 자연 발생한 실무자다(PRD 롤아웃 3단계). 판정 권한을 주는 순간 그는 실무자가 아니라 중간 관리자가 되고, 챔피언 제도 자체가 죽는다.

### 최종 결정권자

| 사안 | 최종 결정권자 | 비고 |
|---|---|---|
| **문서 내용** | **소유자.** 끝 | 조직 관리자가 뒤집을 수 없다 |
| 제3자 이름 표기 | **요청자** (전역 옵트아웃이 이긴다) | 소유자 의사와 무관하게 적용 |
| 개인정보·기밀 위반 | **지정 창구** | 이 경우에만 소유자 동의 없이 해당 구절 삭제 가능. 삭제 사실·위치를 소유자에게 통지하고 감사 로그에 남긴다 |
| 조직 지도 조립 | 각 흐름의 소유자 | 양쪽 다 동의해야 붙는다 |
| 계정·권한·플랜 | 조직 관리자 | |
| **제품 정책 해석** | **공급자(우리)** | 정책 위반이 확인되면 조직 관리자 요구라도 거부한다 |
| **절대 원칙 4개** | **아무도 못 바꾼다** | §11 |

**"소유자 동의 없는 구절 삭제"가 유일하게 열리는 지점**이므로 조건을 좁게 못 박는다 — 개인정보·기밀·괴롭힘 세 가지에 한하고, 삭제 범위는 신고된 구절이며, 문서 전체 열람이 아니고, 통지와 로그가 필수다.

# 6. 데이터 소유권 정책

## 6.1 회사 것인가 개인 것인가

**결정 — 회사가 보유자(controller)이고, 직원이 통제자(custodian)다.**

정확히 이렇게 갈라진다.

| | 귀속 |
|---|---|
| 문서의 **자산 소유권** | **회사** |
| 문서 안 **업무 지식의 이용권** | **회사** |
| 문서의 **접근 통제 결정권** | **직원 (소유자)** |
| **개인 메모** (§6.4) | **직원.** 회사 데이터가 아니다 |

그리고 결정적인 한 줄:

> **회사가 접근 통제 위임을 일방적으로 회수하는 경로를 제품이 제공하지 않는다.**
> (예외는 §6.2 퇴사자 봉인 이전 하나뿐이다)

**근거**

1. **"개인 것"으로 하면 회사가 살 이유가 없다.** 퇴사 시 아무것도 안 남고, 프로세스 지식이 조직에 축적되지 않는다. 그러면 이건 개인용 노트 앱이고 예산이 안 나온다.
2. **"회사 것"으로 하면 아무도 진실을 안 적는다.** 회사 것이라는 말이 "언제든 열 수 있다"로 번역되는 순간 원칙 1이 무너지고 데이터 품질이 죽는다.
3. **실제로 충돌하는 지점은 소유권이 아니라 열람권이다.** 소유권을 회사에 두고 열람권만 소유자에게 두면 두 요구가 동시에 만족된다. TRUST.md §5의 세 번째 응답 스크립트(*"회사 자산이 맞습니다. 그래서 프로세스 지식은 조직에 남습니다"*)가 이미 이 입장이다.

**반대 논거 1** — "회사 자산인데 회사가 못 보는 게 말이 됩니까?"
→ 회사 자산인 메일함도 회사가 함부로 열지 않습니다. **자산 소유와 상시 열람은 다른 문제**입니다. 그리고 회사가 사려는 것 — 프로세스 지도, 집계, 불일치 리포트, 자동화 후보 — 은 전부 제공됩니다. 제공되지 않는 것은 *"누가 무엇을 얼마나 하는지"* 하나이고, 그건 이 도구가 답하는 질문이 아닙니다.

**반대 논거 2** — "그럼 직원이 전부 지우고 나가면?"
→ §6.3이 답한다. **업무 흐름 기록은 삭제 대상이 아니다.** 지워지는 것은 개인 흔적뿐이다.

## 6.2 퇴사 시 처리

```
D-14   본인에게 안내 · 소유권 이전 유도
D-0    계정 비활성화 · 소유권 미이전 문서는 부서 아카이브로 봉인 이전
D+90   개인 흔적 자동 삭제 (§6.3) · 봉인 열람 요청 창구 폐쇄
```

### (1) 기본은 본인이 넘긴다

> **(퇴사 14일 전 · 인앱 + 이메일 · 상한 예외)**
> 곧 계정이 닫혀요. 적어두신 흐름 7개를 지금 넘기시면 원하는 분에게 갑니다.
> 안 넘기시면 부서 보관함으로 들어가요.
> "실제로는 이렇게 합니다" 메모와 개인 메모는 넘어가지 않고 지워져요.
> `[넘길 사람 고르기]` `[보관함으로 둘게요]`

### (2) 안 넘기고 나간 경우 — 봉인 이전

**원칙 1의 유일한 예외다.** 그래서 네 겹으로 봉인한다.

| 조건 | 값 |
|---|---|
| 대상 | **퇴사자 문서만.** 재직자는 어떤 사유로도 불가 |
| 열람 승인 | **관리자 2인** (또는 부서 책임자 + 조직 관리자) |
| 열람 범위 | 지정한 문서 1건씩. 목록 일괄 열람 불가 |
| 로그 | 감사 로그 + **분기 공개 요약에 건수 게시** |
| 유효 기간 | 퇴사 후 **90일**. 이후 열람 요청 자체가 닫힌다 |

**재직자에 대해서는 어떤 경우에도 열리지 않는다** — 휴직·장기휴가·병가·출장·연락 두절 전부 포함.

**근거** — *"휴가 중이라 급해서"* 한 번 열면 다음은 *"출장 중이라"*가 되고, 그다음은 *"자리에 없어서"*가 된다. 예외의 조건은 **되돌릴 수 없는 상태(퇴사)** 하나여야 하며, 판단이 개입하는 조건(급함·중요함)을 넣으면 예외가 규칙이 된다.

**90일 상한의 근거** — 인수인계 필요는 대개 90일 안에 발생한다. 무기한 열람 가능 상태로 두면 그건 실질적으로 상시 열람권이고, 그 상태를 아는 재직자는 자기 문서도 언젠가 그렇게 될 거라고 예상한다.

**반대 논거** — "2인 승인은 현실적으로 번거롭다. 관리자가 한 명인 회사도 있다."
→ 번거로워야 한다. 이건 마찰이 목적인 절차다. 관리자가 1인인 조직에서는 **지정 창구(인사팀)를 두 번째 승인자로** 지정하게 하고, 그마저 불가능하면 **우리(공급자)가 두 번째 승인자**가 된다. 승인 요청은 우리에게 티켓으로 오고, 우리는 퇴사 사실만 확인한다.

### (3) 부서가 없어진 경우

상위 부서로 승계 → 상위가 없으면 `미배정` 부서 → 조직 관리자가 배정.

## 6.3 퇴사자가 삭제를 요구하면

**결정 — 업무 흐름의 뼈대는 남고, 그 사람의 흔적은 지운다. 그리고 이 처리는 요구를 기다리지 않고 퇴사 90일 후 자동 실행된다.**

| 남는 것 | 지워지는 것 |
|---|---|
| 단계·순서·갈래·기다림 구조 | 실명 표시 → **역할명 자동 치환** |
| 도구·소요시간 밴드·빈도 | **"실제로는 이렇게 합니다" 노트 전량** |
| 담당자 FK (표시는 역할명) | 개인 메모 (*"그 시간에 하고 싶은 일"*) |
| 짜증 플래그 (원래 익명) | 체크리스트 실행 기록 |
| 집계 기여분 | 열람 로그의 본인 행 |
| | 프로필 사진·연락처 |

**"요구를 기다리지 않는다"가 이 정책의 핵심이다.** 요구해야 지워지는 권리는 실제로는 거의 행사되지 않는다. 퇴사자가 90일 뒤에 로그인해서 삭제 버튼을 누를 확률은 0에 가깝다. **그래서 기본 동작으로 만든다.**

**업무 기록 자체를 삭제하지 않는 근거**
- 재직 중 업무 수행의 산출물이고, 업무 연속성이라는 회사의 정당한 이익 범위 안이다
- 이 점을 **최초 고지·약관·퇴사 안내 세 곳에 명시**한다. 나중에 통보하지 않는다
- 법적 개인정보 파기 요구는 별도로 존중하되, **대상은 "개인정보"이지 "업무 절차 기록"이 아님**을 처음부터 구분해 고지한다

**반대 논거** — "내가 만든 문서인데 왜 못 지우나."
→ 재직 중에는 언제든 지울 수 있습니다. 지우지 않고 나가신 문서는 **회사가 인수인계를 위해 보유**합니다. 다만 그 문서에서 당신을 알아볼 수 있는 부분은 전부 사라집니다. 남는 건 *"이 일은 이런 순서로 한다"*이고, 그건 당신에 대한 정보가 아닙니다.

## 6.4 "이건 사적인 메모라 회사에 남기기 싫다"

### 개인 메모는 회사 데이터가 아니다

세 종류를 **명시적으로 분리**한다.

| 필드 | 성격 |
|---|---|
| "실제로는 이렇게 합니다" 노트 | 단계에 붙는 비공개 노트 |
| "그 시간에 하고 싶은 일" | 분석 결과 하단 자유 입력 |
| 체크리스트 실행 기록 | 언제 무엇을 체크했는지 |

| 대상 | 처리 |
|---|---|
| 공유 링크 | 포함 안 됨 |
| 내보내기 | 기본 미포함, 선택 시에만 |
| 집계·분석 | **들어가지 않음.** 5인 이상 익명 집계에서만 반영(TRUST.md 공포 3) |
| 소유권 이전 | **따라가지 않고 삭제됨** |
| 퇴사 | 자동 삭제 |
| 편집 권한자 | 못 봄 |
| 관리자 | 못 봄 (봉인 열람으로도) |

> **(노트 입력란 하단 · 상시)**
> 이 메모는 문서를 넘겨도 따라가지 않아요. 회사를 떠나실 때 같이 지워져요.

### 문서 단위 "개인용" 표시

> **(문서 설정)**
> 이건 그냥 제 메모예요
>
> 회사 지도에 안 들어가고, 집계에도 안 들어가고, 나갈 때 같이 지워져요.
> 대신 공유 링크를 만들 수 없고 인수인계 문서로도 못 뽑아요.

**반대 논거** — "다들 개인용으로 표시하면 회사가 얻는 게 없다."
→ 개인용 문서는 **공유도 내보내기도 안 된다. 그게 정의다.** 그런데 이 제품에서 사용자가 얻는 가장 큰 이득이 바로 인수인계 문서와 공유다(PRD §3.1). 즉 개인용 표시를 켜면 사용자가 자기 이득을 포기하게 되므로 실제로는 소수만 쓴다. 그리고 **개인용으로라도 적어두면 나중에 승격할 수 있다** — 안 적는 것보다 낫다. 이 옵션의 진짜 값어치는 사용된 문서 수가 아니라 **"거절할 수 있다는 사실 자체가 주는 안심"**이다.
계측한다 — 개인용 표시 비율이 20%를 넘으면 그건 옵션 문제가 아니라 §1~§2의 신뢰 장치가 안 먹히고 있다는 신호다.

## 6.5 이 정책을 언제 어떻게 고지하는가

| 시점 | 매체 | 내용 |
|---|---|---|
| **롤아웃 2주 전** | 인사팀 명의 전사 공지 | 소유권 · 평가 미사용 · 퇴사 처리 3가지 (WRITING.md §15) |
| **최초 로그인 첫 화면** | 약속 카드 (§12) | 클릭 없이 넘길 수 있다. 강제 확인 버튼 없음 |
| **첫 문서 저장 직후** | 약속 카드 재노출 1회 | **실제로 읽는 시점이 여기다** |
| **첫 공유 링크 생성 시** | 인라인 | 공유 범위와 열람 로그 |
| **첫 내보내기 시** | 인라인 | 개인 메모 미포함 |
| **상시** | 설정 > 개인정보 | 약속 카드 전문 + "관리자 화면에 없는 것" 목록(§8.3) |
| **퇴사 절차 시작 시** | 인앱 + 이메일 | D-14 안내 |
| **정책 변경 시** | §11 |

**강제 확인 버튼을 두지 않는 이유** — 읽음 확인은 읽히지 않는다. 동의 버튼은 마찰만 만들고 실제 이해를 만들지 않으며, 첫 화면에서 버튼을 강요하는 제품은 **"약관을 들이미는 회사 시스템"**으로 읽힌다. 그게 WRITING.md §4 첫 화면이 피하려는 정확히 그 인상이다.

# 7. 문서 생명주기 정책

## 7.1 신선도 확인 주기

**결정 — 날짜가 아니라 "그 단계가 얼마나 변하기 쉬운가"와 "마지막으로 실제 쓰인 게 언제인가"로 정한다. 기본 90일.**

| 주기 | 조건 |
|---|---|
| **30일** | 최근 90일 안에 단계가 2회 이상 수정됨 (변동성 높음) / 담당자가 바뀐 단계가 있음 / `freq_last_7d ≥ 5`인 고빈도 흐름 |
| **90일 (기본)** | 그 밖의 전부 |
| **180일** | 최근 2회 연속 `맞음`으로 확인됨 / 빈도가 분기·연 단위 / 공용 흐름 |

**타이머 리셋 사건 (알림 없이)**
- 체크리스트로 실행 → **즉시 확인으로 간주** ← 주 경로
- 단계 편집 → 그 단계만 리셋
- 신선도 프롬프트에 `맞음` 응답 → 문서 전체 리셋

**계산은 단계 단위(`last_confirmed_at`), 질문은 문서 단위로 묶어 3단계만** 보여준다(WRITING.md §13 신선도 DM).

**근거**
- 고정 주기 알림은 무시당한다 — DECISIONS.md에서 이미 기각된 항목이다(*"6개월 됐으니 검토하세요"*).
- 실제로 변하는 것에만 묻는 것이 응답률을 지킨다. 알림 예산이 주 3건뿐이라 **어디에 쓸지가 정책의 실체**다.
- **확인해준 사람에게 덜 묻는다.** 성실한 사람이 더 자주 시달리는 구조를 만들지 않는다. 이건 공정성 문제이자 이탈 방지 장치다.

**반대 논거** — "180일은 너무 길어서 문서가 썩는다."
→ 2회 연속 안 변한 문서는 실제로 안 변하는 문서다. 그리고 그런 문서도 **열릴 때 마지막 확인일이 보이고**(§5.3), 체크리스트로 실행되면 그 자리에서 갱신된다. 알림 예산은 변하는 문서에 쓰는 것이 총 갱신량을 최대화한다.

## 7.2 자동 아카이브

**조건 — 12개월간 다음 넷이 **모두** 없을 때**

1. 신선도 확인 없음
2. 편집 없음
3. **열람 없음** (소유자·타인 모두)
4. 체크리스트 실행 없음

**절차 — 예정일 14일 전 알림 1건**

> **(인앱 + 이메일 · 여러 문서면 묶어서 1건)**
> 1년 넘게 안 열어보신 흐름이 3개 있어요. 2주 뒤에 보관함으로 옮길게요.
> 지워지는 게 아니라서 언제든 다시 꺼낼 수 있어요.
> `[그대로 둘게요]` `[보관함으로 옮겨도 돼요]`

**14일인 근거** — 7일은 휴가 한 번에 놓친다. 30일은 잊는다. 14일은 국내 근무 리듬(연차·출장·외근)에서 최소 한 번은 로그인하는 창이다.
`[그대로 둘게요]` 1클릭이면 **12개월 연장**된다. 이 버튼이 신선도 확인보다 응답 부담이 낮아야 하므로 문서 내용을 묻지 않는다.

**알림을 끈 사람** — 아카이브는 되돌릴 수 있으므로 손실이 없다. 실행 후 인앱 소식함에 30일간 남는다.

## 7.3 아카이브된 문서의 상태

| 항목 | 상태 |
|---|---|
| 목록·검색 | 제외. 단 `보관함` 탭에서는 검색됨 |
| 소유자 열람 | ✔ 가능 |
| 소유자 편집 | ✔ 가능 — **편집하면 자동 복원** |
| **공유 링크** | **정지** (삭제 아님). 복원하면 **같은 링크가 되살아난다** |
| 집계·조직 지도 | **제외** |
| 자동화 후보 | 제외 |
| 복원 가능 기간 | **무기한** |
| 복원 주체 | 소유자 (퇴사자 문서는 §6.2 봉인 절차) |

> **(정지된 링크를 연 사람에게)**
> 이 흐름은 보관함으로 들어갔어요. 만든 분에게 다시 요청하시면 됩니다.

**링크를 정지하는 근거** — **아무도 안 보는 문서가 회사 밖에서 계속 열리는 상태가 가장 나쁘다.** 그리고 조건 (3)에 열람 없음이 포함되어 있으므로, 아카이브 대상이 된 문서의 링크는 12개월간 한 번도 안 열린 링크다. 실무 피해가 거의 없다.

**집계에서 빼는 근거** — 죽은 문서가 경영진 백로그를 오염시키면 **자동화 후보 목록 전체의 신뢰도가 무너진다.** 그게 무너지면 경영진 약속(PRD §3.2)도 못 지킨다. 살아있는 200개가 죽은 2,000개보다 낫다.

## 7.4 삭제와 아카이브의 차이 — 사용자 설명

두 동작을 **같은 자리에 나란히 두지 않는다.** 보관은 `•••` 메뉴 상단, 삭제는 맨 아래 `danger`.

> **보관함으로 옮기기**
> 목록에서 안 보이게 돼요. 지워지진 않아요. 언제든 다시 꺼낼 수 있어요.
> 만들어두신 링크는 잠깐 닫히고, 다시 꺼내면 그대로 열려요.

> **지우기**
> 30일 안엔 되돌릴 수 있어요. 그 뒤에는 완전히 없어져요.
> 만들어두신 링크는 지금 바로 닫혀요.

| | 보관 | 삭제 |
|---|---|---|
| 되돌리기 | 무기한 | **30일** |
| 링크 | 정지 후 복구 가능 | 즉시 무효, 영구 |
| 집계 | 제외 | 제외 |
| 물리 삭제 | 없음 | 30일 후 |

## 7.5 고아 문서

| 원인 | 처리 |
|---|---|
| **퇴사·계정 비활성화** | §6.2 봉인 이전 (부서 아카이브) |
| **부서 소멸 (조직 개편)** | 상위 부서 승계 → 없으면 `미배정` |
| **SCIM에서 사라졌으나 퇴사가 아님 (동기화 오류)** | **자동 처리하지 않는다.** 30일 유예 → 미복구 시 봉인 이전 |

**세 번째가 중요하다.** SCIM 오설정으로 대량 deprovision이 오는 사고는 실제로 흔하고, 그때 문서가 즉시 봉인되면 복구 비용이 크다. §9.3과 연결된다.

**고아 문서를 집계에서 빼지 않는다** — 프로세스 지식은 조직에 남는다(TRUST.md §5 응답 스크립트 3의 근거). 다만 `last_confirmed_at`이 계속 밀리므로 **분석 스코어가 자동 감쇠**한다(PRD §4.10). 즉 별도 정책 없이 시간이 알아서 처리한다.

| 2 | 문서화된 흐름 수 / 부서 간 인계 수 | 프로세스 | |

| 4 | 자동화 후보 TOP N | 프로세스 | 기여자 5인 이상 |
| 5 | **제거 후보 (ECRS)** | 단계 유형 | |
| 6 | 문서 신선도 | 조직 | **건수만.** 문서 목록 아님 |
| 7 | 자동화 착수·완료 건수 + 절감 추정 | 건 | **신뢰도 등급 병기 필수** |
| 8 | **"우리가 보지 않는 것" 패널** | — | 숨길 수 없음 |
| 9 | 도구 사용 분포 | 카탈로그 | 5인 이상 |
| 10 | 관리 활동 감사 요약 | 조직 | 본인 조직만 |
| 11 | 좌석·플랜 사용량 | 조직 | |

**기간은 프리셋만** — `최근 30일 / 최근 90일 / 최근 365일 / YYYY-MM`. 임의 기간 파라미터가 API에 존재하지 않는다. **동시 필터 최대 2개**, 필터 적용 후 `HAVING` 재평가. (MEASUREMENT.md §3 방어 1·2)

**절대 표시하지 않는 것** (MEASUREMENT.md §5에서 그대로 승계)
개인 이름·pid / 문서 목록·문서 링크 / 개인별 작성 수·소요시간 합계·짜증 플래그 / **미사용자 명단** / 부서 내 개인 순위 / 로그인·활동 시각 / 5인 미만 어떤 셀도 / **모든 드릴다운**

## 8.2 Export

**결정 — 허용한다. 단 화면에 보이는 것과 정확히 같은 것만. API는 제공하지 않는다.**

| 항목 | 값 |
|---|---|
| 형식 | CSV · PDF · PNG |
| 행 단위 | **화면의 행 단위와 동일** (프로세스 × 부서 × 기간 프리셋) |
| 횟수 | 조직 **월 20회** |
| API | **없음** (v1) |
| 감사 | 전량 로그 + 분기 공개 요약에 건수 |

**API를 만들지 않는 근거** — API가 생기면 임의 파라미터 조합으로 **차분 공격(differencing)**이 가능해진다. MEASUREMENT.md §3이 *"이게 5인 차단을 무력화하는 가장 흔한 공격이고, 대부분의 구현이 여기서 뚫린다"*고 명시한 지점이다. 화면과 export가 **같은 뷰를 쓰면 k-익명 방어가 한 곳에만 있으면 된다.** 방어 지점이 하나면 CI 퍼즈 테스트도 하나면 된다.

**월 20회 상한의 근거** — 실무상 충분하고(주 5회), 대량 반복 export를 통한 차분 공격을 비용으로 막는다.

**Export에 반드시 포함되는 것**

```
만든 날짜: 2026-08-17
기간: 최근 90일
5명 미만이 관여해 계산하지 않은 항목: 14개

이 표에는 개인이 들어 있지 않습니다.
5명보다 적은 인원이 관여한 항목은 숨긴 것이 아니라 계산을 하지 않았습니다.
```

**억제 건수를 함께 주는 이유** — 숨긴 것을 숨기지 않는 것이 신뢰다. 그리고 억제가 많으면 관리자가 *"우리 조직은 아직 참여 부서가 적다"*를 알게 되어 **올바른 행동(더 많은 부서 참여)으로 유도**된다. 억제 건수를 감추면 관리자는 데이터가 없는 건지 막힌 건지 몰라서 우리를 의심한다.

## 8.3 "우리가 보지 않는 것" 패널

**위치** — 상단 1줄 배너 + **하단 전체 패널** 둘 다.
상단은 경고(WRITING.md §14에 이미 확정된 문구), 하단은 목록. 상단만 두면 배너 맹시가 생기고, 하단만 두면 안 읽는다.

> **(상단 고정 배너 — WRITING.md에서 승계)**
> 이 화면의 숫자는 일에 대한 거예요. 인사 평가에 쓰는 순간, 다음 분기부터 아무도 사실대로 적지 않습니다.

> **(하단 패널 — 그대로 인쇄)**
> **이 화면에 없는 것**
>
> · 개인 이름과 개인별 기록
> · 누가 무엇을 몇 개 적었는지
> · 아직 안 적은 사람의 명단
> · 개인별 소요시간 합계
> · 짜증 표시를 누가 눌렀는지
> · 체크리스트 실행 기록
> · 부서 안의 개인 순위
> · 로그인·활동 시각
> · 5명보다 적은 인원이 관여한 모든 항목
> · 위 숫자에서 개인으로 내려가는 경로
>
> 이 목록은 아직 안 만든 기능이 아니라, **만들지 않기로 한 것**입니다.
> 문의가 오면 이 화면을 그대로 보여주셔도 됩니다.

**두 가지 규칙**

1. **관리자가 이 패널을 숨길 수 없다.** 설정에 토글이 없다.
2. **직원도 같은 목록을 본다.** 설정 > 개인정보에 *"관리자 화면에는 이런 게 나오고, 이런 건 안 나와요"*로 동일 목록을 인쇄한다.

**2번의 근거** — 관리자만 보는 약속은 약속이 아니다. WRITING.md §14-5가 직원 화면 문구를 관리자가 못 바꾸게 한 논리(*"모두가 같은 문구를 보고 있다는 게 이 도구가 작동하는 조건"*)를 그대로 확장한 것이다. 그리고 실무적으로도 — 직원이 *"관리자 화면에 뭐가 나와요?"*라고 물었을 때 **관리자에게 물어보라고 하지 않아도 되는 것**이 이 제품의 신뢰 구조다.

**마지막 줄이 왜 중요한가** — *"만들지 않기로 한 것"*이라는 표현이 TRUST.md의 핵심 논지(*"만들 수 있는데 안 만들었다"는 증명*)를 관리자 화면 안에서 매일 갱신한다. 그리고 관리자에게 **거절할 언어를 손에 쥐어준다** — 경영진 요구가 왔을 때 이 화면을 보여주면 된다.

## 8.4 관리자 활동 감사 로그의 공개 대상

**결정 — 3중 공개.**

| 대상 | 주기 | 내용 |
|---|---|---|
| **당사자 본인** | 즉시 | 자기 문서·계정에 일어난 관리 행위 (소유권 이전, 계정 비활성화, 발췌 열람) |
| **지정 창구 (인사팀)** | 월간 | 관리 행위 요약 + 봉인 열람 건수 + export 건수 + **"관리자 뷰가 개인을 조회할 수 없었음"의 증명** |
| **전 직원** | 분기 | 조직 설정 페이지에 상시 게시 |

> **(전 직원 공개 · 분기)**
> **이번 분기에 관리자가 한 일**
>
> 초대 34건 · 부서 바꾸기 6건 · 집계 내보내기 12건
> 그만두신 분 문서 열어보기 1건
> **지금 다니시는 분 문서 열어보기 0건 (열 수 있는 방법이 없어요)**

**마지막 줄이 이 정책의 핵심이다.** *"0건(불가능)"*이 분기마다 인쇄되는 것 자체가 제품의 약속을 갱신한다. 그리고 이 숫자는 조작할 수 없다 — 0이 아닐 수 있는 경로가 코드에 없기 때문이다.

**감사 로그 규격**
- append-only 저장소, 보존 **3년**
- 애플리케이션 DB 롤에 `DELETE`·`UPDATE` 권한 없음
- **조직 관리자도, 시스템 관리자도, 우리도 지울 수 없다**

**공급자(우리)의 접근**

| | 규칙 |
|---|---|
| 상시 접근 계정 | **두지 않는다** |
| 집계·설정 접근 | 조직 관리자의 **건별 승인** + 최대 24시간 + 로그 |
| **문서 본문 접근** | **소유자 본인의 동의로만.** 조직 관리자 승인으로도 불가 |
| 로그 | 고객사 감사 로그에 우리 접근도 함께 기록 |

**문서 본문에 조직 관리자 승인이 안 통하는 이유** — 통하면 조직 관리자가 우리를 경유해 문서를 여는 경로가 생긴다. 원칙 1의 우회로가 공급자 지원 채널을 통해 열리는 것이 이 종류 제품에서 가장 흔한 붕괴 지점이다.

## 9.3 부서 구조 동기화(SCIM) 실패

**결정 — 동기화 실패는 절대 삭제로 이어지지 않는다. 실패는 항상 "보류"로 처리한다.**

| 실패 유형 | 처리 |
|---|---|
| **부분 실패** (일부 사용자 누락) | 누락 사용자를 **비활성화하지 않고 기존 상태 유지.** 관리자에게 알림(#14, 즉시) |
| **전체 실패** (연결 끊김) | 마지막 성공 스냅샷 유지. 그동안 수동 초대 허용 |
| **deprovision 이벤트** | ① 즉시 로그인 차단 ② 문서는 **30일 유예** ③ 유예 중 재활성화되면 원상 복구 |
| **부서명 충돌·계층 변경** | 이전 부서 ID 유지 + 매핑 테이블로 승계 (집계 연속성) |
| **5인 미만이 된 부서** | 즉시 `small_dept` 처리 |

**deprovision에 30일 유예를 두는 근거** — SCIM 오설정으로 대량 deprovision이 발생하는 사고는 실제로 흔하다(필터 조건 하나 잘못 건드리면 수백 명이 한 번에 빠진다). 그때 문서가 즉시 봉인되면 복구 비용이 크고, 무엇보다 **직원 입장에서는 "어느 날 갑자기 내 문서가 사라졌다"**가 된다. 그 사고 한 번이면 그 조직에서 이 제품은 끝난다.

**부서 이동 시 권한을 회수하지 않는다**

부서가 바뀌어도 이미 만든 공유 링크와 팀 서재 게시는 유지된다. 새 부서 기준으로 자동 노출되는 것도 없다.

**근거** — §1.5에서 부서 자동 권한을 안 만든 이유와 같다. **조직 개편이 권한 개편이 되지 않게 한다.** 그리고 이 규칙이 있어야 팀 서재가 안전하다 — 소유자가 명시적으로 올린 것만 그 자리에 남는다.

# 10. 요금·제한 정책

## 10.1 이중 좌석의 경계

> **자기 일에 대한 것은 전부 무료. 여러 사람의 일을 합쳐서 보는 것만 유료.**

| 무료 (전 직원) | 유료 좌석 (분석 좌석) |
|---|---|
| 기록·편집·삭제 | 집계 대시보드 |
| 공유 (조직 내·외부) | 자동화 후보 TOP N + 스코어 |
| 내보내기 (인수인계 문서·PDF·PNG) | 제거 후보 (ECRS) |
| 체크리스트 모드 | 불일치 리포트 |
| 요약 카드 | 집계 export |
| 신선도 확인 · 인계 요청 | 조직 지도 **조립 무제한** |
| 팀 서재 · 공용 흐름 열람 | n8n 실행 명세 export (M5+) |
| **조직 프로세스 지도 열람** | |
| 조직 지도 조립 **월 10건** | |

**이 경계가 프라이버시 경계와 정확히 겹치는 것이 핵심이다.** 유료 기능은 정의상 전부 집계(사람이 안 나오는 것)이고, 무료 기능은 정의상 전부 개인 문서다. **과금 경계와 정책 경계가 같으면 가격 협상이 정책 협상으로 번지지 않는다** — *"돈을 더 낼 테니 개인별로 보게 해달라"*는 요구가 성립할 수 있는 가격표가 아예 존재하지 않는다.

**열람을 유료화하지 않는 근거** — 열람자/작성자 3:1이 이 제품의 **유일한 유기적 성장 루프**다(PRD §7). 열람에 좌석이 붙으면 루프가 죽고, 루프가 죽으면 데이터 자산이 안 쌓이고, 그러면 유일한 해자가 사라진다.

**조직 지도 열람을 무료로 두는 근거** — 자기 흐름이 어디에 붙는지 보는 것은 **개인의 이득**이고, 그게 조립에 참여할 동기다. 유료화하면 대부분이 조립 제안을 무시하고, 조직 지도가 안 만들어지면 유료 기능(불일치 리포트)에 팔 것이 없다. **무료 기능이 유료 기능의 원재료를 만든다.**

## 10.2 무료 티어의 제한

| 항목 | 무료 조직 |
|---|---|
| **사용자 수** | **무제한** |
| **문서 수** | **무제한** |
| **데이터 보존** | 유료와 동일 (문서 무기한, 이벤트 13개월) |
| 집계 대시보드 | ✗ |
| 조직 지도 조립 확정 | 월 10건 |
| 그 밖의 전 기능 | ✔ |

**사용자 수를 제한하지 않는 근거** — 전 직원이 대상인 제품에서 좌석 상한은 존재 이유를 부순다. 그리고 좌석당 과금은 갱신 때 반드시 좌석 축소를 부른다(PRD §5.5).

**문서 수를 제한하지 않는 근거** — 문서 수 제한은 **"적지 마세요"라는 뜻**이다. 이 제품에서 그 메시지는 자살이다.

**보존 기간으로 압박하지 않는 근거** — *"무료는 3개월 뒤 삭제"* 같은 정책은 **"당신 기록이 인질"**이라는 뜻이다. 신뢰가 생존 조건인 제품에서 절대 안 된다.

**조립 10건 상한의 근거** — 조직 가치의 핵심이라 맛보게 하되, 전면 무료면 유료 전환 이유가 없다. **제한을 개인 행동이 아니라 조직 기능에 건다**는 것이 이 티어 설계의 원칙이다.

## 10.3 사용량 제한 — 남용 방지 목적, 압박 목적 아님

| 항목 | 한도 | 근거 |
|---|---|---|
| 문서당 단계 수 | **500** | 성능 한계 (ARCHITECTURE.md §5) |
| 1인 활성 공유 링크 | 50 | 링크 위생 |
| 1인 활성 외부 링크 | 10 | 유출 면적 |
| 1인 내보내기 | 하루 30회 | 렌더 비용 |
| 조직 집계 export | 월 20회 | 차분 공격 방어 (§8.2) |
| 붙여넣기 | 1회 20,000자 / 파일 20MB | |
| 챔피언 초대 | 월 20명 | 스팸 방지 |
| API | **없음** | §8.2 |

## 10.4 제한 도달 UX

**원칙 — 한도를 "당신이 많이 썼다"로 말하지 않는다.**

| ✗ | ✔ |
|---|---|
| `무료 플랜 한도에 도달했습니다. 업그레이드하세요.` | `링크가 50개예요. 안 쓰는 링크를 정리하면 새로 만들 수 있어요.` `[오래된 링크 보기]` |
| `문서 단계 수 초과` | `단계가 500개예요. 이쯤 되면 두세 개로 나누는 게 읽기 편해요.` `[나누는 것 도와드릴까요]` |
| `조립 크레딧을 모두 사용했습니다` | `이번 달 이어붙이기는 여기까지예요. 다음 달 1일에 다시 열려요.` |

**규칙 4가지**

1. **모달·배너·카운트다운 금지.** 인라인 한 줄로만
2. 업그레이드 안내는 **작은 텍스트 링크로만**, 그것도 관리자에게만 보인다
3. **직원 화면에 "플랜"·"요금"·"업그레이드"라는 단어가 나오지 않는다.** 결제 화면은 조직 관리자 화면에만 존재한다
4. 한도 문구는 전부 **다음 행동을 함께 준다** (정리하기·나누기·기다리기)

**3번의 근거** — 직원이 한도를 만나는 유일한 지점(링크 50개, 단계 500개)에서 요금 이야기가 나오면, 그 순간 이 도구는 **"회사가 돈 주고 산 시스템"**이 된다. WRITING.md §4의 첫 60초가 만들려는 인상("빈 노트")과 정면 충돌한다.

## 10.5 좌석 회수·구독 종료

| 상황 | 처리 |
|---|---|
| 분석 좌석 회수 | **기록·공유·내보내기는 그대로.** 대시보드만 닫힌다 |
| 구독 종료 | **90일간 읽기·내보내기 가능** (문서 회수 기간) |
| 90일 경과 | 조직의 데이터 보존 설정에 따름. 삭제 전 관리자에게 30일 전 통지 |
| **즉시 잠금** | **하지 않는다** |

**근거** — 데이터를 인질로 잡는 순간, 다음 갱신 협상에서 우리가 얻는 것은 계약이 아니라 **적대감**이다. 그리고 이 제품에서 데이터 인질은 직원에 대한 배신이기도 하다 — 직원은 회사의 결제 상태를 모르는 채로 자기 인수인계 문서를 잃는다.

# 11. 정책 변경 절차

## 11.1 변경 등급

| 등급 | 대상 | 사전 고지 | 소급 |
|---|---|---|---|
| **1급** | **절대 원칙 4개** + 이 문서의 봉인 조항 | **90일** | 없음 |
| **2급** | 권한 모델 · 공유 정책 · 데이터 소유권 · 대시보드 화이트리스트 · 알림 상한 | **60일** | 없음 |
| **3급** | 문구 · 한도 · 카탈로그 · 주기 · UI 위치 | 14일 (사용자에게 유리하면 즉시) | 유리한 것만 |

## 11.2 고지 방법

| 등급 | 방법 |
|---|---|
| **1·2급** | ① 전 사용자 인앱 공지 ② 조직 관리자 이메일 ③ **변경 이력 페이지 상시 공개** (제품 안, 로그인 없이 열림) ④ 직원용 1줄 요약 |
| **3급** | 인앱 소식함 + 변경 이력 페이지 |

**변경 이력 페이지에는 "무엇이 바뀌었나"뿐 아니라 "누가 요구했나"의 종류를 적는다.**

```
2026-11-01  링크 기본 만료 30일 → 유지 (변경 없음)
            요구 출처: 고객사 3곳 (90일로 늘려달라)
            판단: 기각. 근거는 POLICY §2.3
```

**근거** — 압력의 출처가 보이면 다음 압력을 예측할 수 있다. TRUST.md §8(*"이 헌장을 어길 뻔한 순간 기록"*)과 같은 논리이고, **기각된 요구도 함께 적는 것**이 핵심이다. 기각 기록이 쌓이면 그 자체가 다음 기각의 근거가 된다.

## 11.3 절대 원칙 4개를 바꾸려 할 때 — 장치가 필요한가

**결론부터: 필요하다. 그리고 정직하게 말하면 —**

> **바꿀 수 없게 만들 수는 없다. 바꾸는 것이 바꾸지 않는 것보다 비싸게 만들 수 있을 뿐이다.**

아래 다섯은 전부 **비용을 올리는 장치**다.

### 장치 1 — 코드에 남기는 봉인

| 원칙 | 봉인 위치 |
|---|---|
| 1. 관리자 자동 열람권 없음 | `resolveDocumentAccess()`가 `org_members`를 인자로 받지 않는다 (§1.0) |
| 2. 사람이 등장하지 않는다 | 개인 드릴다운 엔드포인트 부재. `pain_flag × assignee_id` 금지 조인 (§4.3) |
| 3. 5인 미만 차단 | 집계 뷰의 `HAVING contributor_n >= 5` + 2차 억제 (MEASUREMENT.md §3) |
| 4. 인사평가 미사용 | 인사 시스템 연동 부재. 개인 단위 export 부재 |

그리고 **CI 속성 기반 퍼즈 테스트가 매 배포마다 이를 검증하고, 실패하면 배포가 차단된다.** 원칙을 바꾸려면 **테스트를 먼저 지워야 하고, 테스트 삭제는 PR 디프에서 눈에 띈다.**

### 장치 2 — 계약에 남기는 봉인

도입 계약서에 4개 원칙을 **고객사에 대한 우리의 의무**로 명시한다.

**이 방향이 중요하다.** 우리가 원칙을 깨면 고객사가 계약 위반을 주장할 수 있는 구조다. 즉 **고객사가 요구해도 우리가 못 바꾼다** — 다른 고객사와의 계약을 위반하게 되기 때문이다.

### 장치 3 — 공개 선언

4개 원칙을 제품 밖 공개 페이지에 게시하고 변경 이력을 남긴다. **조용히 못 바꾼다.**

### 장치 4 — 절차 자체를 무겁게

1급 변경은 다음을 **전부** 충족해야 한다.

1. 90일 사전 고지
2. 전 고객사 조직 관리자 서면 통지
3. **전 사용자에게 개별 통지** (조직 관리자 경유 아님)
4. **통지 후 90일간 전액 환불 + 데이터 반출 권리**
5. 변경 전 작성된 데이터에는 **소급 적용 없음**

**4번이 핵심이다. 원칙을 깨면 우리가 돈을 잃도록 만들어 둔다.** 그리고 이 조항이 계약서에 있으면, 매출 압박 때문에 원칙을 깨자는 내부 제안이 나왔을 때 **재무적으로 자기모순**이 된다.

### 장치 5 — 단독 결정 불가 + 기록

1급 조항 변경은 우리 조직 내부에서 단독 결정할 수 없다 — 제품·법무·창업자 전원 서명. 그리고 **변경 시도 자체를** TRUST.md §8 표에 기록한다(성사 여부와 무관하게).

**반대 논거** — "이렇게 묶어두면 나중에 정말 필요한 변경도 못 한다."
→ 못 하는 게 목적이다. 이 넷은 제품 요구사항이 아니라 **제품의 정체성**이다(TRUST.md §1). 정체성이 바뀌어야 한다면 그건 정책 변경이 아니라 **다른 제품을 만드는 것**이고, 그때는 이 제품을 종료하고 새로 만드는 편이 정직하다. 인사팀 공지문에 이미 그렇게 적혀 있다 — *"이 문장을 어기게 되는 상황이 오면, 인력 조정보다 이 도구를 먼저 폐기합니다."*

## 11.4 소급 적용

**원칙 — 소급하지 않는다.** 사용자에게 불리한 변경은 **변경 이후 생성된 것에만** 적용한다.

| 예시 | 처리 |
|---|---|
| 링크 기본 만료 90일 → 30일 | 기존 링크는 **원래 만료일까지 유효** |
| 조직이 외부 공유를 끔 | 기존 외부 링크 **30일 유예 후 정지** + 소유자 전원 통지 |
| 알림 상한 하향 | 즉시 적용 (사용자에게 유리) |
| 보존 기간 단축 | 즉시 적용 (사용자에게 유리) |
| 새 금지 항목 추가 | 기존 문서를 검사하지 않는다. 새로 쓰는 것부터 |

**소급하는 예외 두 가지**
1. **법령 준수**
2. **사용자에게 유리한 변경** (더 많은 통제권, 더 짧은 보존, 더 적은 알림)

**집계 방법 변경은 항상 소급되지만**, 과거 리포트의 숫자가 바뀌면 반드시 병기한다.

> 계산 방법이 2026-11-01에 바뀌었어요. 그 전 리포트와 숫자가 다를 수 있어요.

**근거** — 소급 적용은 **권한이 조용히 변하는 것**의 다른 이름이다(지배 원칙 3). 어제 만든 링크가 오늘 갑자기 닫히는 경험 한 번이면 사람들은 링크를 안 만든다.

## 이 도구의 약속

**적은 건 내 것이에요**
문서는 나만 볼 수 있어요. 내가 링크를 만들기 전에는 팀장님도, 인사팀도, 대표님도 못 봅니다.

**누가 열어봤는지 내가 봐요**
내 문서를 누가 언제 열었는지 나는 볼 수 있어요. 반대는 없어요.

**관리자 화면에는 사람이 안 나와요**
*"구매 요청은 평균 6일 걸린다"* 같은 흐름 이야기만 보여요. 이름도, 개인별 기록도, 아직 안 적은 사람 명단도 없어요.

**5명보다 적으면 아예 안 세요**
적은 인원의 평균은 익명이 아니니까요. 숨기는 게 아니라 계산을 하지 않아요.

**여기 적은 건 인사평가에 쓰이지 않아요**
회사와 맺은 계약서에 들어 있는 약속이에요.

**규정대로가 아니라 실제로 하시는 대로 적어주세요**
실제와 규정이 다른 지점이 저희가 찾는 거예요. 그렇게 적었다고 불이익을 받지 않아요.

**메모는 따라가지 않아요**
*"실제로는 이렇게 합니다"* 메모와 개인 메모는 공유에도, 내보내기에도, 집계에도 안 들어가요. 문서를 넘겨도 따라가지 않고, 회사를 떠나실 때 같이 지워져요.

**알림은 일주일에 세 번까지**

## 이 문서를 쓰는 법

- 정책 변경은 §11의 등급을 먼저 판정하고 시작한다. 등급 판정 없이 바뀐 정책은 무효로 본다
- 새 기능이 위 어느 표에도 없는 권한·알림·집계를 요구하면 **그건 기능 추가가 아니라 정책 변경이다**
- 기각한 요구도 §11.2 변경 이력에 남긴다. **기각 기록이 다음 기각의 근거가 된다**
- 이 문서와 TRUST.md가 충돌하면 TRUST.md가 이긴다. 이 문서와 WRITING.md가 문구에서 충돌하면 WRITING.md가 이긴다
