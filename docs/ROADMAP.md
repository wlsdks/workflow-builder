## 0. 이 계획의 출발점 — 지금 실제로 있는 것

측정한 것만 적는다.

| | 상태 |
|---|---|
| 기획 문서 | 20종 / **16,625줄**. 착수에 필요한 결정은 사실상 다 나 있다 |
| `packages/graph-core` | **5,245줄 / 16파일**, `dependencies: {}`, 테스트 **378건 통과** (Node 24 네이티브 타입 스트리핑, 빌드 없음) |
| 그 외 코드 | **없다.** `app/`도, `db/`도, `package.json`(루트)도 없다 |
| 커밋 | 4개. 전부 문서 + graph-core |

**즉 지금은 "구현 착수 직전"이 아니라 "graph-core만 있고 나머지 전부가 0인 상태"다.** 이 구분이 §1 전체를 지배한다.

### graph-core가 이미 해결해 둔 것 (다시 만들지 말 것)

착수 시 가장 흔한 낭비가 "이미 있는 걸 앱 레이어에 다시 짜는 것"이다. 배럴(`src/index.ts`)에 있는 것만 쓴다.

| 이미 있음 | 앱에서 이걸로 뭘 하는가 |
|---|---|
| `derive()` / `validate()` | 아웃라인 → 그래프. 200노드 **0.64ms** |
| **`topologyHash`** | **구조 diff 게이트의 준비된 원시재료.** ELK를 돌릴지 말지 판정 |
| **`contentHash`** / `changedNodeIds()` | React Flow 리렌더 게이트 |
| `recomputeScope(ops)` / `needsLayout()` / `OP_SCOPE` | 22개 op별 재계산 범위표 |
| `toLayoutEdges()` (`reversedForLayout`) | 사이클을 ELK에 넘기기 전 역전 |
| `metrics` (`Measure{value, coverage}`) | 요약 카드(M3)의 계산이 **이미 끝나 있다** |
| `projectCanvasEdit()` / `canApplyCanvasEdit()` | 역투영. v1엔 안 쓰지만 이미 있음 |
| `toN8n()` | M5+ 스케치 |
| `compareSortKey()` | fractional index 정렬 (`localeCompare` 금지) |

> **주의**: `derive()`가 200노드에 0.64ms, ELK가 50~1500ms다. **레이아웃이 파생보다 1000배 비싸다.**
> 성능 작업은 전부 ELK 쪽에서 한다. `derive()` 최적화는 시간 낭비다 (D-056).

## 1. 마일스톤 재검토

### 1.1 결론 먼저

> **PRD의 M0~M4 = 9.5주는 1인으로도 2인으로도 불가능하다.**
> 순서는 대체로 옳다. **틀린 건 기간이고, 그 오차는 2~3배가 아니라 2인 기준 약 2배, 1인 기준 약 3배다.**

이건 기획자의 실수가 아니다. 마일스톤 표는 **"이 순서로 가치가 붙는다"**는 배열 논리(PRD §6.2 "개발 난이도 순에서 채택 순으로")를 담은 것이고, 그 논리는 맞다. 다만 **각 칸의 주 수가 어디서 나온 숫자인지 문서 어디에도 근거가 없다.**

반면 **같은 저장소 안에 반대 증거가 있다.**

> `COMPONENTS.md` 부록 「구현 순서」는 **컴포넌트 16개만 만드는 데 5주**를 배정한다.
> PRD의 M0(1주) + M1(2.5주) = **3.5주**다. 그 3.5주 안에 저 5주짜리 컴포넌트 작업의 대부분이 들어가야 하고,
> **파서·에디터·ELK·저장·인증·공유·계측은 그 위에 얹혀야 한다.**

두 문서가 같은 저장소에서 서로를 반증한다. 이 계획은 COMPONENTS 쪽 숫자를 믿는다. **그쪽이 항목을 세어서 나온 숫자이기 때문이다.**

### 1.3 순서 문제 — 의존성이 꼬인 곳 6군데

#### (a) ★ 파일럿 4주 실행안이 M4를 요구한다 — 가장 심각

`MEASUREMENT.md` 주차별 표를 마일스톤에 대입하면:

| 주 | 요구 기능 | 실제 마일스톤 |
|---|---|---|
| W1 | 문서 작성·저장, TTFD ≤12분 | M1 |
| W2 | 공유율 ≥30% | M1 |
| **W3** | **체크리스트 모드**로 채용 프로세스 실행 · **핸드오프 초대 실사용** | **M4** |
| **W4** | **신선도 슬랙 프롬프트 발송** · D14 재편집률 | **어느 마일스톤에도 없음** (PRD §4.10) |

**"M1 끝나면 파일럿"은 성립하지 않는다.** 지금 정의된 파일럿은 **M0→M4 전체 + 슬랙 신선도 봇**을 요구한다.
그리고 W4 실패 판정 기준(`D14 재편집률 <10% → 죽은 문서 생성기`)은 **정확히 M4 기능이 없으면 반드시 미달하게 되어 있다.**
→ **M4 없이 파일럿을 돌리면, 제품이 아니라 계측 설계가 만든 실패를 측정하게 된다.**

**결정: 파일럿을 두 개로 쪼갠다.** (§11)

#### (b) M1.5가 M1의 가설을 증명하는 데 필요하다

PRD가 스스로 이렇게 쓴다 — *"인수인계 문서… **이것 하나가 나머지 전부보다 채택률에 기여**"*, *"채택률의 절반"*.
그런데 M1 가설은 **"공유한다"**이다. **사람들이 공유하는 이유가 바로 인수인계다.**
인수인계 산출물 없이 공유율 30%를 측정하면, 공유 기능이 아니라 **공유할 이유의 부재**를 측정하게 된다.

또한 HANDOVER §6.0은 포맷 우선순위 1위를 **PDF가 아니라 공유 링크 `?view=handover`**로 못박았다. 이건 M1의 `/s/[id]` 라우트에 **뷰 하나 추가**하는 일이다 — 별도 마일스톤이 아니다.

→ **M1.5를 쪼갠다**: `?view=handover` (링크) + 서식 유지 복사는 **M1으로**, PDF·PNG·묶음 문서는 뒤로.

#### (c) 담당자 메타데이터(M2)가 M1.5 산출물의 전제다

인계 문서에서 "누가 하는가"가 빠지면 문서가 성립하지 않는다. 그런데 담당자는 M2다.
다행히 **D-055가 `assigneeId = null`을 "모름"이 아니라 "앞과 같음"으로 정의**해 두었고, PRD §4.5는 "전원 '나'로 미리 채우고 바뀌는 지점만 지정"이다.
→ **담당자 하나만 M1으로 당긴다.** 도구·시간·빈도·😤는 M2에 남긴다. (WorkOS 디렉터리 싱크가 M1에 이미 있으므로 추가 비용이 작다)

#### (d) k-anon 퍼즈 테스트(W0 필수)가 존재하지 않는 화면을 검증해야 한다

W0는 **"k-anon 퍼즈 테스트 CI 통과 — 미통과 시 파일럿 자체 중단"**을 요구한다.
그런데 퍼즈 대상인 **관리자 집계 뷰는 M5+**다. 대상이 없으면 퍼즈는 **공허하게 통과한다(vacuously true)** — 최악의 실패 모드다. 통과했다는 착각만 남는다.

→ **집계 뷰를 M5+에서 M0으로 당긴다.** 단 화면이 아니라 **DB 뷰 + 쿼리 계층만.**
ARCHITECTURE §9-7이 이미 *"집계 5인 미만 차단을 DB 뷰로. 애플리케이션 레벨 검사는 언젠가 우회된다"*고 지시했다. **뷰를 먼저 만들고 화면을 나중에 붙이는 것이 옳은 순서다.**

#### (e) 접기(collapse)가 마일스톤 표에서 누락됐다

D-037 — *"v1부터 넣는다. 나중에 추가하면 **ID 스킴과 레이아웃 캐시를 다시 손대야 한다**"*. M0~M4 어디에도 없다. → M1에 명시적으로 넣는다.

#### (f) 계측이 마일스톤 표에서 누락됐다

이벤트 ~50종 + 금지 속성 하드 차단 + PostHog 자체 호스팅(서울 VPC)이 어느 칸에도 없다. 그런데 W0 게이트다. → M0/M1에 분산해 명시한다.

| 지키는 것 | 자르면 무슨 일이 나는가 |
|---|---|
| **op 기반 변경 (`applyOps`)** | `saveDocument(wholeJson)`으로 시작하면 Yjs·undo·감사·AI diff의 **모든 mutation을 재작성**. ARCHITECTURE §9-1 |

| **도메인 SoT = `items` (ProseMirror JSON 아님)** | 에디터 상태 손상 복구·n8n 익스포트·Yjs가 동시에 지저분해진다 |

| **레이아웃 안정성 6종** | *"나중에 붙이는 최적화가 아니라 초기 설계 항목"*(DESIGN §6.6). 실패 원인 1위 |

| **`ruleVersion` / `pipelineId` 기록** | 파서 품질 회귀 추적이 영원히 불가능해진다 |
| **접근성 텍스트 정본(`<nav>`)** | ELK 폴백 UI를 겸한다. **하나 만들어 둘을 얻는 자리** |

**범위를 자르되 품질은 자르지 않는다.** 위 표의 왼쪽은 "안 만든다"이고, 오른쪽은 "대충 만들지 않는다"이다. 둘을 섞으면 계획이 무너진다.

## 3. 수직 슬라이스 우선순위

### 결론

> **한 기능을 끝까지. 그것도 "가장 얇은 기능 하나"를 가장 먼저 끝까지.**
> 첫 end-to-end 경로 = **로그인 → 문서 생성 → 한 줄 → 노드 하나 → 저장 → 공유 링크 → 로그인 안 한 타인이 열람.**

즉 S3(워킹 스켈레톤)이 S1·S2 다음에 오고, 에디터·캔버스·파서보다 **앞**에 온다.

### 왜 "모든 레이어를 조금씩"이 아닌가

레이어별 접근이 합리적으로 보이는 이유는 **각 레이어가 독립적으로 테스트 가능해 보이기 때문**이다. 이 프로젝트에서는 그게 함정이다.

1. **M1 가설이 문장 하나로 정의돼 있고, 그 문장이 정확히 이 경로다.**
   *"비개발자가 10분 안에 기록하고, 다이어그램을 남에게 보여줄 만하다고 판단해 **실제로 공유한다**"*.
   가설의 종착점이 **"타인이 링크를 연다"**이므로, **그 경로가 안 뚫린 채로 만든 모든 것은 가설 검증에 0을 기여한다.** 에디터를 3주 완벽하게 만들어도 공유가 안 되면 측정되는 게 없다.

2. **North Star가 "타인에게 1회 이상 열람된" 문서 비율이다.** 열람 경로가 제품의 **유일한 유기적 성장 루프**(열람자/작성자 ≥3:1)다. 성장 루프를 마지막에 붙이는 계획은, 루프가 안 돌 때 고칠 시간이 없는 계획이다.

3. **이 경로에 이 프로젝트의 위험이 전부 한 번씩 걸려 있다.**
   인증(WorkOS) · 테넌시(RLS) · op 파이프라인 · `derive()` 결선 · ELK 워커(Turbopack) · 토큰 발급 · **로그인 없는 RSC 렌더** · 배포. 이 중 하나라도 안 붙으면 M1은 없다. **8주 뒤가 아니라 3주차에 아는 편이 5배 싸다.**

4. **`/s/[id]`는 기술적으로 가장 이질적인 화면인데 가장 늦게 만들기 쉽다.**
   *"공유 페이지는 하한선을 훨씬 낮게 — RSC 정적 HTML + 서버 렌더 SVG로 **JS 없이도** 아웃라인 전문 열람 가능. **열람자를 통제할 수 없기 때문이다**"*(STATES §9).
   이건 클라이언트 에디터와 **완전히 다른 렌더 경로**다. 마지막 주에 발견하면 재앙이다.

5. **데모가 매주 나온다.** 스켈레톤이 있으면 이후 모든 스프린트가 "이미 도는 것에 살을 붙이는" 형태가 되어 매주 데모가 자동으로 나온다. 레이어별로 가면 8주차까지 보여줄 게 없다.

### 예외 — 수직 슬라이스보다 먼저 가는 것 2가지

수직 슬라이스 원칙에도 **되돌리기 비싼 것은 먼저 간다.**

| 먼저 가는 것 | 이유 |
|---|---|
| **S1: 토큰·CI 게이트** | 게이트는 코드가 쌓인 뒤엔 못 넣는다. 기존 코드가 전부 위반이라 "일단 끄자"가 된다 |
| **S2: 스키마·RLS·k-anon 뷰** | ARCHITECTURE §9의 "되돌리기 비싼 순" 1~7번이 전부 여기 있다. 특히 op 기반·UUID·fractional index·집계 뷰 |

**그 외 모든 것은 얇게 뚫고 나서 두껍게 만든다.**

### 슬라이스 순서 요약

```
S1 게이트  →  S2 스키마·테넌시  →  ★S3 워킹 스켈레톤(끝까지)★
     ↓
그 다음부터는 "이미 도는 경로를 각 지점에서 두껍게":
   S4~S6 왼쪽(에디터)  →  S7~S8 오른쪽(캔버스)  →  S9~S10 입구(파서·질문)  →  S11 출구(인계·공유)
```

**두껍게 만드는 순서의 근거**: 사용자는 **오른쪽이 늦게 뜨는 건 용서하지만 왼쪽이 안 먹히는 건 못 참는다**(STATES §10-2). 그래서 에디터가 캔버스보다 먼저다. 그리고 입구(파서)보다 본체(에디터)가 먼저인 이유는, 파서의 출력이 결국 에디터 블록이라 **에디터 스키마가 확정되기 전에 파서를 만들면 두 번 만들기 때문**이다.

### S1 — BlockNote 커스텀 블록으로 분기 컨테이너가 되는가 ★최대 미지수

**시간 박스: 3일 (2인 중 1인 전담)**

> **이 스파이크는 §0-1(에디터 아키텍처 모순)도 함께 판정한다.**
> `COMPONENTS §5`는 OutlineBlock을 **직접 만든 `<div role="list">` + `<textarea rows=1>`**로 명세했고, `ARCHITECTURE §3`·`D-034`는 **BlockNote**를 지시한다. 두 문서가 서로 다른 제품을 그리고 있다.
> **판단 기준은 하나다 — 한국어 IME.** ARCHITECTURE §3이 BlockNote를 고른 첫 번째 근거가 *"contenteditable 조합 입력은 ProseMirror가 10년 넘게 잡아온 지옥"*이다. `<textarea>` 기반 직접 구현은 그 지옥을 **우리가 떠안는다는 뜻**이고, 그건 1~2인 팀이 감당할 수 있는 종류의 일이 아니다.
> → **BlockNote가 기본값이고, COMPONENTS §5는 "시각 명세"로 재해석한다**(레이아웃·상태·치수는 유효, 마크업 구조는 무효). 이 스파이크는 그 재해석이 성립하는지를 본다.

**정확히 무엇을 만드는가**
`createReactBlockSpec`으로 컨테이너 블록을 만들고 그 안에:
(a) 자식 블록을 담을 수 있는가 (`content: 'inline'`이 아니라 중첩 블록)
(b) 블록 헤더에 **인터랙티브 인풋**(조건 텍스트박스)이 들어가고 **포커스가 ProseMirror와 싸우지 않는가**
(c) 케이스 추가/삭제 시 자식 블록의 `block.id`가 **보존되는가** (D-031: ID가 위치에서 유도되면 안 됨)
(d) **한글 조합 중** 인풋과 본문 사이 포커스 이동이 조합을 깨지 않는가
(e) `Tab`/`Shift+Tab`이 갈래 안팎으로 동작하되 **유일 통로가 아니어도** 되는가

**성공 기준 (전부 충족해야 성공)**
- 3단계짜리 갈래 2개를 **마우스만으로** 만들고, 새로고침 후 **동일한 `block.id`로 복원**된다
- 조건 인풋에 한글 20자 입력 → 유실 0
- `blockToItem`이 컨테이너 → `kind:'branch'` + 자식 items로 **정확히** 변환된다

**실패 기준**: 위 중 하나라도 3일 안에 안 되면 실패.

**실패 시 아키텍처가 바뀌는가 — ★그렇다★**

| 대안 | 비용 | UX 손실 |
|---|---|---|
| ② 플랫 블록 + `branchId` 속성 + 시각적 그룹 렌더 | +3일 | 중간 (드래그·중첩이 어색) |
| ③ 갈래 편집을 **별도 모달**로 분리 | +2일 | 큼 ("글 쓰듯" 원칙 훼손) |
| ④ **BlockNote 폐기 → Lexical/자체 아웃라인** | **+4주 이상** | IME를 직접 떠안게 됨 — **선택하지 않는다** |

**④가 실질적으로 불가능하므로, ①이 실패하면 ② 또는 ③으로 간다. 즉 이 스파이크의 진짜 산출물은 "어느 UX를 포기할지"의 조기 확정이다.**

### S2 — 한국어 IME + ProseMirror + 자동저장 조합

**시간 박스: 2일**

**무엇을 만드는가**: BlockNote 에디터 + 800ms 디바운스 자동저장 타이머 + 슬래시 메뉴 + `derive()` 호출을 **동시에 켜 놓고** 한글을 친다.

**성공 기준**
- Playwright + CDP `Input.imeSetComposition`으로 `"한글"` 조합 → Enter → **마지막 글자 유실 0** (자동화된 상태로)
- **조합 중 저장 타이머가 발화해도 조합이 안 끊긴다** (타이머를 100ms로 낮춰 강제 발화시켜 검증)

- 조합 중 Enter가 블록을 분리하지 않는다 (한자·후보 확정용)
- macOS 2벌식 + Windows MS-IME **양쪽** 수동 확인
- NVDA + Chrome에서 조합 중 자모 반복 낭독 없음

**실패 기준**: CDP 테스트를 **CI에서 안정적으로 못 돌리면** 실패(플래키 포함).

**실패 시 아키텍처가 바뀌는가 — 부분적으로.**
CDP 자동화가 불가능하면 → **`ime_composition_lost` 프로덕션 이벤트를 주 방어선으로 승격**하고(MEASUREMENT: *"크롬 업데이트 회귀를 CI보다 먼저 잡는다"*), 수동 체크리스트를 **릴리스 게이트**로 만든다. 아키텍처는 안 바뀌지만 **릴리스 프로세스가 바뀐다.**
조합 중 저장/파생 정지가 근본적으로 안 되면 → **자동저장을 `compositionend` 기반으로만** 돌린다(디바운스 포기). 저장 지연이 늘지만 IME가 이긴다.

### S3 — ELK 워커 + 200노드 + 앵커링이 60fps인가

**시간 박스: 2일**

**무엇을 만드는가**: `derive()`로 200노드 합성 그래프 생성 → ELK 워커(옵션 16개 그대로) → React Flow 렌더 → 노드 하나를 "편집"했다 치고 **앵커링 역보정** → 재레이아웃.

**성공 기준**
- `elk_ms` p95 **< 300ms @200노드** (DESIGN 예상치는 50~150ms)
- 줌·팬 **60fps, 프레임 드랍 0** (Performance 패널 실측)
- 앵커링 적용 시 **활성 노드의 화면 좌표 변화 < 2px**
- **`jump_score` p90 < 0.15** (구조를 조금씩 20회 변경하며 측정)

**실패 기준**: 60fps 미달 또는 `jump_score` p90 ≥ 0.15.

**실패 시 아키텍처가 바뀌는가 — ★그렇다, 두 갈래로★**

| 실패 양상 | 대응 | 아키텍처 영향 |
|---|---|---|
| **ELK가 느리다** (elk_ms 과대) | 서버에서 사전 계산 + 좌표 캐시를 **1급 저장소로 승격**, 클라이언트 ELK는 백그라운드 검증으로 강등 | 중간 — `layouts` 테이블 + Route Handler 신설 |

### S4 — Postgres RLS + PgBouncer + Drizzle 조합

**시간 박스: 1.5일**

**무엇을 만드는가**: Postgres + PgBouncer(transaction pooling) + Drizzle. `SET LOCAL app.current_org = ...`를 트랜잭션 안에서 설정하고 RLS 정책이 걸리는지 확인. **커넥션이 재사용될 때 세션 변수가 남는지**를 집중 검사.

**성공 기준**
- transaction pooling 모드에서 **`SET LOCAL`이 트랜잭션 경계를 안 넘는다** (동시 100커넥션 부하에서 교차 오염 0건)
- Drizzle 트랜잭션 래퍼 안에서 RLS가 정상 작동
- **커넥션 반환 시 세션 변수 리셋 검증** 테스트가 있다
- 크로스테넌트 테스트 100케이스 전부 404

**실패 기준**: 교차 오염 1건이라도 발생, 또는 `SET LOCAL`이 pooling과 호환 안 됨.

**실패 시 아키텍처가 바뀌는가 — 예, 그리고 이건 감수할 만하다.**
- **대안 A**: PgBouncer를 **session pooling**으로 (커넥션 수 늘어남, 비용↑) — 300명 규모에선 감당 가능

  단 SECURITY §B가 *"둘 중 하나만 있으면 언젠가 뚫린다"*고 경고했으므로 보상이 필요하다:
  → **CI 크로스테넌트 테스트를 전 리소스·전 엔드포인트로 확대**하고, **테넌트 스코프 없는 쿼리가 타입 에러가 되는 래퍼**를 우회 불가능하게 만든다(raw `db.select()` 직접 사용을 ESLint로 차단).

> **이건 "보안을 낮춘다"가 아니라 "방어 지점을 하나로 모은다"이다.** POLICY §1130이 같은 논리를 쓴다 — *"방어 지점이 하나면 CI 퍼즈 테스트도 하나면 된다."*

### S6 — 붙여넣기 파서의 절 분할이 실제 한국어에서 되는가

**시간 박스: 2일** (문서엔 없지만 추가한다)

**왜 추가하는가**: PARSING.md는 **초안 v0.1**이고 §0이 스스로 *"이 두 개를 합의하지 않으면 아래 알고리즘의 **모든 임계값이 임의값**이 된다"*고 쓴다. `CLAUSE_THRESHOLD = 0.75`, 가중치 10종, 보너스/페널티 7종 — **전부 검증되지 않은 숫자다.**

- 30건에 대해 **precision ≥ 0.85** (목표 0.90의 근처. 미분할 편향이므로 precision이 생명)
- `assertLossless`가 30건 전부 통과

**실패 시 아키텍처가 바뀌는가 — 아니다. 범위가 바뀐다.**
- **미분할로 더 세게 편향**한다. `CLAUSE_THRESHOLD`를 0.75 → 0.85로 올리고, 애매하면 안 쪼갠다. **덜 쪼개면 사용자가 Enter를 치면 되지만, 잘못 쪼개면 사용자가 지운다.** 후자가 훨씬 비싸다
- 그래도 안 되면 **절 분할을 M1에서 뺀다.** 줄바꿈·번호·불릿만으로 분할(R1~R5)하고 R7은 M2로. 커버리지는 떨어지지만 **파서가 틀리는 것보다 낫다**

## 5. 테스트 전략

### 5.1 형태 — 피라미드가 아니라 트로피, 단 이유가 통념과 다르다

> **트로피(통합 테스트 중심)로 간다. 하지만 "단위 테스트가 별로여서"가 아니다.**

일반적인 트로피 논거는 "구현 세부에 결합된 단위 테스트는 리팩터링을 방해한다"이다. 이 프로젝트의 논거는 다르다.

**이 제품의 버그는 대부분 "레이어 사이"에서 난다.**

| 실제 위험 | 어느 레이어? |
|---|---|
| 한글 조합 중 자동저장 타이머 발화 → 글자 유실 | IME × 저장 큐 × React |
| 조합 중 리렌더 → composition abort | IME × `derive()` × 렌더 |
| 커넥션 풀 세션 변수 잔존 → 타인 문서 노출 | DB × 풀 × 인증 |
| 필터 조합으로 5인 차단 우회 | 쿼리 × 뷰 × 파라미터 |
| 레이아웃 점프 | `topologyHash` × 디바운스 × ELK × 앵커링 |
| 캐시 오염(`unstable_cache` + 사용자 데이터) | Next 캐시 × 인가 |

**이 중 단위 테스트로 잡히는 것이 하나도 없다.** 전부 두 개 이상의 것이 만났을 때만 난다.

**반대로 순수 로직은 이미 단위 테스트가 끝나 있다** — graph-core 378건. 그래서 "단위 테스트를 더 쓸 곳"이 사실상 파서밖에 없다.

### 5.2 비율과 경계

| 층 | 비율 | 무엇을 여기서 | 도구 | 실행 시점 |
|---|---|---|---|---|
| **순수 단위** | 25% | `graph-core`(완료·동결) · `paste-parse` 각 단계 · `doc-gen` 문장 생성 · 어휘 표 | `node:test` (러너 추가 없음) | 매 커밋, **< 10초** |
| **통합 ★주력** | **50%** | Server Action + 실제 Postgres(트랜잭션 롤백) · RLS · 집계 뷰 · op 리듀서 · 어댑터(`blockToItem`↔`itemToBlock`) · 저장 상태 머신 · React Testing Library 컴포넌트 상호작용 | Vitest + Testcontainers + RTL | PR, **< 4분** |
| **E2E** | 20% | **핵심 경로 8개만**(아래) | Playwright | PR(핵심 3) / merge(전체), **< 8분** |
| **정적** | 5% | tsc · ESLint · Stylelint · grep 게이트 | — | 매 커밋, **< 90초** |

**E2E는 8개를 넘기지 않는다.** E2E는 유지비가 가장 비싸고 플래키의 원천이다. 사용성 테스트 T1~T5(MEASUREMENT §7)를 그대로 자동화한 것 + 3개.

```
E1  붙여넣기 → 5단계 이상 저장            (T1)
E2  질문 연쇄 → 첫 다이어그램             (T2)
E3  Tab 없이 갈래 생성                    (T3)  ← 실패하면 제품 가설이 깨진 것
E4  공유 링크 생성 → 로그아웃 상태 열람    (T4)  ← M1 가설 그 자체
E5  오프라인 편집 → 복귀 → 전량 반영
E6  한글 IME 조합 → Enter → 유실 0        (CDP)
E7  조직 A 세션 → 조직 B 리소스 → 404
E8  인계 뷰 → 서식 유지 복사
```

### 5.3 한국어 IME 회귀 테스트 (CI 필수)

**이건 "테스트 항목"이 아니라 **이 제품의 생존 조건**이다.** Chrome 업데이트마다 회귀하고, **사람이 반드시 놓친다.**

**구성 2중**

```
① CI — Playwright + CDP Input.imeSetComposition
   - 매 PR. 실패 시 머지 차단
   - 브라우저 매트릭스: Chrome stable + Chrome beta (beta가 회귀를 먼저 잡는다)
   - 케이스 11개 (ACCESSIBILITY §10)
   - 특별 케이스: 저장 타이머를 100ms로 낮춰 조합 중 강제 발화

② 프로덕션 — `ime_composition_lost` 이벤트
   - MEASUREMENT: "크롬 업데이트 회귀를 CI보다 먼저 잡는다"
   - 발생 즉시 P1 알림. browser_key/os_key 별 집계
```

**②가 ①보다 빠르다는 문서의 지적이 중요하다.** CI는 우리가 고정한 브라우저만 본다. 사용자는 온갖 브라우저를 쓴다. **둘 다 필요하다.**

**주간 스케줄 잡**: Chrome beta·canary에 대해 E6을 매일 돌린다. 실패해도 머지는 안 막고 **알림만** — 회귀 조기 경보용.

### 5.4 k-익명성 퍼즈 테스트 (배포 차단)

**속성 기반. 임의 필터·기간 조합 10만 건 → 응답에 `contributor_n < 5` 셀이 단 1건도 없음.**

**설계 요구 3가지**

1. **대상이 실재해야 한다.** §1.3(d)에서 지적했듯, 집계 뷰가 없으면 퍼즈는 **공허하게 통과**한다. → 테스트가 **최소 1개 이상의 셀을 실제로 반환했음**을 함께 단언한다. *"차단된 셀 0건"과 "반환된 셀 0건"을 구분하지 못하는 테스트는 무용하다.*
2. **공격 벡터 5종을 모두 생성한다** (SECURITY §C): ① 기간 파라미터 차분 ② 필터 조합 ③ **입·퇴사에 의한 시계열 차분** ④ 라운딩 역산 ⑤ 억제 셀이 하나뿐일 때의 차집합 복원.
   특히 ③은 **시드 데이터에 입·퇴사 이벤트가 있어야** 생성된다 — 시드 설계 요구사항이다.
3. **금지 조인이 존재하지 않음을 타입으로 증명한다.** POLICY §610: `pain_flag × assignee_id` 조인이 **집계 뷰에 존재하지 않는다.** 이건 퍼즈가 아니라 **스키마 테스트**로 잡는다 — 뷰 정의에 해당 컬럼 조합이 있으면 실패.

**차단 범위**: 실패 시 **배포 차단**. 그리고 **파일럿 W0 게이트**이기도 하다(미통과 시 파일럿 중단).

**추가 방어**: 매일 1회 프로덕션 실데이터에 대해 동일 검사. `contributor_n < 5` 1건이라도 → **P0 + 관리자 대시보드 자동 차단**(킬스위치).

### 5.5 레이아웃 안정성 회귀 (`jump_score` p90 < 0.15)

**성능 테스트가 아니라 회귀 테스트로 만든다.** 한 번 통과하고 끝나는 숫자가 아니다.

```
고정 시나리오 12개 (시드 문서 10개 + 200노드 합성 2개)
  각 시나리오에 대해 결정적 편집 시퀀스 20스텝 실행
  각 스텝마다 jump_score 기록
  → p90 < 0.15 이면 통과, 아니면 실패
```

**결정성이 핵심이다.** 같은 입력이면 ELK는 같은 출력을 내야 하므로(`semiInteractive` 시드 포함) 이 테스트는 **재현 가능**해야 한다. 플래키하면 ELK 옵션이 비결정적이라는 뜻이고, **그 자체가 버그다.**

**CI에서는 경고, merge to main에서는 차단.** ELK가 느려서 PR마다 돌리기엔 부담(12 시나리오 × 20스텝 × 최대 1.5s = 6분).

**프로덕션 상시 계측 병행**: `canvas_layout_computed { jump_score, elk_ms, node_count }`. MEASUREMENT §465가 이미 **`jump_score` p90 > 0.15 → P1 알림, 배포 직후 자동 비교**로 정의했다.

### 5.6 시각 회귀 테스트 — 할 것인가

> **한다. 단 스크린샷 diff가 아니라 **토큰·대비 검사**로 한다.**

**전면 스크린샷 diff를 안 하는 이유**: 이 제품의 화면 대부분이 **자동 레이아웃 결과**다. ELK 좌표가 1px만 달라도 diff가 터진다. 유지비가 가치를 넘는다. 그리고 폰트 렌더링이 OS마다 달라 한글에서 특히 취약하다.

**대신 하는 것 3가지**

| | 무엇 | 차단? |
|---|---|---|
| **Storybook + 컴포넌트 단위 스냅샷** | STATES.md 전 상태에 스토리가 있어야 함(ACCESSIBILITY §10 요구). **컴포넌트 16개 × 상태**만 스크린샷. 캔버스·에디터 본문 제외 | PR 경고 |
| **대비비 자동 검사** | 토큰 조합 전체를 계산해 WCAG AA(텍스트 4.5:1, UI 3:1) 미달 0건 | **차단** |
| **색각 시뮬 아티팩트** | protanopia/deuteranopia/tritanopia/achromatopsia + grayscale 스크린샷을 **CI 아티팩트로 저장**(DESIGN §193). 자동 판정은 안 하고 사람이 본다. **줌 0.3배 포함** | 아니오 |

**세 번째가 특이하다**: 자동 판정 없이 아티팩트만 남긴다. **"타입 3종이 구분되는가"는 기계가 판정할 수 없지만, 매 릴리스에 5초 보는 것만으로 회귀가 잡힌다.**

### 5.7 접근성 — 자동 vs 수동

**목표: WCAG 2.2 AA.** ACCESSIBILITY.md가 2.4.11(포커스 가림), 2.5.7(드래그 대안), 1.4.10(400% Reflow)을 명시했으므로 2.1이 아니라 **2.2**다.

| | 자동 (axe-core, CI, **위반 0건 차단**) | 수동 |
|---|---|---|
| 잡히는 것 | 대비, 라벨 누락, ARIA 오용, 랜드마크, 중복 id, 명도 | — |
| **잡히지 않는 것** | — | **캔버스 텍스트 정본의 정확성** · 키보드 전체 플로우 완주 · 포커스 순서의 의미 · 스크린리더 낭독의 이해 가능성 · **IME 조합 중 낭독** · 400% 확대 실사용 · 40~50대 실사용 |

**수동 검증 주기**

| 시점 | 범위 | 담당 |
|---|---|---|
| **각 스프린트 DoD** | 그 주에 만든 화면만. 키보드 완주 + 400% 확대 (15분) | 만든 사람 |
| **M1 완료 시** | 전 플로우 × NVDA+Chrome / VoiceOver+Safari (반나절) | 2인 교차 |

**자동화 대상으로 특히 중요한 것 하나**: *"§2 텍스트 목록이 그래프와 **완전 일치**(골든 픽스처로 자동 비교)"*. 이건 axe가 못 잡지만 **골든 픽스처로는 잡힌다** — 접근성 테스트를 단위 테스트로 내린 드문 사례다. 반드시 만든다.

### 5.8 파서 테스트의 특수성

파서만 **속성 기반 테스트가 주력**이다.

```
① 골든 6건        — 기대 출력 완전 일치
② 무손실 퍼즈 1,000건 — "기대 출력은 없어도 무손실은 항상 참"
③ 프로덕션 assertLossless — 개발/프로덕션 모두. throw 시 결과 폐기 → 단일 블록 폴백
```

**③이 특이하다.** 보통 단언은 프로덕션에서 끄지만, 여기선 켠다. **이유: 파서가 사용자 텍스트를 잃는 것보다 파싱을 포기하는 게 낫다.** 실패해도 사용자는 "안 쪼개졌네"만 겪고, 원문은 그대로 남는다.

**픽스처 성장 규칙**: 파일럿에서 `edit_distance_band > 60%`인 실제 붙여넣기를 **익명화해 픽스처로 승격**. 이게 골든 픽스처를 LLM 도입 시의 eval set으로 만든다(PARSING §13.4-3).

### 5.9 안 하는 것

- **세션 리플레이 — 프로덕션 전면 금지**(MEASUREMENT §416). 디버깅용으로도 안 켠다
- 스냅샷(`.snap`) 파일 — graph-core가 이미 금지. *"스냅샷은 아무도 안 읽는다"*
- 커버리지 퍼센트 게이트 — 숫자를 채우는 테스트가 생긴다. **대신 "E2E 8경로 + STATES 전 상태 스토리"라는 목록 기반 게이트**를 쓴다
- 뮤테이션 테스팅 — 이 규모에서 비용 대비 효과 없음

- **프리뷰에는 실데이터를 절대 넣지 않는다.** 시드만

### 6.4 마이그레이션 자동화

```
PR         → 마이그레이션 파일 존재 시 스테이징 사본에 리허설 (up → 스모크 → down → up)
main merge → ① 마이그레이션 적용 ② 앱 배포   ← 순서 고정
```

**규칙 4개**

1. **확장 → 배포 → 수축 (expand-contract).** 컬럼 삭제·이름 변경을 앱 배포와 같은 배포에 넣지 않는다. 최소 2회 배포로 나눈다. 이게 있어야 롤백이 가능하다
2. **`COLLATE "C"` 같은 되돌리기 어려운 DDL은 첫 마이그레이션에.** 나중에 하면 인덱스 재생성 + 정렬 재검증이 필요
3. **down 마이그레이션 필수.** 리허설에서 왕복을 실제로 검증
4. **RLS 정책 변경은 반드시 크로스테넌트 테스트 추가와 같은 PR에**

### 6.5 롤백 전략

**계층별로 다르다. 하나의 "롤백 버튼"은 없다.**

| 무엇이 잘못됐나 | 조치 | 소요 |
|---|---|---|
| **앱 코드 버그** | 이전 배포로 즉시 되돌림 (마이그레이션은 그대로 — expand-contract 덕에 구버전이 새 스키마에서 돈다) | < 2분 |
| **기능 단위 문제** | **피처 플래그 킬스위치.** SECURITY §B가 "해당 기능 킬스위치"를 사고 대응 1단계로 명시 | < 30초 |
| **개인 데이터 노출** | ① 킬스위치 ② **캐시 전면 무효화** ③ 로그로 "누가 누구 문서를 언제 몇 초" 정확 산정 ④ **SEV1 무조건** ⑤ 양쪽 모두에게 통지 ⑥ **재발방지 CI 테스트 추가가 완료 조건** | 즉시 |
| **k-anon 셀 노출** | **관리자 대시보드 자동 차단(P0)** → 뷰 수정 → 퍼즈 통과 → 단계적 재개방 | 즉시 |
| **마이그레이션 실패** | down 실행. expand 단계면 안전, contract 단계면 **백업 복원** | 5~30분 |
| **데이터 손상** | `operations` 어펜드 로그로 재생. `snapshots` + 이후 op | 문서 단위 |

**킬스위치 대상 기능 목록을 M1 시점에 미리 정의한다**: 공유 링크 발급 / 공유 페이지 열람 / 붙여넣기 파싱 / 집계 뷰 / 인계 문서 생성 / 계측 수집.

> `operations` 어펜드 로그가 여기서 값을 한다. **문서 단위 시점 복구가 가능한 유일한 이유다.** ARCHITECTURE §9-1이 op 기반을 1순위로 둔 이유이기도 하다.

## 7. 성능 예산과 SLO

### 7.1 사용자 체감 지표

STATES §10의 5개 지점을 예산으로 승격한다.

| 지점 | 목표 | 임계(경고) | 실패 | 어떻게 지키는가 |
|---|---|---|---|---|
| **문서 열기 → 첫 노드** | LCP < 1.2s · 캔버스 첫 페인트 < 600ms | 1.8s | 2.5s | **저장된 좌표 캐시로 즉시 렌더**, ELK는 백그라운드 검증 |
| **첫 글자 입력 지연** | INP < 100ms | 200ms | 500ms | 에디터 아일랜드 **우선 하이드레이트**, 캔버스는 `requestIdleCallback` |
| **Enter → 노드 등장** | 140ms 안에 애니메이션 시작, **서버 왕복 0** | — | — | 완전 낙관적. `derive()` 0.64ms + 구조 diff 게이트 |
| **붙여넣기 → 결과** | 200줄 < **300ms**(동기) | 500ms | 800ms | 정규식 기반, AI 없음. 파서 자체 예산 **60ms** |
| **렌즈·줌·팬** | **60fps, 드랍 0** | — | — | 렌즈는 위치를 1px도 안 바꾼다 (CSS 변수 + opacity) |
| **저장 p95** | 왕복 < 800ms · **`저장 중` 체류 중앙값 < 400ms** | 1.5s | 3s | 800ms 디바운스 배치, op 200개 상한 |
| **첫 다이어그램까지(TTFD)** | **중앙값 ≤ 8분** (PRD 지표) | 12분 | — | 제품 지표 |
| **공유 페이지 `/s/[id]`** | LCP < 1.0s, **JS 0으로 본문 열람 가능** | — | — | RSC 정적 + 서버 렌더 SVG |

> **`저장 중` 체류 400ms가 특이하게 중요하다.** STATES: *"이 숫자가 커지면 **실제 데이터 손실이 없어도 사용자는 제품을 불신한다.**"* 성능 예산에 심리 지표가 들어간 드문 사례.

### 7.2 서버 SLO

> **기획 문서 20종 어디에도 가용성·응답시간 SLO가 없다.** 정량화된 것은 **RTO 4시간 / RPO 15분**(SECURITY §4.5)과 사고 통지 시한뿐이다.
> 아래 표는 **이 계획이 제안하는 값**이고, 승인이 필요하다. 문서에서 온 값은 ★로 표시했다.

**사내 도구다. 99.99%를 목표로 잡으면 비용만 쓰고 아무도 안 알아준다.**

| | 목표 | 측정 |
|---|---|---|
| 가용성 (편집 경로) | **99.5%** / 30일 (월 ~3.6시간) | 합성 모니터 1분 간격 |
| 가용성 (**공유 페이지**) | **99.9%** | 별도 측정 |
| `applyOps` p95 / p99 | 300ms / 800ms | 서버 타이밍 |
| 문서 로드 p95 | 400ms | |
| 에러율 (5xx) | **< 0.1%** | |
| ELK 워커 실패율 | < 0.5% | 클라이언트 이벤트 |
| ★ **RTO / RPO** | **4시간 / 15분** | 분기 1회 복구 훈련에서 실측·기록 |
| ★ 사고 통지 | T+1h 내부 선언 · **T+6h SEV1 고객사 CPO 1보** · T+24h 전 사고 통지 · T+72h 법정 신고 · T+7d 상세 보고 · T+30d 재발방지 완료 | 계약 의무(DPA #11) |

**복구 훈련은 절차 순서가 고정돼 있다** — 격리 복구 VPC → **tombstone 재적용** → 무결성 검증 → 기동 → **복원본 4시간 내 파기 + 대장 기록** → 소유자 통지.
2번째 단계를 **복원 스크립트의 강제 단계로 구현**한다. 런북에만 적으면 언젠가 건너뛰고, *"지운 문서가 장애 복구 때 되살아난다."*

**공유 페이지의 SLO가 더 높은 이유**: 편집자는 우리 직원이고 잠시 못 쓰면 기다린다. **열람자는 통제 밖의 타인이고, 링크가 안 열리면 그 사람은 다시 안 온다.** 그리고 열람자/작성자 3:1이 유일한 성장 루프다.

**에러 예산**: 월 0.5%(편집). 소진 시 **기능 개발을 멈추고 안정화**에 쓴다. 파일럿 4주 동안은 예산을 **절반(0.25%)**으로 조인다 — 파일럿 참가자의 첫인상은 한 번뿐이다.

### 7.3 Degradation ladder — 예산 초과 시 무엇을 포기하는가

**핵심 원칙: 항상 이 순서로 버린다. 절대 순서를 바꾸지 않는다.**

> **장식 → 정밀도 → 자동화 → 실시간성 → 시각화 → (여기서 멈춘다) 글쓰기와 저장은 절대 안 버린다.**

#### 클라이언트 (프레임/응답 예산 초과)

| 단계 | 버리는 것 | 사용자가 느끼는 것 |
|---|---|---|
| **1** | 모션·전이 애니메이션 (`prefers-reduced-motion` 경로 재사용) | 거의 없음 |
| **2** | 미니맵, 도트 그리드, 비네트, 완성도 링 | 거의 없음 |
| **3** | **semantic zoom을 최저 단계로 고정** (제목만) | 정보 밀도 감소 |
| **4** | **자동 그룹 접기 강제** (40노드 초과 구간) | 접힌 걸 펴야 함 |
| **5** | **ELK 중단 → 마지막 좋은 좌표 유지.** 구조 변경도 반영 안 함 | 그림이 잠시 안 맞음 |
| **6** | **캔버스 언마운트 → 텍스트 목록 정식 UI** | "그림 그리기가 잘 안 되네요. 대신 순서대로 보여드릴게요" |
| **7** | — | **글쓰기·저장은 여기서도 100% 동작한다** |

**5~6단계가 이미 STATES §9에 명세돼 있다.** degradation이 사후 대책이 아니라 **설계된 기능**이다. 그리고 6단계의 UI는 **접근성용으로 이미 만들어 둔 것**이다 — 하나 만들어 셋을 얻는다(접근성 + ELK 폴백 + 저사양 degradation).

#### 서버 (부하/지연 예산 초과)

| 단계 | 버리는 것 |
|---|---|
| 1 | 계측 이벤트 샘플링 (100% → 20%). **단 프라이버시 관련 이벤트는 100% 유지** |
| 2 | OG 이미지 생성 (정적 기본 이미지로 대체) |
| 3 | 집계 뷰 갱신 주기 완화 (실시간 → 시간당) |
| 4 | 내보내기(PDF/PNG) 큐잉 + "준비되면 알려드릴게요" |
| 5 | **`applyOps` 배치 창 확대** (800ms → 3s). 저장이 느려지되 안 끊긴다 |
| 6 | 읽기 전용 모드 — 공유 페이지만 서빙 |

**절대 안 버리는 것**: 편집 중인 내용의 로컬 보존(IndexedDB), 저장 큐, 공유 페이지 열람, k-anon 차단 로직.

> **마지막 항목이 중요하다.** 부하가 걸린다고 k-anon 검사를 건너뛰는 코드 경로를 **만들지 않는다.** 그런 경로가 존재하는 순간 TRUST.md의 절대 원칙이 조건부가 된다.

### 7.4 부하 예상치

**전제: 조직 300명, 동시 편집 30명.**

| | 추정 | 근거 |
|---|---|---|
| 총 문서 | 300명 × 40% × 1.5개 ≈ **180개** | PRD: "잘해야 전사 40%가 최소 1개 문서" |
| 살아있는 문서 | 180 × 20% ≈ **36개** | 동 |
| 항목 수 | 180 × 15단계 ≈ **2,700행** | 시드 기준 |
| **동시 편집 30명** | op 배치 = 800ms마다 1회, 배치당 ~5 op → **~37 req/s** | |
| **`applyOps` 쓰기** | 37 req/s × (items UPSERT + operations INSERT) ≈ **150 write/s** | |
| 열람 (공유 페이지) | 작성자의 3배 → 피크 **~100 req/s** | 열람자/작성자 3:1 |
| ELK 계산 | **전부 클라이언트 워커.** 서버 부하 0 | |
| 파싱 | **전부 클라이언트.** 서버 부하 0 | |

**결론: 이 부하는 작다. 아주 작다.**

- 2,700행짜리 테이블. **인덱스가 있으나 없으나 상관없는 규모다**
- 150 write/s는 단일 Postgres 인스턴스(2vCPU)가 여유롭게 처리
- **스케일이 문제가 되는 지점은 없다.** ELK와 파서를 클라이언트에 둔 결정이 서버 부하를 사실상 제거했다

**따라서 성능 작업의 90%를 클라이언트에 쓴다.** 서버 최적화·캐싱·읽기 복제본은 **하지 않는다.** 300명 조직에서 그건 순수한 시간 낭비이고, 오히려 §6.2-7의 캐시 오염 위험만 늘린다.

**단 하나 주의할 서버 지점**: **집계 뷰**. 5인 차단 + 2차 억제 + 라운딩이 걸린 쿼리는 조인이 깊어질 수 있다. 여기만 실행 계획을 본다.

## 8. 관측성

### 8.1 근본 제약

> **문서 본문을 로그에 남길 수 없다.** 그리고 이건 "조심하자"가 아니라 **아키텍처 제약**이다.
>
> - D-070: **서버는 문서 본문을 스캔하지 않는다**
> - D-071: **지원용 임시 열람 기능을 만들지 않는다**
> - SECURITY §567: **Sentry 등 에러 트래킹 SaaS를 쓰지 않는다** — *"스택 트레이스의 지역 변수, 요청 바디, breadcrumb에 본문이 딸려 나가는 사고가 이 업계에서 가장 흔하다"*
> - MEASUREMENT §49: 금지 속성 하드 차단 (본문·제목·이름·이메일·**밴드 값 자체**·코멘트·파일명·전체 URL·원본 IP·full UA)

**"고객 데이터를 보고 디버깅한다"는 선택지가 이 제품에는 없다.** 다른 회사에서 당연한 도구가 여기선 전부 금지다.

### 8.2 그럼 디버깅은 어떻게 하는가 — 5가지 대체 수단

이게 이 절의 핵심이다.

#### ① 구조를 로그한다, 내용은 안 한다

본문 없이도 **놀랄 만큼 많이 알 수 있다.**

```
❌ { docTitle: "월마감 정산", itemTitle: "엑셀에 정리" }
✅ { doc_pid: "a3f…", item_count: 14, depth_max: 2, branch_count: 2,
     hold_count: 1, kinds: {task:11, branch:2, hold:1},
     topology_hash: "9c2…", has_explicit_edges: true, cycle_count: 0 }
```

**`topologyHash`와 `contentHash`가 여기서 예상 못 한 값을 한다.** 두 문서가 같은 버그를 내는지, 재현 시도가 같은 그래프를 만들었는지를 **본문 없이 동일성 판정**할 수 있다.

#### ② op 로그로 재현한다 — 가장 강력한 수단

`operations` 어펜드 로그에는 `{docId, seq, actorId, op:{type, payload}, ts}`가 있다.

**`op.type`과 순서만 있으면 payload 없이도 재현 시퀀스가 나온다.**
```
set_title × 12 → insert_item(parent=x) → set_kind(branch) → insert_item × 3
→ set_attr(mode) → [여기서 크래시]
```
→ **로컬에서 같은 op 타입 시퀀스를 더미 텍스트로 재생**한다. 버그의 90%는 내용이 아니라 **구조 변경 순서**에서 나온다.

**구현 요구**: 에러 리포트에 **최근 50개 op의 `type`만**(payload 제외) 첨부. 이건 본문이 아니다.

#### ③ 클라이언트에서 재현 케이스를 익명화해 만든다 — 사용자 동의 기반

에러 발생 시 사용자에게:
> *"이 문제를 고치는 데 도움이 될 정보를 보내주시겠어요? **글 내용은 보내지 않고**, 단계 수와 구조만 보냅니다. [무엇을 보내는지 보기]"*

**[무엇을 보내는지 보기]를 누르면 보낼 JSON 원문을 그대로 보여준다.** TRUST.md의 *"만들 수 있는데 안 만들었다는 증명"* 원칙을 관측성에도 적용한다.

동의 시 **`items`의 title을 전부 `"단계 3"` 같은 서수로 치환한 그래프 구조**를 전송. 이건 사실상 골든 픽스처가 된다.

#### ④ 결정성을 관측성으로 쓴다

`derive()`가 **순수하고 결정적**이므로(`Math.random`/`Date.now` 금지, 입력 순서 무관), **구조만 있으면 서버에서 완벽히 동일한 그래프를 재현**할 수 있다. 이건 대부분의 제품에 없는 사치다. 순수 패키지 결정(D-033)의 부수 이득이다.

#### ④-b 관측성의 유효기간이 12개월이라는 것을 설계에 반영한다

`actor_pid = HMAC-SHA256(user_id, org_salt)`이고 **`org_salt`는 12개월마다 회전, 구 salt는 즉시 파기**된다.
→ **같은 사람의 13개월 전 행동과 지금 행동을 연결하는 것이 구조적으로 불가능하다.** 이건 버그가 아니라 설계다(*"개인을 1년 넘게 추적하는 것이 구조적으로 불가능"*).

**실무 함의 2가지**
- 코호트 분석·리텐션 곡선은 **12개월을 넘길 수 없다.** 넘기려는 쿼리를 짜는 순간 잘못된 길에 들어선 것이다
- **회전 시점에 롤업을 미리 만들어 둬야 한다.** 회전 후에는 소급 계산이 불가능하다 → **회전 런북에 "롤업 선행 생성"을 강제 단계로** 넣는다

#### ⑤ 사용자에게 직접 묻는다

파일럿 4주 동안은 **리서처가 옆에 있다.** *"방금 뭐 하셨어요?"*가 어떤 로그보다 빠르다. **파일럿 기간에는 이걸 1차 수단으로 계획에 넣는다** — 관측성 도구를 과잉 구축하지 않는 이유이기도 하다.

### 8.4 에러 추적에 본문이 새지 않게 하는 방법 — 5중 방어

**하나로는 부족하다. 이 업계에서 가장 흔한 사고다.**

| 층 | 방어 |
|---|---|
| **1. 벤더** | **SaaS를 안 쓴다.** 자체 호스팅(서울). *"국외이전 항목을 하나 늘리지 않는 것이 실사 대응 비용을 크게 줄인다"* |
| **2. 전송 전** | 요청 바디 **미전송**(옵트인이 아니라 코드에서 제거). `beforeSend` 스크러빙 — 한글 3자 이상 연속 문자열, UUID, 이메일 패턴을 `[redacted]` |
| **3. 타입** | 에러에 붙일 수 있는 컨텍스트를 **`ErrorContext` 타입으로만** 제한. 자유 `Record<string, unknown>` 금지 → **본문을 넣을 자리가 타입에 없다** |
| **4. 수신 후** | **서버측 재검** — 스크러빙을 통과한 페이로드를 서버가 한 번 더 검사. 위반 시 이벤트 드롭 + 알림 |
| **5. CI** | 금지 속성 drop 테스트. 일부러 `item_title`을 넣은 이벤트가 **드롭되는지** 검증 |

**3번이 가장 강하다.** 스크러빙은 정규식이라 언젠가 뚫리지만, **타입에 자리가 없으면 컴파일이 안 된다.** graph-core가 순수성을 타입으로 강제한 것과 같은 발상이다.

```ts
// 이것만 허용. 자유 필드 없음.
type ErrorContext = {
  route: string;
  op_types?: OpType[];          // payload 없음
  item_count?: number;
  topology_hash?: string;
  browser_key?: string;         // enum
  // ★ string 자유 필드는 여기에 추가할 수 없다 (리뷰 규칙 + 타입 테스트)
};
```

**추가**: `console.error(item)` 같은 실수를 막기 위해, 프로덕션 빌드에서 `items`/`blocks` 타입 값이 로깅 함수에 들어가면 **타입 에러**가 나도록 로거 시그니처를 브랜딩한다.

### 8.5 알림 라우팅과 온콜

**전제: 팀이 1~2인이다. 알림을 많이 만들면 전부 무시된다.** 그래서 **P0/P1만 만들고 P2는 대시보드로만** 본다.

| 등급 | 조건 | 라우팅 | 응답 |
|---|---|---|---|
| **P0** | `contributor_n < 5` 셀 **1건**(매 배포 + 매일) · `admin_reader`의 base 테이블 접근 시도 **1건** · 이벤트 스키마 금지 속성 검출 **1건** · `private_note` 소유자 세션 밖 복호화 **1건** · 프로덕션 로그 샘플 PII 검출 · **`ime_composition_lost` 세션 비율 > 0.5%**(브라우저 회귀) · **D14 재편집률 4주 이동평균 < 10%**(로드맵 재검토 트리거) | **전화 + 즉시 킬스위치 자동 실행** | 즉시 |
| **P1** | **`jump_score` p90 > 0.15**(배포 직후 자동 비교) · **`elk_ms` p95 > 800ms** · `parse_ms` p95 > 300ms · 저장 실패율 > 1% · `editor_error_shown` > 2% · TTFD 중앙값 > 12분 · 첫 저장률 < 40% 또는 WoW −10%p · 세션당 드래그 시도 중앙값 ≥ 2 · 공유율 < 20% 2주 연속 · 열람자/작성자 < 1.5:1 · 신선도 응답률 < 25% · D14 재편집률 < 15% | 슬랙 DM | 영업일 4시간 |
| **P2** | `edit_distance > 60%` 비율 > 30% · 파싱 실패율 > 25% · 메타 카드 개별 이탈률 > 40% · `nl_branch_suggestion_dismissed/shown` > 50% · 세션당 `undo_performed` 중앙값 > 5 · `canvas_edge_reason_hovered` 급증 | **대시보드만.** 주간 리뷰에서 본다 | 주간 |

> **`elk_ms`의 두 숫자를 혼동하지 말 것**: **예산은 p95 300ms**(§7.1, CI 게이트), **알림 임계는 p95 800ms**(MEASUREMENT). 전자는 "이 선을 넘으면 머지 안 된다", 후자는 "프로덕션에서 이 선을 넘으면 사람을 부른다". 둘은 다른 장치다.

**P2에 있는 것들이 흥미롭다.** 전부 **제품 품질 신호이지 장애가 아니다.**
- `canvas_edge_reason_hovered` 급증 = **자동 그래프가 오해를 사고 있다**
- `undo_performed` 급등 = **조작 오작동의 가장 빠른 신호**
- `edit_distance_band > 60%` 비율 > 30% = **붙여넣기 경로가 순비용**

이건 알림이 아니라 **주간 제품 리뷰의 안건**이다. 알림으로 만들면 대응할 수 없어 곧 무시된다.

**온콜**: 1~2인 팀에 로테이션은 무의미하다. **P0만 24/7, 나머지는 영업시간.** 파일럿 4주 동안만 **P1도 09:00~19:00 대응**으로 올린다.

**킬스위치 자동화**: P0 중 k-anon과 크로스테넌트는 **사람을 기다리지 않고 자동으로 해당 기능을 차단**한다. SECURITY가 "관리자 대시보드 자동 차단"을 명시했다. **사람이 자는 동안 노출이 이어지는 것보다 기능이 꺼진 게 낫다.**

## 9. 개발 환경

### 9.1 로컬 셋업 — 목표는 "10분 안에 첫 커밋"

```bash
git clone … && cd workflow-builder
pnpm i                     # Node 24 (.nvmrc), corepack
docker compose up -d       # postgres:16 · posthog · errortrack

```

**설계 원칙 5개**

1. **`docker compose up` 하나로 모든 외부 의존이 뜬다.** 클라우드 계정 없이 개발 가능
2. **인증 우회는 개발 전용 어댑터로.** `getCurrentUser()`가 유일한 진입점이므로 여기 한 곳만 분기.
   `?as=<seed-user-id>` 쿼리 또는 `DEV_USER` 환경변수.
   **★ 프로덕션 빌드에서 이 모듈이 번들에 포함되면 빌드 실패** (환경변수 런타임 분기가 아니라 빌드타임 제거 + CI 검사)
3. **시드는 SEED-CONTENT.md 14개 중 10개 + 접합 지도 20건.** 파일럿 W0의 시드 작업과 **같은 데이터를 쓴다** — 두 벌 만들지 않는다
4. **시드에 반드시 포함할 것**: 5인 미만 부서 1개(k-anon 차단 검증) · **입·퇴사 이벤트**(시계열 차분 공격 퍼즈용) · 한글 NFD 텍스트 1건(macOS 복사 재현) · 200노드 합성 문서 1건(레이아웃 회귀용)
5. **`pnpm test:ime`을 로컬에서 돌 수 있게** — CI에서만 도는 테스트는 아무도 안 고친다

### 9.2 모노레포 구조와 도구

**pnpm workspace + Turborepo.** 근거:
- **pnpm**: graph-core의 `dependencies: {}` 계약을 지키려면 **엄격한 의존성 격리**가 필요하다. npm/yarn의 호이스팅은 `react`가 우연히 해석되게 만들어 **린트로 막은 것을 런타임이 뚫는다.** pnpm의 심링크 구조가 이걸 구조적으로 막는다
- **Turborepo**: 워크스페이스 5개 정도면 nx는 과하다. 원격 캐시 + `--filter`면 충분
- **Node 24 고정** — graph-core가 **네이티브 타입 스트리핑으로 빌드 없이** 돈다(`erasableSyntaxOnly`). 이걸 잃으면 빌드 단계가 하나 늘어난다

- 커밋 메시지: `feat|fix|docs|chore|test: 한국어 요약`. 기존 4개 커밋과 일관되게
- **결정을 바꿀 때는 `docs/DECISIONS.md`에 항목을 추가한다.** 코드만 바꾸고 문서를 안 고치면 6개월 뒤 아무도 이유를 모른다. **"뒤집는 조건"을 반드시 적는다** — 비어 있으면 무엇을 가정하는지 모른다는 뜻이다

### 9.4 PR 리뷰 기준

**1~2인 팀이므로 리뷰는 가볍게, 단 특정 파일은 무겁게.**

| PR 종류 | 리뷰 |
|---|---|
| 일반 기능 | **셀프 머지 허용** (CI 녹색 + 셀프 체크리스트). 2인이면 비동기 리뷰 24시간 |
| **`db/schema.ts` · 마이그레이션 · RLS 정책 · 집계 뷰** | **반드시 타인 리뷰.** 1인이면 **24시간 숙려 후 본인 재검토** + 체크리스트 |

**PR 체크리스트 (템플릿에 박아둔다)**

## 10. 팀 구성과 역할

### 10.1 시나리오별 — 무엇이 달라지는가

| | 1인 | 2인 | 4인 |
|---|---|---|---|
| **M1(파일럿 A 가능 시점)** | **27주** | **14주** | **9주** |
| M0~M4 | 52주 | 27주 | 17주 |
| 병목 | **컨텍스트 스위칭** | **분기 컨테이너 + 캔버스가 직렬** | **조율 비용** |

**4인이 2인의 2배가 아닌 이유**: 이 제품은 **에디터↔캔버스↔파서가 같은 데이터 모델을 공유**한다. 3명이 동시에 어댑터를 건드리면 충돌한다. 4인의 실질 효율은 **2.4인 수준**이다.

### 10.2 2인 — 권장 구성

**분할선을 "프론트/백"이 아니라 "왼쪽/오른쪽"으로 긋는다.**

| | A | B |
|---|---|---|
| 주 영역 | **왼쪽** — 에디터, BlockNote, IME, op 파이프라인, 자동저장, 파서 | **오른쪽** — 캔버스, ELK, 레이아웃 안정성, 접근성 정본, 공유 페이지, 내보내기 |
| 공유 | 스키마·인증·RLS·CI·토큰은 **S1/S2에서 함께** 만들고 이후 공동 소유 | |
| 스파이크 | S1(분기 컨테이너) · S2(IME) · S6(파서) | S3(ELK) · S4(RLS) · S5(SCIM) |

**경계면은 `blockToItem`/`itemToBlock` 어댑터와 `derive()` 출력 하나.** graph-core가 이미 순수하고 결정적이라 **두 사람이 서로를 기다릴 필요가 없다.** 이 아키텍처의 가장 큰 실무 이득이다.

### 10.3 4인이라면

+ **디자인/프론트 1명** — 컴포넌트 16개 + STATES 전 상태 스토리 (COMPONENTS 부록의 5주 작업이 여기로 통째로 빠진다. **이게 4인의 최대 이득이다**)
+ **인프라/보안 1명** — CI 게이트 30종, RLS, k-anon 퍼즈, 자체 호스팅 3종, 온콜

**주의**: 사람을 늘려도 **분기 컨테이너 스파이크는 병렬화되지 않는다.** 그건 여전히 임계 경로다.

### 10.4 ★ 혼자 한다면 — 무엇을 포기하는가

**정직하게: 1인은 27주다. 그건 6개월 반이다. 그 사이 조직의 관심이 유지될 가능성은 낮다.**
따라서 1인 시나리오의 핵심은 "더 빨리 하기"가 아니라 **"더 적게 만들기"**다.

1. **op 기반 변경** — 나중에 바꾸면 모든 mutation 재작성
2. **클라이언트 UUID + tombstone + fractional index + `COLLATE "C"`**

7. **`Boundary.confidence` / `ruleVersion` 기록** (파서를 만든다면) — 소급 불가

## 11. 파일럿 준비 체크리스트 (W0)

### 11.1 먼저 — 파일럿을 두 개로 쪼갠다

§1.3(a)에서 밝힌 대로, **현재 정의된 4주 파일럿은 M4까지 필요하다.** M1 직후에 그대로 돌리면 W3·W4가 자동으로 실패한다.

| | 시점 | 주차 | 게이트 | 판정하는 것 |
|---|---|---|---|---|
| **파일럿 A** (신설) | M1e 직후 | **W1~W2 (2주)** | W1·W2 게이트만 | **입력 절벽과 공유** — M1 가설 그 자체 |
| **파일럿 B** | M4a 직후 | **W3~W4 (2주)** | W3·W4 게이트 | **문서 생존** — 체크리스트·신선도·D14 |

**같은 참가자 그룹을 유지한다.** B 시점에 A의 문서가 살아 있어야 D14 재편집률이 의미를 갖는다.

**이렇게 쪼개면 얻는 것**: M1 직후에 *"입력 절벽이 해결됐는가"*를 **8주 일찍** 안다. PRD 리스크 1이자 실패 판정 1순위다. **그걸 M4까지 기다려서 알 이유가 없다.**

**주의**: A에서 *"지원 없이 두 번째 문서 <25%"*가 나오면 **B로 넘어가지 않는다.** 입력 절벽이 안 풀린 채로 M2·M3·M4를 만드는 건 낭비다.

### 11.3 W0-6이 진짜 게이트다

> *"직원이 불편함을 적었는데 6개월간 아무것도 안 바뀌면, 그 직원은 물론 **그가 속한 부서 전체가 두 번 다시 안 쓴다.**"*
> *"도구보다 '발굴된 것을 처리하는 팀'이 먼저다."*

**W0-1~12 중 11개는 개발팀이 통제할 수 있다. W0-6만 통제할 수 없다.** 그래서:

- **W0-6을 가장 먼저 시작한다.** 킥오프 2주 전이 아니라 **M1 시작 시점에 시작한다.** 14주 걸리는 개발과 병행해서 서명 하나를 못 받으면, 그건 조직이 이 프로젝트를 원하지 않는다는 신호다
- **M1 중간(7주차)에 확약서 진행 상황을 점검한다.** 그때까지 진전이 없으면 **M1의 나머지를 만들기 전에 그 사실을 논의**한다. 다 만들고 나서 "예산이 없다"를 듣는 것이 최악이다

**이건 개발 계획이 아니라 조직 리스크이지만, 개발 일정에 넣어야 실제로 관리된다.**

### 11.4 파일럿 중 개발팀의 역할

| 주 | 개발팀이 하는 것 | **하지 않는 것** |
|---|---|---|
| W1 (1인1문서 워크숍) | 대기·관찰. 심각도 1 이슈 즉시 수정 | **개입 금지.** 손 든 경우만 지원. 개입 요청 횟수·사유를 로그로 남긴다 |
| W2 (자연 사용 주) | 버그 수정만 | **공지·리마인드 금지.** 자연 사용을 측정하는 주다 |
| W3~W4 (파일럿 B) | 체크리스트·신선도 관측 | 새 기능 추가 금지 |

**W1에서 "개입 요청 횟수 ≤1.5회/인"이 게이트다.** 개발자가 도와주면 그 숫자가 좋아지지만 **측정이 오염된다.** 참는 것이 일이다.

## 13. 이 계획의 가장 큰 리스크

정직하게 쓴다. 순서는 **일정을 깨뜨릴 확률 × 파급** 순이다.

### 1위 — 일정 자체가 이미 3배 틀렸다는 사실이 받아들여지지 않는 것

**이게 압도적 1위다.**

PRD는 M0~M4를 **9.5주**로 적었다. 이 문서는 **2인 27주 / 1인 52주**로 추정한다. 두 숫자의 차이는 오차가 아니라 **다른 세계**다.

**위험한 건 추정이 틀린 게 아니라, 조직이 9.5주를 이미 들었다는 것이다.**

- *"2.5주라며?"*가 나오는 순간, 압박은 **범위 축소**가 아니라 **품질 축소**로 간다
- 그러면 제일 먼저 잘리는 게 **CI 게이트 30종**이다. "일단 끄고 나중에 켜자"
- 그런데 이 제품에서 게이트는 **품질 장치가 아니라 신뢰의 근거다.** k-anon 퍼즈를 끄면 파일럿을 할 수 없고(W0 게이트), IME 테스트를 끄면 한글이 사라지고, 금지어 린트를 끄면 "감시 도구" 프레임이 살아난다
- **한 번 감시 도구로 낙인찍히면 정책을 바꿔도 신뢰는 안 돌아온다**(PRD §3.3)

**완화**
- **§1.2의 21줄짜리 표를 그대로 들고 대화한다.** "느낌상 오래 걸린다"가 아니라 **"이 21개 중 무엇을 지울까요"**로 대화를 바꾼다
- **§1.5의 "자르는 것 / 지키는 것" 2열 표를 계약으로 만든다.** 왼쪽은 언제든 협상 가능, 오른쪽은 협상 불가
- **첫 주 금요일 데모에서 숫자를 공개한다.** 6주차에 말하면 은폐로 보이고, 1주차에 말하면 전문성으로 보인다
- **파일럿 A(2주)를 M1 직후에 배치**해, 14주 뒤에 **실제 사용자 반응**이 나오게 만든다. 27주를 통째로 요구하지 않는다

### 2위 — 분기 컨테이너가 BlockNote에서 깔끔하게 안 나오는 것

**M1의 단일 최대 미지수이고, 이 제품의 핵심 UX가 여기 걸려 있다.**

PRD §4.2가 **Tab 들여쓰기를 문법에서 제거**하기로 한 것은 *"30~50%가 즉시 이해 못 하고, 더 나쁜 건 실패 모드가 조용하다"*는 판단 때문이었다. 그 대안이 **컨테이너 블록**이다. 즉 **컨테이너 블록이 안 되면 대안이 없는 게 아니라, 이미 버린 대안(Tab)으로 돌아가야 한다.**

그런데 BlockNote 0.52.x는 **0.x다.** 중첩 커스텀 블록 + 인터랙티브 인풋 + 한글 IME + 안정 ID 보존을 **동시에** 요구하는 사용례는 흔하지 않다.

**완화**
- S1 스파이크를 **첫날 오후에** 시작한다. 이 주에서 가장 먼저 시작하는 스파이크다
- **대안 사다리 ①→②→③을 미리 정해뒀다.** ③(별도 모달)은 UX가 나쁘지만 **일정은 지킨다**
- ④(BlockNote 폐기)는 **선택하지 않는다.** IME를 직접 떠안는 순간 이 프로젝트는 다른 프로젝트가 된다
- BlockNote 타입이 어댑터 밖으로 못 나가게 린트로 막아, **최악의 경우 에디터 교체 비용을 어댑터 크기로 제한**한다

### 3위 — 파일럿이 요구하는 기능과 M1이 어긋난 채로 킥오프하는 것

§1.3(a)에서 발견한 것이다. **MEASUREMENT의 4주 실행안은 M4를 전제한다.** W3(체크리스트·핸드오프)와 W4(신선도 슬랙 프롬프트)는 M1에 없다.

**이걸 모르고 M1 직후에 4주 파일럿을 돌리면**:
- W3·W4가 자동 미달 → 게이트 규칙상 **"그 주를 반복"** → 반복해도 기능이 없으니 또 미달
- W4 D14 재편집률 <10% → **"죽은 문서 생성기 판정"** → *"M4 완료 전 확산 금지"*
- **즉 M4 없이 파일럿을 하면, M4를 만들어야 한다는 결론이 나오는데, 그건 파일럿 없이도 알던 것이다**
- 그 사이 참가자 14명의 첫인상은 소진된다. **첫인상은 한 번뿐이다**

**완화**: §11.1의 파일럿 A/B 분리. 그리고 **파일럿 설계 문서를 킥오프 전에 개발 현실에 맞춰 개정**한다 — 이건 개발팀이 아니라 **PM이 해야 하는 일**이고, 그래서 §11에 담당을 PM으로 명시했다.

### 4위 — 게이트를 먼저 만들지 않아서 나중에 못 만드는 것

CI 게이트 30종은 **코드가 쌓인 뒤에는 넣을 수 없다.** 기존 코드가 전부 위반이기 때문이다. 그러면 반드시 이렇게 된다:

> *"일단 warning으로 두고 나중에 error로 바꾸자"* → 영원히 warning

특히 위험한 것: **금지어 42항**과 **`n-400` Stylelint**. 이 둘은 UI 코드 전반에 퍼지므로, 화면 4개를 만든 뒤에 켜면 위반이 수백 건 나온다.

**완화**: §2의 S1 스프린트에서 게이트를 **기능보다 먼저** 넣는다. 그리고 **일부러 위반하는 PR을 열어 게이트가 실제로 빨간지 확인**한다 — 게이트가 도는지는 위반시켜야만 안다. 이걸 S1의 DoD에 명시했다.

### 5위 — 혼자 하게 되는 것

현재 인원이 명시되지 않았다. **1인이면 27주(축소 시 13.5주)다.** 그 사이:
- 조직의 관심이 유지될 확률이 낮다
- 리뷰어가 없어 스키마·RLS 실수가 안 잡힌다
- 수동 QA(IME 브라우저 매트릭스, 접근성 수동 검증)를 할 사람이 없다

**완화**: §10.4의 축소 목록. 그리고 **1인일수록 CI를 더 많이 만든다** — 게이트가 유일한 리뷰어다. 그리고 **파일럿 A를 13.5주 지점에 배치**해 조직에 중간 산출을 보인다.

### 6위 — 앵커링이 안정화되지 않는 것

DESIGN §6.6의 6개 장치 중 **활성 노드 앵커링**만 실제로 어렵다. 나머지 5개는 구현이 명확하다.

앵커링이 안 되면 *"통제 상실이 아니라 정리되는 느낌"*이라는 UX 가정이 무너지고, **레이아웃 점프는 이런 제품이 실패하는 가장 흔한 이유**다.

**완화**: S3 스파이크가 이걸 명시적으로 겨냥한다. 실패 시 **"배치 고정" 토글 기본 ON + 명시적 [다시 정리] 버튼**으로 후퇴 — 자동 정리를 포기하고 **사용자가 시점을 통제**하게 만든다. UX는 나빠지지만 **어지럽지는 않다.**

### 7위 — 파서가 기대만큼 안 되는 것

*"AI 없이 80% 커버"*는 **검증되지 않은 주장**이다. PARSING.md 스스로 절 분할은 **70~80%가 천장**이라고 쓴다. 그리고 판정 지표가 명확하다 — **`edit_distance_band > 60%` 비율이 30%를 넘으면 붙여넣기 경로는 순이익이 아니라 순비용.**

**완화**: 이건 **일정 리스크가 아니라 제품 리스크**다. 파서는 어차피 만들어지고, 품질이 낮으면 **미분할 편향을 더 세게** 하면 된다(덜 쪼개면 Enter를 치면 되지만, 잘못 쪼개면 지워야 한다). 최악의 경우 §10.4처럼 **파서를 통째로 빼고 질문 연쇄만** 남긴다 — 질문 연쇄는 *"실패 불가능"*하게 설계돼 있다.

### 마지막으로 — 이 계획에서 가장 확신하는 것과 가장 불확실한 것

**가장 확신하는 것**: **기획이 이례적으로 잘 되어 있다.** 16,625줄 안에 임계값, 금지 조건, 대안, "뒤집는 조건"이 전부 적혀 있다. 대부분의 프로젝트는 **무엇을 만들지 모르는 것**이 최대 리스크인데, **여기선 그게 리스크가 아니다.** graph-core가 378건 테스트와 함께 이미 도는 것도 크다. **위험이 "무엇"이 아니라 "얼마나 걸리는가"에 집중돼 있는 것은 좋은 상태다.**

**가장 불확실한 것**: **이 문서의 모든 추정치.**

§1.2의 21줄 표는 **문서를 읽고 항목을 센 결과이지, 이 코드베이스에서 실제로 만들어 본 결과가 아니다.** BlockNote 커스텀 블록이 하루에 될 수도, 8일이 될 수도 있다. 그 차이가 M1 전체를 흔든다.

**그래서 첫 주가 스파이크 주간이다.** 이 문서의 §1.4 표는 **금요일 오후에 갱신되도록 설계되어 있다.**
