# 인수인계 문서 생성기

> 최종 갱신: 2026-08-17 · 상태: v0.1
> 문구는 [WRITING.md](./WRITING.md), 내보내기 디자인은 [DESIGN.md](./DESIGN.md) §8을 따른다.

---

> **왜 이 문서가 존재하는가**
>
> 조직 도입 전문가와 PM이 독립적으로 같은 판정을 냈다 — *"직원이 이걸 쓸 유일한 이기적 동기는 설명 노동 회피 / 인계·휴가 / 증명 셋뿐이고, 그중 인수인계 문서 하나가 나머지 전부보다 채택률에 기여한다."*
> 그런데 [PRD.md](./PRD.md) §6.2에 M1.5로 올려놓고 스펙이 한 줄도 없었다. 그걸 여기서 만든다.
>
> 이 기능의 출력물은 **사용자가 아니라 남이 읽는 유일한 표면**이다. 앱 안의 모든 문구 규칙이 여기에도 그대로 적용되지만, 여기에는 규칙이 하나 더 붙는다 — **작성자를 부끄럽게 만들지 않으면서 받는 사람에게 정직해야 한다.** 이 둘이 충돌하는 지점이 이 설계의 거의 전부다.

## 1. 산출물 종류 정의

### 1.1 전수 열거와 판정

| 산출물 | 독자 | 독자가 이 일을 할 것인가 | 목적 | 분량 | 기본 포맷 | 판정 |
|---|---|---|---|---|---|---|
| **인계 문서** | 후임·부서이동 인수자 (사내, 이 일은 처음) | 한다 (계속) | 혼자 할 수 있게 | A4 3~6쪽 | 링크 · PDF · 복사 | ★ **본체** |
| **자리 비울 때 볼 안내** | 대신 맡는 동료 (조직은 앎) | 한다 (잠깐) | 당장 막지 않게 | A4 1~2쪽 | 링크 · 복사 | ★ **별개 산출물** |
| **한 장 요약** | 팀장(1on1) · 나 자신 | 안 한다 | 대화 재료 | A4 1쪽 | 이미지 · 복사 | ★ **별개 산출물** |
| 신입 교육자료 | 신입 | 한다 (배우면서) | 배우게 | A4 4~8쪽 | 링크 | **인계 문서의 프리셋** |
| 감사·인증 SOP | 감사인·심사원 | 안 한다 | 규정대로 하는지 확인 | 지정 양식 | 지정 양식 | **v1에서 만들지 않음** |
| 체크리스트 | 나 | 한다 | 실행 중 순서 유지 | — | 앱 안 | 이미 있음 (M4) |
| 조직 조립 뷰 | 여러 팀 | — | 접합 확인 | — | 앱 안 | 별개 기능 (M4) |

**결론: 만드는 것은 3개. 프리셋 1개. 안 만드는 것 1개.**

### 1.2 왜 신입 교육자료는 프리셋인가

인계 문서와 **섹션 구성이 완전히 같다.** 다른 것은 두 개뿐이다.

- 설명 깊이 — 이미 [WRITING.md](./WRITING.md) §10에 스위치가 있다(`받는 분이 이 일을 처음 보시나요?`)
- 「첫 2주에 이것만」 블록이 앞에 붙는가

이 정도 차이로 산출물을 늘리면, 사용자는 버튼 4개 앞에서 0.5초를 더 쓰고 그만큼 이탈한다. **인계 문서 버튼 하나에 질문 하나를 붙이는 쪽이 낫다.**

### 1.3 왜 「자리 비울 때 볼 안내」는 프리셋이 아니라 별개인가

섹션이 다르다. 같은 템플릿의 옵션으로 만들면 둘 다 나빠진다.

| | 인계 문서 | 자리 비울 때 |
|---|---|---|
| 뼈대 | **순서** (1→14) | **날짜** (월~금) |
| 없는 섹션 | — | 「순서대로」가 통째로 없다 |
| 있는 섹션 | — | **「이건 안 하셔도 돼요」** — 인계에는 존재할 수 없는 섹션 |
| 태생 | 흐름 1개 | **흐름 여러 개가 기본** — 사람이 자리를 비우면 그 사람 일 전부가 멈춘다 |
| 유효기간 | 없음 | 문서에 있음. 지나면 자동 만료 |

특히 마지막 두 줄이 결정적이다. 「자리 비울 때」는 **태생적으로 묶음 문서**이고, 인계 문서 생성기에 기간 필터를 얹어서 나오는 물건이 아니다.

### 1.4 왜 감사·인증 SOP는 v1에서 만들지 않는가

세 가지 근거. 세 번째가 압도적으로 중요하다.

1. **데이터가 없다.** SOP는 통제점, 증빙 보관 위치·기간, 책임과 권한 범위, 개정 이력, 승인자를 요구한다. 스키마에 하나도 없다. 넣으면 필드가 6개 늘고, PRD §4.5가 경고한 "작성 중 필드 노출 → 입력률 20% 미만"이 재현된다.
2. **틀렸을 때의 비용 등급이 다르다.** 인계 문서가 틀리면 후임이 물어본다. SOP가 틀리면 부적합 판정이 나고 회사가 다친다. 신뢰도 0.5의 자기신고 데이터로 만들 수 있는 문서가 아니다.
3. **제품의 생존 조건이 깨진다.** 이 도구의 유일한 데이터 자산은 "규정이 아니라 **실제로 어떻게 하는가**"다. 감사 대응 문서를 뽑을 수 있게 되는 순간, 적는 행위가 심사 대비가 된다. 사람들은 실제가 아니라 **규정대로** 적기 시작하고, 그 순간 이 제품은 그냥 또 하나의 사규 저장소가 된다. [TRUST.md](./TRUST.md)의 약속("적은 것이 심사에 안 쓰인다")은 관리자 화면만의 문제가 아니라 **내보내기의 문제**다.

**대신 제공하는 것**: 「단계별 표」 CSV 내보내기. 심사원이 실제로 요구하는 건 대개 "누가·무엇을·언제·무엇으로"의 목록이고, 그건 표로 충분하다. 지정 양식에 옮기는 건 사람이 한다. — **이 판단은 뒤집을 수 있다.** 파일럿에서 ISO·내부감사 요청이 3건 이상 나오면 재검토한다.

### 1.5 선택 부담을 없애는 방법

버튼은 3개다.

```
[ 인계 문서 만들기 ]   [ 자리 비울 때 볼 안내 ]   [ 한 장 요약 ]
```

그런데 **대부분의 사용자는 이 화면을 보지 않는다.** 트리거(§8)에서 들어오면 종류가 이미 정해진 채로 미리보기가 열린다. 자리 비운다고 말한 사람에게 "무슨 문서를 만들까요"를 묻지 않는다. 선택 화면은 흐름 상세의 `•••`에서 직접 들어온 사람만 본다.

````markdown
## 순서대로

### 1. 마감 D-3 전사 공지

이수진 님이 슬랙·메일로 해요. 한 번에 15분쯤 걸려요.
지출결의랑 경비를 며칠까지 올려야 하는지 전사에 알리는 공지예요.

### 2. 각 부서 증빙 제출

여기서 멈춰요. 각 부서가 증빙을 올릴 때까지 보통 4일쯤 걸려요.
기다리는 동안 4번 매출 대사를 먼저 시작해도 돼요.
마감일이 지나도 안 올라오면 3번으로 가요.

> 마감을 잠그고 나서 "이거 지난달 건인데요" 하고 증빙이 오는 일이 10번에 4번쯤 있어요. 금액이 크면 12번까지 되돌려야 해요.

### 3. 아직 안 올린 부서에 개별로 연락

이수진 님이 슬랙·그룹웨어로 해요. 한 번에 1시간쯤 걸려요.
그룹웨어에서 부서별로 뭐가 들어왔는지 보고, 안 올린 곳에 슬랙 DM을 보내요.

### 4. 매출 대사

이수진 님이 홈택스·더존 ERP·엑셀로 해요. 한 번에 반나절쯤 걸려요.
세금계산서, ERP에 잡힌 매출, 실제 입금 세 가지를 서로 맞춰봐요.

> 세금계산서 공급가액이나 사업자번호가 틀린 걸 여기서 발견하는 일이 10번에 2번쯤 있어요.
>
> 거래처가 자기 시스템에서 발행하는 곳이 세 곳 있어요. 그건 홈택스 조회로만 확인돼서 항상 여기서 튀어요.

### 5. 매입 대사

이수진 님이 홈택스·엑셀로 해요. 한 번에 반나절쯤 걸려요.
받은 세금계산서, 지출결의, 카드 명세를 맞춰봐요.

### 6. 은행 거래내역 확인

이수진 님이 인터넷뱅킹·엑셀로 해요. 한 번에 1시간쯤 걸려요.
거래내역을 내려받아서 아직 확인 안 된 입출금이 있는지 봐요.

### 7. 차이가 있나요

이수진 님이 엑셀로 봐요. 한 번에 15분쯤 걸려요.
4·5·6번에서 맞춰본 게 서로 맞는지 보고, 여기서 갈려요.

**7-가. 차이가 있으면**
해당 부서에 원인을 물어봐요. 이수진 님이 슬랙으로 해요. 한 번에 1시간쯤 걸려요.
확인이 끝나면 **4번으로 돌아가서** 다시 맞춰봐요.
한 달에 3~6건쯤 있어요. 이렇게 되면 하루쯤 더 걸려요.

**7-나. 맞으면**
````

### 2.3 반드시 다뤄야 할 것들 — 판단과 규칙

#### (a) 받는 사람이 이 일을 처음 본다는 전제

`처음이에요`를 고르면 **네 가지가 추가**된다. 그 외에는 아무것도 바뀌지 않는다 — 문장을 친절하게 다시 쓰지 않는다.

1. **「시작 전에 받아두실 것」 표** — 도구 목록에서 자동 생성. *가장 실용적인 추가 섹션이다. 권한이 없으면 1번부터 못 하는데, 사람이 쓴 인계 문서에 이게 들어 있는 경우는 거의 없다.*
2. **줄임말·시스템 이름 첫 등장 시 괄호 풀이 1회** + 뒤쪽 용어표
3. **단계 제목 아래 "무엇을 하는 일인지" 한 줄** — 각 단계의 예외 각주·도구 조합에서 만들지 않는다. **소유자가 이미 적어둔 설명 필드가 있을 때만** 붙인다. 없으면 안 붙인다. (엔진이 업무를 추측해 설명하면 반드시 틀린다)
4. **「제일 조심할 곳」이 문서 맨 앞으로** — `대충은 아세요`일 때는 「막히면」 다음으로 내려간다

#### (b) 줄임말·사내 시스템 이름 풀이

4단 파이프라인.

| 단계 | 출처 | 예 |
|---|---|---|
| ① 도구 카탈로그 | `tools.description` (신설 컬럼) | 홈택스 → `국세청 사이트. 세금계산서를 여기서 봐요` |
| ② 조직 별칭 사전 | 관리자가 도입 시 1회 입력 | 그룹웨어 → `다우오피스. 사번으로 로그인해요` |
| ③ 업무 용어 후보 탐지 | 2~4자 한자어 명사 중 표준 사전 미등재 + 이 조직 문서에 3회 이상 등장 | `대사`, `수불`, `전표` |
| ④ 소유자 확인 | 내보내기 직전 카드 스택. **최대 3개만** 묻는다 | `'수불'을 처음 보는 분께 한 줄로 설명한다면요?` |

- ③에서 잡힌 것 중 소유자가 답한 것은 **조직 용어 사전에 쌓인다.** 같은 말을 다음 사람에게는 안 묻는다. **이게 도구명 정규화 사전([TOOLS.md](./TOOLS.md))과 나란한 두 번째 데이터 자산이다.**
- 영문 약어는 별도 규칙: 전부 대문자 2~5자 → `ERP(회사 전체가 쓰는 시스템)`
- **인라인 괄호는 첫 등장 1회, 6자 이내.** 그보다 길면 괄호를 쓰지 않고 용어표로만 보낸다. 괄호가 길면 문장이 읽히지 않는다
- **못 푼 말은 본문에서 건드리지 않는다.** 용어표에 `아직 안 풀렸어요`로 넣지 않고 「물어보셔야 해요」로 보낸다

#### (c) 예외 경로를 어떻게 서술하는가

**원칙: 문서는 선형이다.** 다이어그램은 위치를 보여주지만 문서는 "지금 뭘 해야 하나"에 답한다. 트리 구조는 읽는 사람의 위치 감각을 파괴한다.

| 상황 | 처리 |
|---|---|
| 갈래 비중이 있음 (`10번에 8번`) | **흔한 쪽을 본선으로 번호 흐름에 태우고**, 나머지는 그 자리에서 들여쓴 블록 |
| 갈래 비중이 없음 | **두 갈래를 대등하게** 나란히 쓴다. 어느 쪽이 본선인지 추측하지 않는다 |
| 갈래 안이 1단계 | `7-가.` 볼드 소제목 + 문장 |
| 갈래 안이 2~4단계 | `7-가-1`, `7-가-2` 까지 |
| 갈래 안이 5단계 이상, 또는 3단 중첩 | **본문에서 빼서 부록으로.** 본문에는 `이 경우는 뒤에 따로 적었어요 → 부록 가` |
| `mode: and` (동시) | `이 셋을 같이 해요. 하나라도 안 끝나면 다음으로 못 가요.` — AND는 반드시 이 두 번째 문장을 붙인다 |
| `mode: skip` (조건스킵) | `{조건}이면 이 부분은 안 해도 돼요. {N}번으로 바로 가요.` |
| 텍스트 각주 (승격 전 예외) | 해당 단계 아래 **인용문으로 원문 그대로.** 다시 쓰지 않는다 |

**각주와 갈래는 문서에서 다르게 생겼다.** 갈래는 "고르는 것"이라 소제목이 되고, 각주는 "가끔 벌어지는 것"이라 인용문이 된다. 받는 사람이 이 둘을 헷갈리면 안 된다.

#### (d) 대기 단계 표현

`여기서 하루 기다립니다`는 **부족하다.** 대기는 상태인데 독자는 행동을 찾고 있다. 항상 세 가지를 붙인다.

```
여기서 멈춰요. {대상}이 올 때까지 보통 {기간}쯤 걸려요.
[기다리는 동안 {N}번을 먼저 시작해도 돼요.]         ← 병렬 가능 단계가 있을 때만
{타임아웃}이 지나도 {소식}이 없으면 {행동}.          ← timeoutH 있을 때만
```

- **"기다립니다"가 아니라 "여기서 멈춰요"** — 주체가 사람이 아니라 흐름이다. WRITING §6의 `기다리는 시간은 아무도 잘못한 게 아니에요`와 같은 태도
- **판단 문구를 절대 붙이지 않는다.** `4일이나 걸려요`, `여기가 제일 오래 걸려요` 금지
- `waitFor`별 어미:

| waitFor | 문형 |
|---|---|
| `reply` | `{대상}에서 답이 올 때까지` / `답이 없으면 {행동}` |
| `approval` | `{대상}이 볼 때까지` / `다시 하라는 얘기가 나오면 {N}번으로` |
| `time` | `{시각}이 될 때까지` / `놓치면 다음은 {다음 기회}예요` |
| `resource` | `{대상}이 올 때까지` / `오는 걸 어떻게 아는지: {방법}` |

- **avgWaitH가 없으면 본문에 밝힌다** — `여기서 멈춰요. 얼마나 걸리는지는 아직 안 적혀 있어요.` 대기 시간을 모르면 받는 사람이 일정을 못 짠다. **위험 결핍**이다

#### (e) 재작업 루프

`반려되면 12번으로 돌아갑니다` 한 줄로는 부족하다. 네 가지를 채운다.

```
{빈도} 이렇게 되는 일이 있어요.        ← reworkRate. 없으면 이 문장 생략
그러면 {N}번으로 돌아가서 {무엇}을 다시 해요.
{추가 기간}쯤 더 걸려요.               ← 돌아가는 구간의 duration 합. 없으면 생략
```

- **되돌아가는 곳은 두 번 등장한다** — 갈래 안에서 한 번, 「이렇게 안 흘러갈 때」에서 모아서 한 번. 순서대로 읽는 사람과 문제가 생겨서 찾는 사람이 다르다
- 웹은 앵커 링크, PDF는 `4번(3쪽)`으로 쪽수를 붙인다
- 루프가 2개 이상 겹치면(A→B→A) 문장으로 쓰지 않고 **되돌아가는 곳 목록에서만** 다룬다. 문장으로 쓰면 반드시 헷갈린다

#### (f) 담당자가 바뀌는 지점

**문장 안에 섞지 않는다. 줄을 나눠 가로선 블록으로 낸다.**

```
────────────────────────────────────────
여기서부터 {이름} 님({팀})이 해요.
넘길 것: {산출물}                      ← 있을 때
넘길 것이 뭔지는 아직 안 적혀 있어요.   ← 없을 때. 위험 결핍
────────────────────────────────────────
```

- 인계 지점은 **사고가 나는 곳**이고, 인계 문서의 존재 이유 그 자체다. 시각적으로 가장 강해야 한다
- **되돌아오는 지점도 같은 블록으로 표시**한다 (`10번부터 다시 이수진 님 일이에요`). 이게 없으면 받는 사람이 9번 이후를 계속 남의 일로 읽는다
- 타이틀 블록의 `담당이 바뀌는 곳 4번`이 이 블록 개수와 반드시 일치해야 한다 (자동 체크 항목)
- **"인계"라는 단어를 문서 본문에 쓰지 않는다.** 제목에만 쓴다. WRITING §3의 `인계 / 넘기다` 중 본문은 동사형

#### (g) "이 사람에게 연락하세요"

이름·전화번호 나열은 쓸모가 없다. 받는 사람에게 필요한 건 **상황 → 사람**이다.

- 표의 첫 열은 **이름이 아니라 상황.** 상황은 그 사람이 담당한 단계 번호에서 자동 생성 (`9번 재고 수불`)
- 행 순서: ① 전임자 ② 흐름 안 담당자 sortKey 순 ③ 외부
- **전임자 행은 항상 맨 위**, 그리고 **재직 기한**을 붙인다 (`9월 12일까지 계세요`). 이 정보가 문서 전체의 유효기간을 정한다
- **연락처 원문(휴대폰·개인 메일)은 PDF·마크다운에 넣지 않는다.** 사내 채널 핸들만. PDF는 메일 첨부로 굴러다니고, 개인 연락처가 붙은 파일이 회사 밖으로 나가는 경로가 된다. 링크 버전에서는 로그인한 사내 사용자에게만 디렉터리 카드로 노출
- **회사 밖 사람의 연락처는 어떤 포맷에도 넣지 않는다.** 대신 `이수진 님 메일함의 '○○세무회계' 스레드를 넘겨받으세요` — 사내 사람을 경유하게 한다
- 디렉터리에서 **비활성(퇴사) 계정이 잡히면** 그 행은 `이 분은 지금 안 계세요. {팀} 팀에 물어보세요.`
- 부재 시 대체자는 디렉터리에 있을 때만. 없으면 행을 만들지 않는다

#### (h) 짜증 플래그 — 문서에 넣을 것인가

**넣지 않는다.** 근거 셋.

1. **짜증은 일에 대한 사실이 아니라 작성자의 상태다.** 내보내는 순간 문서는 작성자의 감정 기록이 되고, 그 문서는 퇴사자가 팀장에게 넘긴다. 한 번이라도 이런 일이 생기면 그 사람은 다시는 플래그를 안 누른다. PRD §4.5가 말한 대로 **짜증은 시간·빈도보다 신호가 강한 데이터**인데, 내보내기가 그 데이터를 죽인다.
2. **받는 사람에게 도움이 안 된다.** "이건 짜증나는 단계예요"로는 아무것도 못 한다. 도움이 되는 건 결과 서술이다 — `여기서 3일 밀려요`, `10번에 2번은 틀려 있어요`.
3. **TRUST.md·PRD §3.3과 정면충돌한다.** "개인이 적은 짜증 플래그는 어떤 경로로도 실명 도달 불가"가 원칙인데, **내보내기는 실명이 박힌 유통 경로다.** 관리자 화면만 막고 여기를 열면 원칙이 무너진다.

**대신 하는 것** — 짜증 플래그는 **문장의 원료로만** 쓴다. 플래그가 2개 이상 연속된 구간이 있으면 내보내기 직전 소유자에게만 1회:

```
4·5번이 이어서 손이 많이 가는 곳으로 표시돼 있어요.
대신 하실 분이 여기서 헤맬 것 같으면, 한 줄만 적어두실래요?

[ 적어두기 ]      [ 괜찮아요 ]
```

적으면 그건 예외 각주가 되어 문서에 들어간다. **짜증을 문장으로 바꾸는 일은 사람이 한다. 엔진은 하지 않는다.**

#### (i) 비공개 노트 — 절대 안 나가지만, 그중 상당수가 제일 필요한 정보다

이게 이 기능에서 가장 어려운 지점이다. 픽스처의 노트 2(`CFO님은 화요일 오전엔 임원회의라…`)는 **대체자에게 가장 값진 한 줄**인데, 규칙상 절대 나갈 수 없다.

**해법: 자동 포함은 영원히 없다. 명시적 승격만 있다.**

```
적어두신 메모가 세 개 있어요. 이건 남한테 안 보이는 거예요.
이 중에 문서에 같이 넣을 게 있을까요?

☐ 4번  사실 홈택스 자료보다 내가 만든 매출대장 엑셀로 먼저 맞춰요…
☐ 13번 CFO님은 화요일 오전엔 임원회의라 그때 올리면 하루 밀려요
☐ 3번  ○○팀은 매달 늦어요. 팀장님 참조 넣으면 그날 와요

넣으면 받는 분이 봐요. 안 넣어도 문서는 그대로 나와요.
```

- **기본값 전부 꺼짐.** 체크박스 순서는 노트를 적은 순서 그대로 (추천 정렬을 하면 그 자체가 유도가 된다)
- 승격하면 **원본 노트는 그대로 비공개로 남고**, 텍스트가 예외 각주 필드로 **복사**된다. 승격은 되돌릴 수 있어야 하고, 되돌려도 원본은 그대로 있어야 한다
- 승격된 각주는 문서에서 `— {이름} 님이 덧붙인 말이에요`로 표시된다. **사람이 적은 것과 데이터로 만든 것을 문서 안에서 구분**하는 장치
- 이 카드는 **내보내기당 1회**. 거절하면 그 문서에 대해 90일간 다시 안 묻는다
- **엔지니어링 강제**: 렌더 트리에 `privateNote` 필드가 존재하면 예외를 던진다. 경고가 아니라 빌드 실패. 스냅샷 테스트에 "노트 텍스트가 출력에 없다"를 골든 픽스처로 고정

## 3. 자리 비울 때 볼 안내 — 인계와 무엇이 다른가

### 3.1 다섯 개의 차이

| | 인계 문서 | 자리 비울 때 |
|---|---|---|
| 목표 | 이해 | **안 막히기** |
| 뼈대 | 순서 | **날짜** |
| 범위 | 전부 | **그 기간에 실제로 닥치는 것만** |
| 가장 중요한 섹션 | 「순서대로」 | **「이건 안 하셔도 돼요」** |
| 전임/부재자 연락 | 물어보라고 권한다 | **연락해도 되는 조건을 정한다** |
| 유효기간 | 없음 | 문서에 있음. 지나면 자동 만료 |
| 분량 상한 | 없음 | **2쪽.** 넘으면 그건 인계 문서다 |

특히 네 번째와 다섯 번째가 문서를 근본적으로 바꾼다.

**「이건 안 하셔도 돼요」가 왜 제일 중요한가** — 대신 맡는 사람의 실제 불안은 "내가 뭘 해야 하나"가 아니라 **"어디까지가 내 책임인가"**다. 이 경계를 안 그어주면 그 사람은 아무것도 안 하거나 전부 다 하려다 사고를 낸다. 인계 문서에는 이 섹션이 존재할 수 없다 — 인계는 전부가 그 사람 일이 되니까.

**연락 규칙** — 실무의 진짜 문제는 "휴가 중인 사람에게 연락해도 되나"다. 이걸 문서에 안 적으면 (a) 대신 맡은 사람이 눈치 보다 일을 그르치거나 (b) 하루에 여덟 번 카톡이 간다. 그래서 **부재자가 직접 조건을 정하게 한다.** 문구는 조심스러워야 한다 — 이 섹션이 "연락하지 마세요"로 읽히면 안 되고 "이럴 땐 하세요"로 읽혀야 한다.

### 3.2 기간에 따른 차이 — 별개 문서가 아니라 필터 하나

| 기간 | 처리 |
|---|---|
| **3일 이하** | 「꼭 해야 하는 것」만 남기고 나머지는 한 줄씩. **1쪽.** 단계 상세 없음 |
| **4일 ~ 3주** | 네 섹션 전부 + 주기적으로 돌아오는 단계는 접힌 상세. **2쪽** |
| **3주 초과** | **인계 문서로 안내한다.** `한 달 가까이 비우시면, 대신 하실 분이 흐름을 알아야 해요. 인계 문서 쪽이 나아요.` `[인계 문서로 만들기]` `[그래도 짧게 만들기]` — 두 버튼 동일 크기 |

기간이 하는 일은 **문서 종류를 바꾸는 게 아니라 단계를 걸러내는 것**이다.

**필터 규칙**

1. 흐름 주기(월 1회·주 1회·수시)와 기준일로 부재 기간 안 발생 여부를 판정
2. 주기 정보가 없으면 → **전부 「오면 받아만 두시면 되는 것」으로.** 안전한 기본값이다. 그리고 소유자에게 `언제 하는 일인지 표시하면 이 안내가 훨씬 짧아져요` 1회 제안
3. **`hold`의 avgWaitH가 부재 기간에 걸치면 별도 항목으로 뽑는다** — `제가 없는 동안 답이 올 거예요`. 실무에서 사고가 제일 자주 나는 곳이 여기다. 부재 직전에 던져놓은 요청의 답이 부재 중에 오고, 아무도 안 받는다
4. `😤`가 붙은 단계는 「막히면」 섹션의 우선순위를 올린다 (문서에 짜증을 표시하지는 않는다)

### 3.4 이 문서의 생성 규칙 요약

- **소유자에게 묻는 질문은 두 개뿐이다.** `언제부터 언제까지 비우세요?` / `저한테 연락해도 되는 경우가 있어요?` — 두 번째 질문은 건너뛸 수 있고, 건너뛰면 그 섹션이 통째로 빠진다
- 「꼭 해야 하는 것」의 각 항목은 **날짜 → 무엇 → 어디서 → 안 하면 어떻게 되는지** 순서 고정. 마지막 문장은 `timeoutH` 또는 하류 단계에서 유도하고, 없으면 생략
- **「안 하셔도 돼요」가 비면 문서를 만들지 않고 되묻는다** — `이 기간에 미뤄도 되는 일이 하나도 없나요?` 전부 급한 일이면 그건 안내가 아니라 휴가를 못 가는 상태다. 실제로 이 되물음이 「휴가를 왜 못 가는가」의 데이터가 된다
- **분량 강제**: 렌더 후 A4 2쪽을 넘으면 「더 알고 싶으시면」의 링크로 밀어낸다. 잘라내는 순서는 ④ 참조 상세 → ③ 안 하셔도 돼요의 사유 → ② 받아만 두기의 설명. **「꼭 해야 하는 것」은 절대 자르지 않는다**
- 만료: 부재 종료일 +3일에 링크가 닫힌다. 닫힌 뒤 열면 `이 안내는 8월 31일까지였어요. 지금 모습은 여기서 보실 수 있어요.` + 흐름 링크

## 4. 생성 규칙 엔진

### 4.0 두 개의 상위 원칙

**① 사용자가 적은 글자는 절대 다시 쓰지 않는다.**
`title`, `caseLabel`, 예외 각주는 원문 그대로 나간다. 어미도 안 고친다. 금지어 사전은 **엔진이 만든 문장에만** 적용된다. 근거 — 다시 쓰면 (a) 틀리고 (b) 작성자가 "내가 쓴 게 아닌데"라고 느낀다. 후자가 더 치명적이다. 자기 이름이 붙어 나가는 문서에서 자기 말이 사라지면 다음부터 안 쓴다.

**② 엔진은 서술하지 않고 주석을 단다.**
단계 제목은 소제목으로 그대로 두고, 그 아래에 메타데이터만으로 만든 문장을 붙인다. 엔진이 "이 단계는 ~하는 일입니다"를 지어내지 않는다.

```
### 4. 매출 대사                                             ← title 원문
이수진 님이 홈택스·더존 ERP·엑셀로 해요. 한 번에 반나절쯤 걸려요.   ← 생성
세금계산서, ERP에 잡힌 매출, 실제 입금 세 가지를 서로 맞춰봐요.      ← 소유자 설명 필드 (있을 때만)
> 세금계산서 공급가액이…                                     ← 각주 원문
```

### 4.1 슬롯 문법 — `task`

```
META = [WHO] [TOOL] [TIME] [FREQ]

WHO   = "{name} 님이"                        assigneeId 있음
      = ""                                    없음 (주어 생략. 앞 단계 담당자를 승계하지 않는다)
TOOL  = "{t1}·{t2}로"                        도구 1~3개
      = "{t1}·{t2} 등 {n}가지로"              4개 이상
      = ""                                    없음
TIME  = "한 번에 {band}쯤 걸려요"             durationBand 있음
      = ""                                    없음
FREQ  = "이건 지난주에 {n}번 했어요"          freqLast7d ≥ 흐름 평균 × 2
      = ""                                    그 외 (전 단계에 빈도를 쓰면 소음이 된다)
```

**결합표** — 25자 규칙(WRITING §1)을 지키기 위해 두 문장으로 나눈다.

| WHO | TOOL | TIME | 출력 |
|---|---|---|---|
| ○ | ○ | ○ | `이수진 님이 홈택스·엑셀로 해요. 한 번에 반나절쯤 걸려요.` |
| ○ | ○ | ✕ | `이수진 님이 홈택스·엑셀로 해요.` |
| ○ | ✕ | ○ | `이수진 님이 해요. 한 번에 반나절쯤 걸려요.` |
| ○ | ✕ | ✕ | `이수진 님이 해요.` |
| ✕ | ○ | ○ | `홈택스·엑셀을 써요. 한 번에 반나절쯤 걸려요.` |
| ✕ | ○ | ✕ | `홈택스·엑셀을 써요.` |
| ✕ | ✕ | ○ | `한 번에 반나절쯤 걸려요.` |
| ✕ | ✕ | ✕ | **문장 없음.** 제목만 남는다 |

`durationBand` 표기: `1m`→`1분`, `5m`→`5분`, `15m`→`15분`, `1h`→`1시간`, `halfday`→`반나절`, `1d+`→`하루 넘게`

### 4.2 슬롯 문법 — `hold`

```
여기서 멈춰요. {WAIT_OBJ}{WAIT_VERB} 보통 {avgWaitH→자연어}쯤 걸려요.
[기다리는 동안 {N}번을 먼저 시작해도 돼요.]
{timeoutH→자연어}이 지나도 {NO_REPLY}면 {ESCALATION}.
```

| waitFor | WAIT_OBJ + WAIT_VERB | NO_REPLY |
|---|---|---|
| `reply` | `{대상}에서 답이 올 때까지` | `소식이 없으면` |
| `approval` | `{대상}이 볼 때까지` | `아직 안 봤으면` |
| `time` | `{시각}이 될 때까지` | — (대신 `놓치면 다음은 {다음 기회}예요`) |
| `resource` | `{대상}이 올 때까지` | `안 왔으면` |

- `avgWaitH` 자연어화: `≤2` → `금방`, `≤8` → `{n}시간`, `≤24` → `하루`, `>24` → `{n}일` (주 단위로 바꾸지 않는다 — 업무일 감각을 해친다)
- **병렬 가능 판정**: 이 `hold` 이후 단계 중 이 노드에 의존하지 않는 것이 있으면 두 번째 줄을 넣는다. 그래프에서 파생하므로 사용자가 안 적어도 나온다. **엔진이 만드는 것 중 가장 실용적인 문장이다**
- `avgWaitH` 없음 → `여기서 멈춰요. 얼마나 걸리는지는 아직 안 적혀 있어요.` (위험 결핍)
- `approval` + 반려 행선지 없음 → `다시 하라는 얘기가 나오면 어디부터 다시 하는지는 아직 안 적혀 있어요. {소유자}께 물어보세요.` (위험 결핍)

### 4.3 슬롯 문법 — `branch`

```
{META}                                             ← task와 동일
{BRANCH_LEAD}

**{번호}-{가/나/다}. {caseLabel}{이면/면}**
  {하위 단계들, 또는 "N번으로 가요."}
```

| mode | BRANCH_LEAD |
|---|---|
| `xor` | `여기서 갈려요.` (앞에 소유자 설명이 있으면 `…보고, 여기서 갈려요.`로 이어붙임) |
| `and` | `이 {n}가지를 같이 해요. 하나라도 안 끝나면 다음으로 못 가요.` |
| `skip` | `{caseLabel}이면 이 부분은 안 해도 돼요.` |

- `caseLabel` 없음 → `**7-가.**` 만 남기고 `여기서 뭘 보고 갈리는지는 아직 안 적혀 있어요.` (위험 결핍 — 판단 기준이 없으면 실행이 불가능하다)
- 갈래 끝에 자식이 없고 합류하면 → `{N}번으로 가요.`
- 갈래 끝이 종료면 → `여기서 끝이에요.`
- `returnToItemId` 있으면 → `**{N}번으로 돌아가서** {그 단계 제목}을 다시 해요.`

### 4.4 접속 표현 선택 규칙

**기본값은 "쓰지 않는다".** 번호가 이미 순서를 말한다. 아래 다섯 경우에만 붙인다.

| 조건 | 표현 | 위치 |
|---|---|---|
| 앞이 `hold` | `답이 오면,` / `확인이 끝나면,` (waitFor별) | 다음 단계 첫 문장 앞 |
| 갈래 여러 개가 합류한 직후 | `어느 쪽이든 여기서 다시 만나요.` | 단계 제목 아래 첫 줄 |
| 담당자 변경 | (접속어 없음 — **인계 블록**이 대신한다) | 단계 앞 |
| `returnToItemId`의 대상 단계 | `여기로 되돌아오는 일이 있어요. {N}번에서요.` | 단계 제목 아래 |
| `mode: skip` 이후 | `건너뛰었으면 여기부터 이어져요.` | 스킵 대상 다음 |

**"그다음", "이때", "만약"은 쓰지 않는다.**

- `그다음` — 번호가 이미 말한다. 14번 반복되면 소음이다
- `이때` — 지시 대상이 모호하다. 앞 문장인지 앞 단계인지 알 수 없다
- `만약` — 갈래 소제목이 이미 조건을 보여준다. 화면 편집기에서는 `만약 [ ]라면`이 필요했지만(WRITING §6), 그건 **쓰는 사람에게 구조를 가르치기 위한 껍데기**였다. 읽는 사람에게는 필요 없다

### 4.5 같은 표현의 반복을 어떻게 피하는가

**결론: 문체를 다양화하지 않는다. 데이터의 다양성이 문장의 다양성을 만들게 한다.**

이건 회피가 아니라 판단이다. 자동 생성에서 어미를 로테이션하면(`~해요` / `~합니다` / `~하죠`) 세 번째 문장에서 어색해지고, 어색함은 "기계가 쓴 티"로 정확히 읽힌다. 사람이 지루해하는 것은 **반복 자체가 아니라 정보 없는 반복**이다.

**실제로 작동하는 네 가지 장치**

1. **문장 개수가 데이터에 따라 달라진다.** 메타 3개면 2문장, 1개면 1문장, 0개면 0문장. §2.1 픽스처의 실제 분포는 2·3·2·3·2·2·2·2·2·2·3·2·3·2 문장이고, 각주가 붙는 단계는 4~5문장이 된다. 이 리듬은 자연스럽고, 무엇보다 **정직하다** — 문장이 긴 단계가 실제로 정보가 많은 단계다.
2. **문형이 타입마다 다르다.** `task`는 주석형, `hold`는 `여기서 멈춰요`, `branch`는 소제목 분기. 14단계 중 3개가 `hold`, 2개가 `branch`라 **다섯 번은 확실히 다른 모양이 나온다.**
3. **인계 블록·되돌아감 표시가 리듬을 끊는다.** 픽스처에서 4번 등장한다. 가로선이 들어가면 눈이 쉰다.
4. **사용자 원문이 문체의 다양성을 담당한다.** 제목 14개와 각주 3개는 전부 사람이 쓴 말이고, 문서에서 눈에 띄는 부분은 대부분 그쪽이다.

**하지 않는 것**: 어미 로테이션, 동의어 치환(`해요`↔`처리해요`), 문장 순서 셔플, "다양성 점수". 전부 품질을 떨어뜨린다.

**딱 하나 변주하는 곳**: `hold`의 재촉 문장. `waitFor` 4종이 문형이 다르므로 자연히 달라진다. 이건 변주를 만든 게 아니라 데이터가 다른 것이다.

### 4.6 번호 체계

| 대상 | 표기 | 근거 |
|---|---|---|
| 최상위 단계 | `1` ~ `14` | |
| **`hold`도 번호를 받는다** | `2`, `11`, `13` | "몇 번까지 했어요?"에서 대기 구간에 번호가 없으면 위치를 못 가리킨다. 그리고 대기가 흐름의 정식 구성원이라는 제품 철학(WRITING §6)과도 맞는다 |
| 갈래 케이스 | `7-가`, `7-나`, `7-다` | **소수점(`7.1`)을 쓰지 않는다.** 소수점은 목차를 IT 문서처럼 보이게 하고, 무엇보다 **소리 내어 못 부른다.** 인계는 문서만으로 안 끝나고 반드시 대화가 따라온다. "칠 가 그거요"는 말이 되지만 "칠 점 일"은 안 된다 |
| 갈래 안의 단계 | `7-가-1`, `7-가-2` | 3단까지만 |
| 3단 초과 | 본문에서 빼서 `부록 가` | 부를 수 없는 번호는 만들지 않는다 |
| 되돌아가기 | `4번으로` | 웹은 앵커, PDF는 `4번(3쪽)` |
| 묶음 문서 | `3-7` (세 번째 흐름의 7번) | 표지·목차에서만. 본문 안에서는 흐름 안 번호만 쓴다 |

번호는 **문서 생성 시점에 고정되고 흐름이 바뀌어도 이 문서에서는 안 바뀐다.** 종이에 인쇄된 문서와 대화가 어긋나면 안 된다.

## 5. 부족한 데이터 처리

### 5.1 핵심 프레임 — 위험 결핍과 부끄러운 결핍

모든 결핍을 똑같이 다루면 문서가 망가진다. 기준은 하나다.

> **이게 없으면 받는 사람이 실행하다 멈추는가?**

| | 위험 결핍 | 부끄러운 결핍 |
|---|---|---|
| 판정 | 없으면 못 한다 | 없어도 할 수 있다 |
| 예 | 갈래 판단 기준 · 반려 행선지 · 대기 길이 · 인계 시 넘길 것 · 시작 계기 | 소요시간 · 도구 · 빈도 · 예외 · 담당자 |
| **본문에서** | **밝힌다** — `아직 안 적혀 있어요. {누구}께 물어보세요.` | **조용히 생략한다** — 문장 자체가 안 나온다 |
| 뒤 섹션 | 「물어보셔야 해요」에도 들어감 | 「물어보셔야 해요」에만 들어감 |

이 구분이 §5 전체의 답이다. 부끄러운 결핍을 본문에 흩뿌리면 문서가 구멍투성이로 보이고 작성자가 다음부터 안 만든다. 위험 결핍을 숨기면 받는 사람이 3번 단계에서 멈추고 문서를 덮는다.

### 5.2 필드별 처리표

| 없는 것 | 본문 | 표 | 요약 숫자 |
|---|---|---|---|
| `assigneeId` | 주어 생략. **앞 단계 담당자를 승계하지 않는다** (승계는 틀리면 인계 지점을 지우는 것이라 가장 위험한 추측이다) | 빈 칸 | `함께 하는 사람` 계산에서 제외 |
| `durationBand` | 시간 문장 생략 | `안 적혀 있어요` | `적힌 것만 합쳐서 약 N일` — **"적힌 것만"을 절대 빼지 않는다** |
| 도구 | 도구 문장 생략 | 빈 칸 | `쓰는 것 N가지`에서 제외 |
| `freqLast7d` | 원래 대부분 안 씀 | 빈 칸 | — |
| `avgWaitH` (hold) | **`얼마나 걸리는지는 아직 안 적혀 있어요.`** | `기다림 · 안 적혀 있어요` | `기다리는 시간` 합계에 `적힌 것만` 단서 |
| `timeoutH` (hold) | 세 번째 줄 생략 | 빈 칸 | — |
| 반려 행선지 (`approval`) | **밝힌다 + 물어볼 목록** | `안 적혀 있어요` | — |
| `caseLabel` (branch) | **`여기서 뭘 보고 갈리는지는 아직 안 적혀 있어요.`** | `안 적혀 있어요` | — |
| 갈래 비중 | 두 갈래를 대등하게 서술. 본문에 결핍 표시 안 함 | — | 물어볼 목록에만 |
| 인계 시 넘길 것 | **인계 블록 안에서 밝힌다** | — | 물어볼 목록에도 |
| 예외 각주 0개 | 섹션 대체 문구 + PDF 필기 여백 | — | — |
| 흐름 주기 | 「이 일은 이렇게 시작해서」에서 밝힘 | — | 「자리 비울 때」 필터가 무력화됨 |
| 용어 풀이 | 인라인 괄호 없음 | 용어표에서 행 제외 | 물어볼 목록에 |

### 5.3 "아직 안 적힌 곳" 표시 — 넣을 것인가

**넣는다. 단 세 가지 조건 하에.**

이 판단이 §5에서 제일 중요하다. 받는 사람에게는 결핍 정보가 문서의 절반쯤 되는 가치를 갖는다 — 인수인계에서 제일 어려운 건 **뭘 물어봐야 하는지 아는 것**이다. 그런데 작성자에게 그건 자기 성적표다.

**조건 ① 본문에 흩뿌리지 않고 뒤에 한 곳으로 모은다.** (위험 결핍만 예외)
읽는 흐름이 끊기지 않고, 작성자가 문서를 스크롤할 때 자기 빈칸을 14번 마주치지 않는다.

**조건 ② 결핍 목록이 아니라 질문 목록으로 뒤집는다.**

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| `안 채워진 항목: 6개` | `이건 물어보셔야 해요` |
| `13번 · 반려 행선지 없음` | `13번 — 다시 하라고 하면 어디부터 다시 하나요` |
| (담당 없음) | `누구에게: 이수진` |

같은 데이터인데 **주어가 "빠진 것"에서 "받는 사람이 할 일"로 바뀐다.** 그리고 뒤에 한 줄을 붙인다 — `여쭤보고 나서 이 흐름에 적어두시면, 다음 분은 안 물어봐도 돼요.` 결핍이 문서의 흠이 아니라 **다음 사람을 위한 작업 지시**가 된다. 이건 수사가 아니라 실제로 그렇다.

**조건 ③ 부끄러움은 내보내기 전에 해소할 기회를 준다.**
미리보기에서 **소유자에게만** 같은 목록이 배지로 보인다. `지금 채우면 문서에서 빠져요` + 인라인 입력. 문서가 나간 뒤에는 그 배지가 사라진다.

### 5.4 "3개만 더 채우면 훨씬 좋아져요"를 제안할 것인가

**한다. 단 한 번, 그리고 거절이 같은 크기여야 한다.**

임계치 — **단계의 60% 이상에 담당자·시간·도구가 전부 비어 있을 때만.** 그 외에는 아무 말 없이 문서를 만든다.

```
지금 만들면 순서만 나와요. 그것만으로도 쓸 수 있어요.
세 가지만 채우면 받는 분이 훨씬 덜 헤매요. 1분쯤 걸려요.

[ 세 가지 채우기 ]      [ 그냥 만들기 ]
       h44 동일 크기, 동일 위계
```

**어떤 3개를 고르는가** — 데이터 완성도 순이 아니라 **문서 가독성 기여도 순**이다.

| 순위 | 필드 | 근거 |
|---|---|---|
| 1 | **담당자가 바뀌는 후보 지점** | 인계 블록이 하나도 없으면 인계 문서가 아니다 |
| 2 | **`hold`의 대기 길이** | 없으면 받는 사람이 일정을 못 짠다 |
| 3 | **갈래의 판단 기준** | 없으면 실행이 불가능하다 |
| 4 | `approval`의 반려 행선지 | |
| 5 | 인계 시 넘길 것 | |

시간·도구·빈도는 이 목록에 없다. 없어도 문서가 성립한다.

**거절하면 그 흐름에 대해 다시 안 묻는다.** 두 번 묻는 순간 이건 독촉이 된다.

### 5.5 문서를 아예 만들지 않는 선

만들지 않는 게 나은 경우가 있다. §10.6에서 다룬다.

## 6. 포맷별 설계

### 6.0 우선순위

| | 포맷 | 근거 |
|---|---|---|
| **1** | **공유 링크** `?view=handover` | 항상 최신이고, 유통 비용이 0이고, **읽은 사람의 피드백을 회수할 수 있는 유일한 포맷**이다 |
| **2** | **복사 (서식 유지)** | 노션·위키·한글·워드·메일 본문에 그대로 붙는다. **이게 실질적인 DOCX·HWP 지원이다** |
| **3** | **PDF** | 인쇄·첨부·외부 제출. 인계 실무에서 여전히 요구된다 |
| **4** | **PNG (세로 긴 이미지)** | 카톡으로 도는 경로. 낮은 우선순위가 아니라 **네 번째지만 실제 유통량은 2위일 수 있다** |
| — | DOCX / HWP 파일 | **v1 미지원.** §6.4 |

### 6.1 공유 링크 `/s/[id]?view=handover`

기존 `/s/[id]`([DESIGN.md](./DESIGN.md) §8, [SCREENS.md](./SCREENS.md) §6)와 **같은 라우트, 다른 뷰**다. 다섯 가지가 다르다.

1. **다이어그램이 위에 오지 않는다.** 인계 문서를 여는 사람은 읽으러 왔지 보러 오지 않았다. 560px 프레임이 먼저 나오면 본문까지 한 번 더 스크롤해야 한다. → 상단에 접힌 링크 하나: `그림으로 한 번에 보기 ▸`. 펼치면 그 자리에서 560px 프레임이 열린다
2. **좌측 고정 목차** (≥1024px, 240px 폭). 14단계 문서는 목차가 없으면 길을 잃는다. 스크롤에 따라 현재 위치 표시. `<1024px`에서는 상단 sticky 한 줄(`4. 매출 대사 ▾`)
3. **뷰 전환 탭을 노출하지 않는다.** 링크를 만든 사람이 "인계용"으로 준 것인데 받는 사람이 다른 뷰로 넘어가면 의도가 흐려진다. 하단 텍스트 링크 하나만
4. **만료 기본값 90일** (일반 공유는 30일). 인수인계는 3개월간 참조된다. 만료 7일 전 작성자에게 DM 1회
5. **하단 1문항 피드백** (§9.2)

그 외는 기존 공유 페이지 규칙 그대로 — 최대폭 960px, `prefers-color-scheme` 대응, 배너형 CTA 금지, 워터마크 우하단 12px.

**추가**: `@media print` 를 제공해서 `Ctrl+P`가 PDF 내보내기와 거의 같은 결과를 내게 한다. 링크를 받은 사람은 PDF 버튼이 없다.

### 6.2 PDF

- **A4 세로**, 여백 상 22mm · 하 18mm · 좌우 20mm (화면 48px 규칙의 인쇄 환산)
- 본문 10.5pt / 1.65, 소제목 12pt/600, 문서 제목 20pt/600. `tabular-nums`
- **보더 1.5px, 그림자 전면 제거** (DESIGN §8 내보내기 규칙 상속). `[data-export="true"]` 컨텍스트 사용

**페이지 나눔 규칙**

| 규칙 | 내용 |
|---|---|
| 단계 블록 | `break-inside: avoid`. 단, 블록이 반 페이지를 넘으면 허용하되 **제목 + 첫 문장은 반드시 같은 페이지** (`orphans: 3; widows: 3`) |
| 인계 블록 | **앞에서 강제 개행하지 않는다.** 인계가 페이지 첫 줄에 오면 앞 맥락이 끊긴다. 대신 페이지 하단 1/5 안에서 시작되면 통째로 다음 장으로 민다 |
| 갈래 | `7`과 `7-가`는 같은 페이지에서 시작. `7-가`가 페이지를 넘겨야 하면 `7` 전체를 다음 장으로 |
| 섹션 | 섹션마다 개행하지 않는다. 4쪽짜리가 9쪽이 된다. **개행하는 것은 「단계별로 한눈에」와 부록뿐** |
| 표 | 2쪽을 넘으면 헤더 행 반복 (`thead { display: table-header-group }`) |

**헤더 / 푸터**

```
헤더 (2쪽부터)   좌: 월 마감 정산 · 재무팀 · 이수진        8.5pt n-500
                 우: 3 / 7
푸터 (전 페이지) 좌: 2026년 8월 17일 기준
                 우: ▣ Preflow로 만들었습니다
```

- 표지(1쪽)에는 헤더 없음
- **모든 페이지에 흐름 이름 + 부서 + 전임자 한 줄**을 넣는다. PDF는 페이지 단위로 인쇄되어 흩어진다
- **범례는 매 페이지에 반복하지 않는다.** 문서 PDF에서 범례가 필요한 곳은 마지막 표 하나뿐이다. (DESIGN §8의 "하단 푸터 범례"는 **다이어그램** PNG/PDF 규칙이고, **문서** PDF는 여기서 갈라진다 — 명시적으로 다른 규칙임을 문서화한다)

**마지막 페이지 메타 표 — 본문의 요약이 아니라 보완**

표의 존재 이유는 "다이어그램에서 의도적으로 숨긴 정보의 회수"다. 그러니 **본문에 없는 것**이 들어가야 한다.

| 열 | 폭 | 내용 | 본문에 있나 |
|---|---|---|---|
| `#` | 12mm | `7-가` | ○ |
| 단계 | 58mm | title 원문 (2줄까지) | ○ |
| 누가 | 20mm | 이름. 담당 변경 지점은 **굵게** | ○ |
| 뭘로 | 34mm | **도구 전부** (본문은 3개까지 접음) | △ |
| 한 번에 | 20mm | `반나절` / `기다림 4일` | ○ |
| 그 밖에 | 26mm | **빈도 · 타임아웃 · 되돌아감 대상 · 결핍 표시** | ✕ |

합 170mm. 6열이 A4 세로의 한계다. 7열(빈도 독립 열)은 단계명이 3줄이 되어 표가 무너진다.

표 아래 **표 보는 법** 3줄 — `기다림은 사람이 손을 대는 게 아니라 흐름이 멈춰 있는 구간이에요` / `굵게 된 이름은 담당이 바뀌는 곳이에요` / `안 적혀 있어요는 아직 안 쓴 곳이에요`.

### 6.3 마크다운

**§2.1의 전문이 곧 마크다운 출력이다.** 세 가지만 추가로 규정한다.

**① 다이어그램은 mermaid를 기본으로 하지 않는다.**

| | 판정 |
|---|---|
| mermaid | **기본 꺼짐.** 노션은 되지만 컨플루언스·그룹웨어 게시판·메일 본문은 대부분 못 그린다. 실패하면 코드가 그대로 노출되어 문서가 망가진다. 그리고 우리 그래프의 갈래 비중·대기 길이·인계 마커가 mermaid로 옮기면 전부 죽는다 |
| **텍스트 아웃라인** | **기본값.** 문서 본문 자체가 이미 아웃라인이다. 별도 블록을 만들지 않는다 |
| **이미지 링크 한 줄** | 문서 맨 위에 `![월 마감 정산](https://…/s/{id}/diagram.png)` — 노션·컨플루언스는 이미지 URL을 자동 임베드한다. 엔드포인트는 만료 없이 최신을 렌더 |
| mermaid | `고급` 체크박스로 제공. IT팀·개발팀 사용자 대비. 기본 꺼짐 |

**② ASCII 안전 문자만 쓴다.** 마크다운은 어디에 붙을지 모른다.

```
사용   1. 2. 3.   **볼드**   > 인용   | 표 |   --- 가로선
금지   ◇ ⏸ ↩ ▸ 같은 기호 문자, 이모지, 전각 괄호
대체   [기다림] [갈래] 라벨도 쓰지 않는다 — 소제목과 문장으로 이미 구분된다
```

인계 블록의 가로선은 마크다운 출력에서 `---` + 볼드 한 줄 + `---` 로 낸다(§2.1 참조). 웹·PDF에서는 실제 가로선 블록으로 렌더된다.

**③ 클립보드에 두 가지를 같이 넣는다.**

`text/plain` (마크다운) + `text/html` (서식 유지). 붙여넣는 곳이 알아서 고른다.

| 붙여넣는 곳 | 무엇이 들어가나 | 결과 |
|---|---|---|
| 노션 | `text/plain` 마크다운 | 제목·표·인용이 블록으로 변환 |
| 컨플루언스 | `text/html` | 서식 유지 |
| **한글(HWP)** | `text/html` | **표와 굵기가 유지된다** |
| 워드 | `text/html` | 동일 |
| 슬랙 | `text/plain` | 표는 깨지지만 목록은 살아남음 |
| 메일 본문 | `text/html` | 서식 유지 |

**이게 §6.4의 답이다.**

### 6.4 DOCX / HWP — 지원할 것인가

**v1 미지원.** 근거 넷.

1. **받는 사람이 편집할 이유가 거의 없다.** 편집은 원본 흐름에서 해야 하고(그래야 다음 사람에게도 반영된다), 파일을 고치면 원본과 갈라진다. **파일 내보내기는 문서 부패의 주된 경로다** — PRD §4.10이 막으려는 바로 그것
2. **`text/html` 클립보드가 90%를 커버한다.** 한글은 HTML 붙여넣기로 표·굵기·제목을 받는다. "hwp로 주세요"의 실제 요구는 대개 "한글에 붙여서 결재 양식에 넣겠다"이고, 그건 복사로 해결된다
3. **HWP 생성은 유지보수 비용이 비대칭이다.** 표준 API가 없고([TOOLS.md](./TOOLS.md): 연결성 `하`), 버전별 렌더 차이가 크며, 깨진 hwp 하나가 "이 도구 이상하다"로 직결된다
4. 진짜 필요한 건 대개 **인쇄물**이고 그건 PDF다

**뒤집는 조건** — 파일럿에서 "hwp/워드 파일로 주세요"가 3건 이상 나오면 **DOCX를 먼저** 넣는다(한글이 docx를 연다). HWP 직접 생성은 그다음이고, 아마 영원히 안 온다.

**대신 반드시 하는 것**: `text/html` 클립보드가 한글 2018 이상 / 워드 / 노션 / 컨플루언스에서 안 깨지는지를 **릴리즈 체크리스트에 고정**한다. 저비용 고효과다.

### 6.5 PNG (세로 긴 이미지)

- 폭 1080px 고정 (카톡·슬랙에서 잘 보이는 폭), 높이 가변, `pixelRatio 2`
- 문서가 길면 **섹션 경계에서 분할**하고 우하단에 `1 / 3`
- 여백 48px, 그림자 없음, 보더 1.5px — 기존 내보내기 규칙 그대로
- **다이어그램이 아니라 문서를 그린다.** 인계 문서 PNG는 텍스트 이미지다
- 워터마크는 마지막 조각 우하단에만

## 7. 여러 흐름 묶기

### 7.1 배열 순서 — 캘린더 순

후보를 놓고 판단한다.

| 후보 | 기각 근거 |
|---|---|
| 빈도순 | "매일 하는 일"이 앞에 온다. 그런데 월 1회짜리 마감이 사흘 뒤면 그게 1순위다 |
| 중요도순 | 중요도 데이터가 없다. 만들면 그건 작성자의 자기 평가고, 이 제품에서 평가는 금지다 |
| 부서별 | 한 사람의 인계에서 부서는 대개 하나다 |
| **캘린더순 ★** | 인계받은 사람의 첫 질문은 "내가 이번 주에 뭘 해야 하나"다 |

**4군 분류가 곧 목차다.**

| 군 | 이름 | 판정 | 정렬 |
|---|---|---|---|
| 1 | **곧 닥치는 것** | 30일 안에 주기가 돌아옴 | 발생 예정일 순 |
| 2 | **요청이 오면 하는 것** | 주기 없음 + `freqLast7d ≥ 1` | 빈도 내림차순 |
| 3 | **한참 뒤에 오는 것** | 분기·연 단위 | 발생 시기 순 |
| 4 | **안 하셔도 되는 것** | 보관함 · 이미 다른 사람에게 넘어감 | 상관없음 |

- 4군을 넣는 이유는 §3.1과 같다 — **경계를 그어주는 것이 목록을 주는 것만큼 중요하다.** 그리고 퇴사자가 "이건 이제 안 해요"를 남길 자리가 없으면 후임이 죽은 일을 계속한다
- 주기 정보가 없는 흐름은 전부 2군. 그리고 소유자에게 `언제 하는 일인지 표시하면 순서가 훨씬 정확해져요` 1회 제안

### 7.2 커버 페이지

```
┌──────────────────────────────────────────────┐
│                                              │
│  재무팀 회계 업무 인계                        │  24pt/600
│  이수진 님이 2026년 9월까지 하시던 일          │  13pt n-500
│                                              │
│  받는 분  조은비                              │  11pt
│  만든 날  2026년 8월 17일                     │
│  흐름 9개 · 단계 106개 · 다 읽으면 40분쯤      │
│                                              │
│  ─────────────────────────────────           │
│                                              │
│  제일 급한 것 세 가지                          │  14pt/600
│                                              │
│  1. 9월 1일 · 월 마감 시작 (3쪽)              │
│  2. 9월 4일 · 대금 지급 (21쪽)                │
│  3. 요청이 계속 옴 · 세금계산서 발행 (14쪽)    │
│                                              │
│  ─────────────────────────────────           │
│                                              │
│  이 책 읽는 법                                 │  14pt/600
│                                              │
│  · 앞에서 여덟 쪽만 읽으셔도 이번 주는 돼요.    │
│  · 나머지는 그 일이 실제로 올 때 펴보세요.      │
│  · 뒤에 「물어볼 것」을 모아뒀어요.             │
│                                              │
│  이수진 님은 9월 12일까지 회사에 계세요.        │  11pt, 박스
│                                              │
└──────────────────────────────────────────────┘
```

판단 두 가지.

- **표지 제목은 일 중심, 부제에 사람 이름.** `이수진 님 인수인계`가 아니라 `재무팀 회계 업무 인계`. 문서는 조직에 남고 그 사람은 없다. 다만 **누구에게 물어볼지는 실무상 필수**라 부제와 하단 박스에 이름이 반드시 있어야 한다
- **「제일 급한 것 세 가지」가 표지에 있다.** 표지에서 목차로 넘어가는 사이에 사람이 문서를 덮는다. 표지에서 바로 할 일이 보여야 한다

### 7.3 「앞 여덟 쪽」 — 묶음 문서의 진짜 설계 문제

15개 흐름 × 평균 4쪽 = 60쪽. **60쪽짜리는 안 읽힌다.** 이게 묶음 문서의 유일한 실질 문제다.

→ **앞 8쪽이 문서 전부라고 가정하고 만든다.**

| 쪽 | 내용 |
|---|---|
| 1 | 커버 |
| 2 | 목차 (4군 분류 + 쪽수 + 흐름 간 연결 표시) |
| 3–4 | **첫 2주 달력** — 날짜별로 뭐가 오는지 |
| 5 | **사람들** — 이 책 전체에 나오는 사람을 한 표로 |
| 6 | **미리 받아둘 것** — 계정·권한을 흐름 9개에서 합쳐서 중복 제거 |
| 7–8 | **물어볼 것 전부** — 흐름별 결핍을 한 곳으로 모음 |
| 9~ | 흐름 본문 (참조 문서) |

그리고 **앞 8쪽만 따로 뽑는 버튼**을 준다: `[ 앞부분만 (8쪽) ]`. 이걸 슬랙으로 보내고 전체는 링크로 준다. 실무에서 실제로 읽히는 것은 이 8쪽이다.

### 7.4 흐름 간 접합점 표시

- **목차에서**: 흐름 이름 옆에 `↔ 3번과 이어져요`
- **본문에서**: 해당 단계 아래 한 줄 — `→ 「세금계산서 끊기」 4번으로 이어져요 (62쪽)`
- **묶음 안에 상류만 있고 하류가 없을 때**: `→ 「법인카드 정산」으로 이어지는데, 그건 다른 분이 하세요.` — 후임이 없는 흐름을 찾아 헤매지 않게 한다
- **목차 뒤에 접합 그림 1장** (흐름 9개를 노드로, 접합을 엣지로). 세로 A4 한 쪽. 노드 9개면 읽힌다. **15개를 넘으면 이 그림을 넣지 않는다** — 읽을 수 없는 그림은 넣지 않는 게 낫다
- 접합 데이터의 출처는 [SEED-CONTENT.md](./SEED-CONTENT.md) B의 접합 지도와 같은 구조(`J-xx`)다

### 7.5 묶음 생성 규칙

- 대상 흐름은 **소유자가 고른다.** 자동 전체 선택 안 함. 기본 체크는 최근 90일 내 편집·확인된 것만
- **흐름당 페이지 번호는 통짜로 다시 매긴다** (1~60). 흐름 안 단계 번호는 그대로 (`4번`). 두 체계를 섞지 않는다 — 목차·접합 표시에서만 쪽수를 쓰고, 본문 안에서는 단계 번호만 쓴다
- 30개를 넘으면 만들지 않는다: `흐름이 서른 개가 넘으면 한 권으로는 안 읽혀요. 팀별로 나눠서 만드시는 게 나아요.`
- 중복 제거 대상: 사람 표, 계정·권한 표, 용어표. 이 셋은 합쳐서 앞으로 뺀다

## 8. 트리거 설계

### 8.0 원칙 셋

1. **홍보하지 않고 사건에 얹는다** (PRD §6.3 롤아웃 2단계와 같은 원리). `문서 만들어 보세요`가 아니라 `이번엔 여기서 뽑으시면 돼요`
2. **한 사람에게 같은 종류의 제안은 2주에 한 번을 넘지 않는다** (WRITING §13). 그리고 **거절 2회면 90일 침묵**
3. **배너를 쓰지 않는다.** 배너는 광고로 읽히고, 광고로 읽히는 순간 이 제품의 톤이 무너진다. 전부 텍스트 링크·인라인 카드·DM

### 9.1 자동 체크 — 생성 시점, 소유자에게만

| 11 | 등장 인물이 디렉터리에 없거나 비활성 | | 경고 |

**점수를 붙이지 않는다.** `완성도 72%`는 평가다(WRITING §2: 진행률·완료율 삭제). 소유자에게 보이는 것은:

```
받는 분이 여기서 멈출 것 같은 데가 두 곳 있어요.

· 9번 — 정민아 님께 뭘 드려야 하는지가 없어요
· 13번 — 다시 하라고 할 때 어디로 가는지가 없어요

[ 지금 채우기 ]      [ 이대로 만들기 ]
```

**최대 3개만.** 그리고 두 버튼은 같은 크기다.

### 9.2 사용자 피드백 — 받는 사람 쪽이 더 중요하다

**① 받는 사람에게 (공유 링크 하단, 1문항)**

```
이 문서로 그 일 하실 수 있겠어요?

[ 네 ]        [ 여기가 막혀요 ]
```

`막혀요`를 누르면 단계 목록에서 하나를 고르게 하고(선택), 한 줄 입력(선택). 결과는 **작성자에게 실명으로** 간다. 받는 사람은 이미 서로 아는 사이라 익명일 이유가 없고, 익명이면 작성자가 후속 대화를 못 한다.

```
조은비 님이 6번에서 막혔대요.
"거래내역을 어디서 받는지 모르겠어요"

한 줄만 더 적어두실래요? 그러면 다음 분은 안 물어봐요.
[ 6번 열기 ]
```

**이게 문서 부패 방지의 진짜 엔진이다.** PRD §4.10은 "재사용이 곧 갱신"이라고 했는데, 인계 문서는 작성자가 다시 안 쓴다 — 그 사람은 이미 그 일을 떠났거나 휴가 중이다. 대신 **읽는 사람이 작성자에게 질문 하나를 만들어주는 것**이 갱신 경로가 된다. 읽는 사람에게 편집 권한을 주는 것보다 이쪽이 낫다(편집권을 주면 원본이 오염되고, 사람들은 남의 문서를 안 고친다).

**② 작성자에게 (내보낸 지 14일 뒤, 1문항)**

```
그때 만든 '월 마감 정산' 문서, 쓸 만했대요?

[ 네 ]   [ 다시 물어보더라고요 ]   [ 안 썼어요 ]
```

- `다시 물어보더라고요` → `뭘 물어봤어요?` 한 줄 입력. **이 답변이 이 기능에서 가장 값진 데이터다** — 문서가 못 담은 것의 직접 목록이고, 그게 곧 다음 버전의 스펙이다
- `안 썼어요` → `왜요?` 3택: `만들고 보니 별로였어요` / `그냥 말로 했어요` / `그 일이 안 생겼어요`. 첫 번째 답이 임계치를 넘으면 **이 기능을 접어야 한다는 신호다**

### 9.3 지표

| 지표 | 목표 | 의미 |
|---|---|---|
| **내보낸 문서의 열람자 수** | ≥ 2명 | 0명이면 만든 것만으로 아무것도 증명 안 된다 (PRD §6.1) |
| **`이 문서로 하실 수 있겠어요` 긍정률** | ≥ 70% | 문서 품질의 직접 측정 |
| **`다시 물어보더라고요` 비율** | ≤ 30% | 제품 약속("같은 걸 다섯 번 설명하지 않아도 된다")의 직접 측정 |
| **내보낸 뒤 7일 내 재편집률** | 20~40% | **5% 미만이면 안 읽혔다는 뜻이거나 문서가 죽었다는 뜻이다.** 열람자 수와 교차해서 구분한다 |
| 인계 문서를 만든 사람의 D30 재방문율 | ≥ 50% | 이 기능이 실제로 채택 동인인지 |
| 제안 → 생성 전환율 (트리거별) | T2 ≥ 40%, T5 ≥ 10% | 트리거 취사선택 근거 |

**북극성과의 연결** — PRD §7의 North Star는 "문서가 타인에게 1회 이상 열람된 직원 비율"이다. **이 기능이 그 지표를 직접 움직이는 유일한 기능이다.** 다른 어떤 것도 열람을 만들지 않는다.

## 10. 반대 의견

### 10.1 자동 생성 문서가 사람이 쓴 것보다 나쁠 위험 — 정직하게

**사람이 쓴 인수인계 문서는 대체로 나쁘다. 그런데 그것들은 "선택적"이다.** 사람은 14단계 중 어디가 진짜 위험한지 안다. 그래서 8단계를 대충 쓰고 한 단계에 세 문단을 쓴다. 그 비대칭이 문서의 가치 거의 전부다.

**자동 생성은 14단계를 균질하게 다룬다.** 이게 이 설계의 가장 큰 구조적 결함이고, 정직하게 말해서 완전히 해결되지 않는다.

**균질성을 깨는 데이터는 네 개뿐이다.**

| 데이터 | 문서에 나타나는 방식 | 커버리지 |
|---|---|---|
| 예외 각주 | 인용문 | 있으면 강력. 대부분 0~3개 |
| `😤` | 문서에는 안 나감. 소유자에게 되묻는 데만 씀 | 간접 |
| `reworkRate` · 되돌아감 | 되돌아가는 곳 표시 | 구조적으로 확실 |
| `avgWaitH` | 긴 대기가 자연히 두드러짐 | 확실 |

여기에 **딱 하나를 더 얹는다. 그리고 이 하나가 나머지를 다 합친 것보다 크다.**

> 내보내기 직전, 소유자에게 질문 하나:
> **`대신 하실 분이 제일 헤맬 것 같은 데가 어디예요?`**
> 답 한 줄이 문서 맨 앞 「제일 조심할 곳」이 된다.

이 질문은 이미 [TOOLS.md](./TOOLS.md)의 흐름 완성 프롬프트에 있다(`만약 누가 대신 이 일을 해야 한다면, 어디서 제일 헤맬 것 같아요?`). 답이 이미 있으면 다시 안 묻고 그대로 쓴다.

**한 문장이 문서를 얼마나 바꾸는가** — §2.1의 그 한 줄(`4번에서 홈택스랑 ERP가 안 맞을 때… 거래처가 자기 시스템에서 발행하는 곳이 세 곳 있어요`)은 14단계 전체의 메타데이터를 합친 것보다 후임에게 유용하다. **자동 생성 문서와 사람 문서의 격차 대부분이 이 한 칸에 있다.**

그래서 이 질문은 건너뛸 수 있지만, **UI에서 다른 어떤 것보다 크게 놓는다.** 이 기능에서 사용자에게 요구하는 유일한 추가 노동이고, 요구할 가치가 있다.

### 10.2 거짓 완결감

**문서가 그럴듯하면 작성자가 "다 됐다"고 믿고, 실제로 필요한 대화를 안 한다.**

이건 실재하는 위험이고 자동 생성이 사람 작성보다 **더 나쁜** 지점이다. 손으로 쓰다 보면 "이건 말로 해야겠다"가 저절로 떠오르는데, 버튼 한 번으로 6쪽이 나오면 그 계기가 사라진다.

**완화 두 가지.**

1. 문서 마지막의 고정 문구 — `이 문서로 다 되진 않아요. 한 번은 같이 해보시는 게 제일 빨라요.` **이 문장은 옵션이 아니다. 항상 나간다.**
2. **전임자 재직 기한을 표지와 푸터에 넣는다** — `이수진 님은 9월 12일까지 회사에 계세요.` 시한이 보이면 사람은 약속을 잡는다.

그래도 부족하다. 정직하게 말하면 이건 제품이 못 푸는 문제다.

### 10.3 책임 전가 도구화 — 이게 제일 위험하다

**인사팀이 이 문서를 퇴사 필수 제출물로 지정하면 제품이 죽는다.**

- 퇴사자는 "인계 문서 냈습니다"의 알리바이로 쓴다
- 요구 문서가 되면 사람들은 최소 노력으로 채운다
- 최소 노력으로 채운 데이터가 관리자 집계 뷰로 흘러가고, 자동화 후보 순위가 쓰레기가 된다
- 그리고 **다음 사람들이 "이건 인사팀이 시키는 것"으로 인식하는 순간** 롤아웃 2단계(계기 확산)의 전제가 무너진다

제품 밖 조건이지만 명시해야 한다. **도입 계약서·인사팀 안내문에 한 줄을 박는다**: `이 문서는 제출물이 아닙니다. 인사팀은 작성 여부를 확인하지 않습니다.` 그리고 §8.2의 인사팀 도구는 **안내 발송만 되고 회신 여부는 인사팀에게 안 보이게** 만든다. 이건 UI가 아니라 API 레벨에서 막는다.

### 10.4 틀렸을 때의 비용이 비대칭

인계 문서가 틀리면 후임이 물어본다 — 대체로 괜찮다. 그런데 **날짜·금액·규정**은 다르다. 잘못된 마감일 하나가 가산세를 만든다.

**규칙: 엔진은 숫자를 새로 만들지 않는다.**

- 날짜·금액·규정·계정번호는 **사용자 원문에만** 등장한다. 생성 문장이 만들지 않는다
- 유일한 예외는 **시간 합계**이고, 그때도 `적힌 것만 합쳐서 약 3일`처럼 **단서를 절대 생략하지 않는다**
- `avgWaitH`를 더해서 `이 일은 8일 걸려요`라고 단정하지 않는다. `처음부터 끝까지 보통 8~10 영업일 걸려요`처럼 범위로 쓰고, 근거는 사용자가 적은 주기 정보다

### 10.5 PDF가 진짜 유통 매체가 아닐 수 있다

설계는 PDF에 공을 들였지만, 실제로는 **카톡으로 캡처 이미지가 돈다.** 그리고 사내 위키에 붙여넣는다. PDF를 여는 사람은 생각보다 적을 수 있다.

→ 그래서 §6.0의 우선순위를 링크 > 복사 > PDF > PNG로 잡았고, **PNG를 4순위에 두되 품질을 낮추지 않았다.** 파일럿 4주차에 포맷별 실제 사용 분포를 보고 순위를 조정한다. PNG가 1위로 나오면 PDF에 들인 공의 절반을 PNG 분할·가독성에 옮긴다.

### 10.6 어느 수준 이하면 안 만드는 게 나은가

**세 가지 중 하나라도 아니면 생성 자체를 막는다.**

| 조건 | 근거 |
|---|---|
| **단계 5개 이상** | 4개 이하는 문서가 아니라 메모다. 6쪽짜리 껍데기를 씌우면 오히려 우스워진다 |
| **단계 제목 평균 8자 이상** | 제목만으로 무슨 일인지 모르면 그건 문서가 아니라 목차다. `접수`, `확인`, `발송` 세 글자짜리 14개로는 아무도 일을 못 한다 |
| **갈래가 있으면 판단 기준이 최소 1개는 채워짐** | 갈래 라벨이 전부 비면 문서가 "여기서 갈리는데 왜인지는 모릅니다"를 반복한다 |

**그 외는 전부 만든다.** 담당자 0%, 시간 0%, 도구 0%여도 만든다 — **순서만 있어도 인계에는 쓸모가 있다.** 이게 임계선의 위치에 대한 판단이고, 낮게 잡은 것이 의도다. 높게 잡으면 데이터가 없는 사람은 영원히 이 기능의 가치를 못 보고, 그러면 데이터를 채울 이유도 영원히 안 생긴다.

**막을 때는 실패 메시지가 아니라 대안이다.**

```
지금은 단계가 세 개라서, 문서보다 그냥 복사해서 보내시는 게 나아요.

[ 복사하기 ]        [ 단계 더 적기 ]
```

### 10.7 이 설계에서 가장 자신 없는 부분

솔직하게 셋을 남긴다.

1. **「이건 물어보셔야 해요」의 심리적 효과를 검증하지 못했다.** 결핍을 질문으로 뒤집는 프레이밍이 작성자에게 실제로 안전하게 읽히는지는 5명에게 보여주면 30분 만에 알 수 있다. **파일럿 전에 반드시 한다.** 여기서 "부끄럽다"는 반응이 나오면 이 섹션은 기본 꺼짐으로 바뀌어야 한다.
2. **비공개 노트 승격 카드가 노트 작성을 위축시킬 수 있다.** "언젠가 이걸 넣을지 물어본다"는 걸 알면 애초에 솔직하게 안 적을 수 있다. → 카드에 `안 넣어도 문서는 그대로 나와요`를 넣었지만 부족할 수 있다. **노트 작성률을 승격 카드 도입 전후로 비교**해야 한다. 떨어지면 카드를 뺀다. **노트가 솔직하게 쌓이는 것이 문서 한 줄보다 중요하다.**
3. **「제일 조심할 곳」 질문의 응답률.** 이 한 문항이 §10.1의 핵심 완화책인데, 건너뛰기 가능하게 만든 이상 응답률이 20%일 수도 있다. 20%면 §10.1의 위험은 사실상 완화되지 않은 것이다. → 파일럿에서 응답률이 40% 미만이면, 이 질문을 **내보내기 직전이 아니라 흐름 완성 직후**(기억이 선명하고 문서 압박이 없을 때)로 옮긴다.

### 11.2 라우트

```
app/
  s/[id]/page.tsx                      ?view=handover | cover | onepager
  api/export/pdf/[id]/route.ts         ?view=... (기존 자리 활용)
  api/export/png/[id]/route.ts
  api/export/md/[id]/route.ts          text/plain + text/html
  api/export/csv/[id]/route.ts         단계별 표 (감사 대응 대체물)
  api/export/book/[ids]/route.ts       묶음
packages/
  doc-gen/                             ← 신설. graph-core 의존, UI 의존 없음
    render/{handover,cover,onepager}.ts
    sentence/{task,hold,branch,link}.ts
```

`doc-gen`은 **순수 함수 패키지**로 만든다. 입력은 `derive(tree) ⊕ overrides` 결과, 출력은 문서 트리. 렌더러(웹/PDF/MD/PNG)는 같은 트리를 각자 그린다. **문장은 한 곳에서만 만들어지고, 포맷마다 다시 쓰지 않는다.**

### 11.3 골든 픽스처 (CI)

`graph-core` 50개와 나란히 `doc-gen` 12개.

| # | 픽스처 | 검증 |
|---|---|---|
| 1 | §2.1 「월 마감 정산」 전문 | 스냅샷 일치 |
| 2 | 메타데이터 0% (제목만 14개) | 문서가 나오고, 문장이 하나도 안 깨짐 |
| 3 | 메타데이터 100% | 결핍 섹션이 생략됨 |
| 4 | 비공개 노트 3개 | **출력에 노트 텍스트가 0회 등장** (하드 어서션) |
| 5 | 3단 중첩 갈래 | 부록으로 빠짐 |
| 6 | 루프 2개 겹침 | 문장 대신 목록으로만 |
| 7 | 담당자 전원 동일 | 인계 블록 0개, 요약도 0번 |
| 8 | 담당자 8명 | 인계 블록 수 = 요약 숫자 |
| 9 | 단계 4개 | **생성 거부 + 대안 제시** |
| 10 | 흐름 15개 묶음 | 앞 8쪽 구조 성립, 접합 그림 생략 |
| 11 | 부재 3일 / 2주 / 5주 | 기간 필터 3종. 5주는 인계 문서로 안내 |
| 12 | 생성 문장 전수 | **금지어 0개 · 느낌표 0개 · 이모지 0개 · 25자 이내** |

12번은 사용자 원문을 제외한 **생성 문장만** 검사한다. 이 구분이 무너지면 사용자 원문을 고치기 시작하고, 그건 §4.0 원칙 ①의 위반이다.

## 부록: 이 문서의 핵심 판단 요약

- **산출물 3개** — 인계 문서 · 자리 비울 때 볼 안내 · 한 장 요약. 신입 교육자료는 인계 문서의 프리셋, 감사 SOP는 v1에서 안 만든다(데이터 부재보다 **"적은 게 심사에 안 쓰인다"는 약속이 깨지는 것**이 결정적 근거).
- **엔진은 서술하지 않고 주석을 단다.** 사용자 원문은 절대 다시 쓰지 않고, 금지어 사전은 생성 문장에만 적용한다. 문체를 다양화하지 않고 데이터의 다양성이 리듬을 만들게 둔다.
- **결핍을 두 종류로 나눈다.** 위험 결핍(없으면 못 함)은 본문에서 밝히고, 부끄러운 결핍은 조용히 생략한 뒤 **「이건 물어보셔야 해요」라는 질문 목록으로 뒤집어** 뒤에 모은다.
- **짜증 플래그는 내보내지 않는다.** TRUST/PRD의 실명 도달 금지 원칙이 내보내기에도 적용되고, 감정 표시는 받는 사람에게 실행 가치가 없다. 대신 소유자에게 되물어 사람이 문장으로 바꾸게 한다.
- **비공개 노트는 자동 포함이 영원히 없고 명시적 승격만 있다.** 렌더 트리에 노트 필드가 있으면 빌드 실패.
- **포맷 우선순위: 링크 > 서식 유지 복사 > PDF > PNG.** DOCX/HWP 파일은 미지원이고, `text/html` 클립보드가 실질적 한글 지원이다. 마크다운의 다이어그램은 mermaid가 아니라 이미지 URL 한 줄.
- **묶음은 캘린더 순 4군 분류**이고, 60쪽짜리 현실을 인정해 **앞 8쪽을 별도로 뽑을 수 있게** 만든다.
- **가장 효율 좋은 트리거는 신선도 확인에 `맞음`을 누른 직후**다. 열람자 기반 트리거는 k-익명성 위반으로 기각.
- **가장 큰 위험은 균질성**이고, 이를 메우는 것은 소유자에게 묻는 단 하나의 질문(`제일 헤맬 것 같은 데가 어디예요?`)이다. 이 질문의 응답률이 40% 미만이면 위험은 완화되지 않은 것으로 본다.
- **단계 5개 미만 · 제목 평균 8자 미만 · 갈래 라벨 전무** 중 하나면 만들지 않고 복사를 권한다. 그 외에는 메타데이터가 0%여도 만든다.
