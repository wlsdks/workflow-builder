## 0. 이 정책의 위협 모델 — 무엇을 막으려 하는가

대부분의 SaaS 보안 정책은 "외부 공격자"를 1순위 위협으로 놓는다. 이 제품은 다르다.

| 순위 | 위협 | 실현 확률 | 피해 |
|---|---|---|---|
| **1** | **정당한 권한을 가진 내부자의 열람** — 고객사 관리자, 우리 제품팀, 지원 담당자 | **높음.** 요구는 반드시 온다 | 조직 전체 채택 0. 복구 불가 |
| **2** | **애플리케이션 레벨 인가 결함** — 잘못된 매칭, 캐시 오염, RLS 누락 | 중간 | 타인 문서 노출. 신뢰 즉사 |
| **3** | **공유 링크 유출** — 카톡 전달, 검색엔진 색인, 이메일 오발송 | 높음 | 조직 밖 유출. 우발적 제3자 개인정보 동반 |
| **4** | **집계를 통한 재식별** — 차분 공격, 소집단 셀 | 중간 | k-익명성 약속 파기 |
| 5 | 인프라 침해 — DB 탈취, 자격증명 유출 | 낮음 | 대규모 유출. 법정 신고 |
| 6 | 우발적 제3자 개인정보 — 고객 실명·주민번호가 본문에 | **매우 높음** | 사고 등급 상승(72시간 신고 트리거) |

**이 순서가 이 문서의 모든 결정을 지배한다.** 그래서 아래에서 "본문 애플리케이션 암호화는 하지 않고, 운영자 접근 경로 자체를 없앤다", "지원용 임시 열람 기능을 만들지 않는다" 같은 선택이 나온다. 위협 5(인프라)를 막는 대책에 자원을 쓰는 대신 위협 1~3을 막는 데 쓴다.

# 1. 데이터 분류 체계

## 1.1 등급 정의

5등급 + 3개 부속 범주. 등급은 **"유출 시 누가 가장 다치는가"**로 결정한다. 회사가 다치는 것보다 개인이 다치는 것을 높게 놓는다.

| 등급 | 이름 | 정의 | 실제 데이터 예시 |
|---|---|---|---|
| **L0** | 공개 | 아무나 봐도 되는 것 | 마케팅 사이트, 시드 예시 문서(합성 데이터), 도구 카탈로그 공용 항목("슬랙", "더존"), 이 정책 문서, 신뢰 헌장 |
| **L1** | 내부 | 조직 내 공유 전제. 개인 귀속 없음 | 조직 설정, 부서 트리(SCIM 유래), 조직별 도구 카탈로그(`tools.name`="사내 그룹웨어"), 요금제·청구 메타, 프로세스 키 사전 |
| **L2** | 개인정보 (직원 신원) | 특정 개인을 식별. 국내법상 개인정보 | `users.name`, `email`, `employee_no`(SCIM), 부서·직급, `assignee_id`가 가리키는 실명, 로그인 IP, 세션 정보, 지원 문의 이메일 |
| **L3** | 업무 콘텐츠 (기밀) | 문서 본문. 소유자 것 | `items.title`("A사 견적 3,200만원 발행"), `documents.title`, `attrs`의 자유 텍스트, 붙여넣기 원문, 코멘트, 내보내기 파일(PDF·Markdown) |
| **L4** | 극비 (소유자 전용) | 유출 시 **개인이 회사로부터 불이익**을 받을 수 있는 것 | 비공개 노트("원래는 결재 받아야 하는데 그냥 처리함"), `pain_flag`(짜증 플래그), `duration_band`(개인 귀속 상태의), 인앱 설문 자유응답, 인터뷰 녹취 |

**부속 범주** — 등급 축과 직교한다.

| 범주 | 정의 | 예시 | 법적 성격 |
|---|---|---|---|
| **P1** | 가명 행동 이벤트 | `actor_pid`, `doc_pid`, `dept_bucket`, `tenure_band`, 이벤트명 | **가명정보 = 개인정보.** 익명정보 아님(§2.1) |
| **P2** | 무기명 집계 | `agg_process` 뷰 산출물(k≥5, 5단위 라운딩, 2차 억제) | 익명처리 결과. 적정성 검토 문서 보유 조건부 |
| **K** | 시크릿 | `org_salt`, DB 자격증명, KMS 키, 공유 링크 토큰, SCIM 시크릿, LLM API 키 | 유출 시 상위 등급 전체가 함께 무너짐 |

## 1.2 등급별 취급 규칙

| 규칙 | L0 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|---|
| 저장 위치 | 어디든 | P0 | P0 | P0 | P0 |
| 리전 | 제한 없음 | 국내 | **국내**(WorkOS 예외 §2.4) | **국내 고정** | **국내 고정** |
| 전송 암호화 | TLS | TLS 1.3 | TLS 1.3 | TLS 1.3 | TLS 1.3 |
| 저장 암호화 | — | KMS(볼륨) | KMS(볼륨) | KMS(볼륨) | **KMS(볼륨) + 애플리케이션 레벨 봉투 암호화** |
| 애플리케이션 로그 기록 | 허용 | 허용 | **ID만**(이메일·이름 금지) | **전면 금지** | **전면 금지** |
| 분석 이벤트(P1) 전송 | 허용 | 허용 | **금지**(pid만) | **금지** | **금지**(값 없는 신호만) |
| 제품팀 열람 | 자유 | 자유 | JIT 승인 | **경로 없음**(break-glass만, §5.4) | **경로 없음. break-glass도 불가** |
| 고객사 관리자 열람 | 자유 | 자유 | 조직 디렉터리 범위 | **불가** | **불가** |
| 집계(P2) 반영 | — | 직접 | 불가 | 파생 수치만 | **파생 태그만, 5인 이상에서만** |
| 조직 밖 반출 | 자유 | 관리자 | 관리자 | **소유자만** | **소유자만, 이전·상속 불가** |
| 보존 | 무기한 | 계약 기간 | 계약 종료+60일 | 소유자 삭제까지 | 소유자 삭제까지 · **소유권 이전 시 자동 파기** |
| 사고 시 기본 등급 | — | SEV3 | SEV2 | **SEV1** | **SEV1 + 개인 직접 통지** |

## 1.3 L4가 별도 등급인 이유

L4는 **"약속의 대가로 얻은 데이터"**다.

"실제로는 이렇게 합니다" 비공개 노트는 소유자만 본다는 약속이 없었으면 애초에 존재하지 않는다. 짜증 플래그도 마찬가지다. 이 데이터는 수집 근거 자체가 약속이므로, 약속이 깨지면 데이터의 존재 근거가 사라진다. 그래서 L4는 다른 등급과 달리 다음이 추가된다.

- **소유권 이전 대상이 아니다.** 퇴사·부서이동·조직개편·계약종료 어느 경우에도 다른 사람에게 넘어가지 않고 파기된다(§9.2).
- **break-glass 예외가 없다.** 데이터 복구를 위해서도 열지 않는다. 복호화 함수가 운영·지원 코드 경로에 링크되지 않는다.
- **AI 전송 대상이 아니다**(§11.2).

## 1.4 등급 판정이 애매한 것들 — 미리 정해둔다

| 데이터 | 판정 | 근거 |
|---|---|---|
| `duration_band`("반나절") | 개인 귀속 상태 = **L4**, 프로세스 집계 상태 = L1 | 개인에 붙으면 업무량 평가 재료가 된다 |
| `tools.name` 자유 입력("김부장 엑셀") | **L3** | 사람 이름이 도구명에 들어오는 사례가 실제로 있다 |
| 문서 제목 | **L3** | "3월 미지급 거래처 정리"만으로도 정보가 샌다 |
| OG 미리보기 이미지 | **L3** | 카톡·슬랙 캐시에 영구 저장된다(§8.5) |
| 열람 로그(누가 내 문서를 봤나) | **L2 + L4 혼합** | 열람자에겐 L2, 소유자에겐 자기 문서 관련 L4 |
| `actor_pid` | **P1(가명정보)** | salt 보유자가 있으면 익명이 아니다 |
| 파기 대장·감사 로그 | **L2** | 누가 무엇을 언제 했는지가 곧 개인 행위 기록 |

# 2. 개인정보 관점 정리 (국내 법령 기준)

## 2.1 이 제품에서 개인정보에 해당하는 것

「개인정보 보호법」 제2조 제1호 기준으로 세 덩어리다.

### (1) 직원 신원 정보 — 명백한 개인정보

WorkOS AuthKit SCIM 디렉터리 싱크로 들어오는 값: 이름, 회사 이메일, 사번, 부서, 직급, 재직 상태, 관리자 관계. 여기에 우리가 생성하는 `user_id`, 로그인 시각, 접속 IP, 세션 정보가 붙는다. **논쟁의 여지 없이 개인정보이며, 처리 근거는 고객사의 인사·업무 관리(계약 이행 및 정당한 이익)에 있다.**

### (2) 문서 본문에 우발적으로 포함된 제3자 정보 — 개인정보이고, 가장 다루기 어렵다

"고객 김OO(010-1234-5678) 주문 조회" 같은 문장. 다음이 전부 성립한다.

- **개인정보다.** 성명+전화번호 조합은 특정 개인을 알아볼 수 있다.
- **우리는 수집한 적이 없다.** 직원이 자유 텍스트에 적어 넣었다. 항목 정의도, 수집 동의도, 보유기간 설계도 없다.
- **주민등록번호가 들어오면 즉시 위법 리스크가 된다.** 법 제24조의2는 법령 근거 없는 주민등록번호 처리를 금지한다. 고객사도 우리도 그 근거가 없다.
- **유출 시 신고 기준이 바뀐다.** 유출 규모가 작아도 고유식별정보·민감정보가 1건이라도 포함되면 72시간 내 신고 대상이다(시행령 제40조).

**정책적 결론**: 이 범주는 **"발생을 전제하고, 최소화하고, 사고 시 등급을 올려서" 관리한다.** "발생하지 않는다"고 쓰지 않는다. 구체적 처리는 §3 전체.

### (3) 행동 로그(P1) — 가명정보이며, 익명정보가 아니다

`actor_pid = HMAC-SHA256(user_id, org_salt)` 앞 16바이트. 이것은 **가명정보다(법 제2조 제1의2호).**

익명정보라고 주장하지 않는 이유는 정직해야 한다. `user_id`의 공간은 조직 규모만큼(수백~수천)으로 작고, `org_salt`에 접근할 수 있는 주체가 존재하는 한 전수 대입으로 재식별이 가능하다. **"복호화가 불가능한 해시"는 원본 공간이 넓을 때만 성립하는 주장이다.**

따라서 P1에는 가명정보 규율을 그대로 적용한다.

- 재식별 금지(법 제28조의5). 재식별 시도 자체를 금지하는 서약을 제품팀 전원에게 받고, 위반 시 징계 사유로 명문화.
- 다른 정보와의 결합 금지. **P1 → P2 파이프라인 부재**가 이 금지의 기술적 구현이다(MEASUREMENT.md §1).
- 안전조치 의무 적용: 접근권한 관리, 접속기록 보관, 암호화.
- **`org_salt` 12개월 회전 + 구 salt 즉시 파기** → 회전 이후 구 pid는 재식별 경로가 사라져 사실상 익명화된다. 즉 P1은 **"최대 12개월간 가명정보, 이후 익명정보"**다. 이 상태 전이를 문서화해 실사에서 설명한다.

### (4) P2 집계 — 익명처리 결과로 취급하되, 그렇게 "주장"만 하지 않는다

k≥5 + 5단위 라운딩 + 2차 억제 + 임의 기간 파라미터 제거 + 동시 필터 2개 제한(MEASUREMENT.md §3). 이 조합의 적정성을 **익명처리 적정성 검토 결과서**로 남기고(연 1회 갱신), CI 퍼즈 테스트 결과를 증적으로 첨부한다. 검토서 없이 "익명이니까 개인정보가 아니다"라고 말하지 않는다.

## 2.2 처리자 vs 수탁자 — 우리는 둘 다이며, 경계를 명확히 긋는다

이 구분을 흐리면 정보주체 권리 요구가 왔을 때 서로 미루게 된다.

| 데이터 | 개인정보처리자 | 우리 지위 | 근거 |
|---|---|---|---|
| 직원 신원(SCIM) | **고객사** | **수탁자** | 고객사가 목적·수단을 결정. 우리는 계약 범위 내 처리만 |
| 문서 본문 및 그 안의 제3자 정보 | **고객사** | **수탁자** | 위와 동일 |
| P1 행동 이벤트 | **고객사** | **수탁자** | 아래 주석 참조 |
| 공유 링크 열람 로그 | **고객사** | **수탁자** | |
| 서비스 계약 담당자(구매·법무 담당자 연락처) | **우리** | **처리자** | 우리 계약 이행을 위한 자체 수집 |
| 결제·세금계산서 정보 | **우리** | **처리자** | |
| 마케팅 사이트 방문자, 문의 폼 | **우리** | **처리자** | |
| 지원 문의자(고객사 직원)의 문의 내용 | **우리** | **처리자**(문의 처리 목적 한정) | 문의는 우리와의 직접 관계 |

**P1에 대한 주석 — 여기가 실사에서 반드시 지적된다.**

행동 이벤트는 "제품 개선"이라는 **우리의 목적**을 위해 수집한다. 목적을 우리가 정하므로 형식논리로는 우리가 처리자에 가깝다. 그러나 그렇게 정리하면 우리가 고객사 직원의 행동 데이터에 대해 독립적 처리 권한을 갖는 모양이 되고, 이는 "감시 아님"이라는 제품 서사와 정면으로 충돌한다.

**채택하는 정리**: P1도 **위탁 처리 범위 안**에 둔다. 즉 "서비스 제공 및 서비스 품질 개선"을 위탁 목적에 명시하고, 처리 항목·보유기간(원시 180일, 롤업 25개월)·금지 속성 목록을 위탁계약 부속서에 **열거**한다. 우리가 마음대로 목적을 넓힐 수 없게 계약으로 묶는 것이 서사와 법률 양쪽에서 옳다.

## 2.3 위탁계약(DPA)에 반드시 들어갈 조항

법 제26조 제1항 및 시행령 제28조 제1항의 **법정 필수 사항**(빠지면 계약 자체가 위법):

1. 위탁업무 수행 목적 외 개인정보 처리 금지

4. 재위탁 제한

**WorkOS 이전 요건**

이전 항목은 직원 이름·회사 이메일·사번·부서·재직상태·인증 이벤트(L2)다. **문서 본문(L3/L4)은 전송되지 않는다** — 이 한 줄이 실사에서 가장 중요하다.

법적 근거는 **법 제28조의8 제1항 제3호(정보주체와의 계약의 체결 및 이행을 위하여 필요한 처리위탁·보관)**를 택한다. 이 경우 별도 동의 대신 **개인정보처리방침 공개 등으로 갈음**할 수 있다. 다만 처리자는 고객사이므로:

- **고객사의 처리방침**에 기재해야 하고, 우리는 그 기재용 완성 문장을 제공한다(§12 문서 #18).
- 기재 항목(법 제28조의8 제2항 및 시행령): ① 이전되는 개인정보 항목 ② 이전되는 국가·시기·방법 ③ 이전받는 자의 명칭 및 연락처(정보관리책임자 포함) ④ 이전받는 자의 이용목적 및 보유·이용 기간 ⑤ 이전 거부 방법·절차 및 거부 효과.
- 보호조치(법 제28조의8 제4항): 이전받는 자와의 계약에 안전조치·고충처리 조항 포함, 암호화 전송, 접근권한 최소화.

**국외이전 제로 플랜 (옵션)**

국외이전 자체가 계약 결격 사유인 고객(공공 연계, 금융 계열사, 일부 제조 대기업 협력사)이 실제로 있다. 이들을 위해 WorkOS를 걷어낸 경로를 제공한다.

- 인증: 이메일 매직링크 + 조직 도메인 제한, 또는 고객사 IdP와의 SAML 직결(우리 서버에서 처리)
- 프로비저닝: SCIM 대신 **CSV 업로드 또는 우리 자체 SCIM 수신 엔드포인트**(서울 리전)
- 대가: 디렉터리 자동 동기화 기능 축소, 온보딩 수작업 증가. 계약서에 기능 차이를 표로 명시

이 옵션이 존재한다는 사실만으로 실사 대화가 "그럼 그 플랜으로 가죠"로 끝난다. **만들어두는 비용보다 못 만들어서 잃는 계약이 크다.**

## 2.5 정보주체 권리 대응

### 원칙 구조

법적으로 권리 행사의 상대방은 **처리자인 고객사**다. 그러나 이 제품에서는 그렇게만 설계하면 안 된다. 직원이 자기 권리를 행사하기 위해 인사팀에 신청서를 내야 한다면, 그 순간 "내 데이터가 회사 손에 있다"는 것이 확인되고 제품의 전제가 무너진다.

**채택하는 구조: 법정 절차를 타기 전에 제품이 먼저 해결한다.**

| 권리 | 제품 내 셀프서비스 | 법정 절차(셀프서비스로 불가한 부분) |
|---|---|---|
| **열람**(제35조) | 내 문서 전체 목록·본문 상시 열람. **내 데이터 전체 내보내기** 버튼(JSON+Markdown, 즉시). 내 문서를 누가 열람했는지(90일). **AI에 보낸 기록**(§11.5) | P1 이벤트 원본 사본 요구 시 → 요청 접수 후 **10일 이내** 제공(pid 기준 추출) |
| **정정**(제36조) | 문서 본문·메타 상시 편집 | SCIM 유래 신원 정보(이름·부서)는 고객사 인사시스템이 원천 → 고객사로 이전 |

### "내가 적은 거 다 지워주세요" — 정확한 답

**재직 중이면: 즉시, 전량, 본인이 직접 지운다. 승인 없다.**

설정 > 내 데이터 > `내가 적은 것 모두 지우기`. 동작은 다음과 같다.

| 대상 | 처리 | 시점 |
|---|---|---|
| 내 문서 전체(L3) | 논리 삭제 → 30일 휴지통 → 물리 삭제 | 즉시 / T+30 |
| 비공개 노트(L4) | **휴지통 없이 즉시 물리 삭제 + 암호키 슬롯 파기** | 즉시 |
| 내가 만든 공유 링크 | 전부 즉시 무효 | 즉시 |
| P1 행동 이벤트 | `doc_pid`·`actor_pid` tombstone 큐 → **24시간 내 물리 삭제** | T+24h |
| P2 집계에 이미 반영된 무기명 수치 | **되돌리지 않는다** | — |
| 접속기록(감사 로그) | **삭제하지 않는다**(법정 보존) | 1년 후 파기 |

**P2를 되돌리지 않는 이유를 미리 고지한다.** 두 가지다. (1) 집계는 개인 식별성이 제거된 상태라 개인정보가 아니다. (2) 더 중요한 실질적 이유 — 한 사람이 빠졌다고 집계를 재계산하면 **전후 차분으로 그 사람의 기여분이 역산된다.** 삭제가 오히려 개인을 드러낸다. 이 사실을 삭제 확인 화면에 그대로 쓴다.

> 지운 뒤에도 **이미 만들어진 부서 단위 숫자는 그대로 남아요.** 되돌리면 빠진 사람이 누구인지가 오히려 드러나거든요. 그 숫자엔 이름도 문서도 들어 있지 않아요.

**퇴사 후에는 다르다.** §9.3에서 별도로 정한다. 이 비대칭은 **입사 온보딩 화면과 이용약관에 미리 고지한다.** 나중에 알리면 배신이고, 지금 알리면 규칙이다.

### 회사가 "이 직원 문서 지우지 마라"고 하면

재직 중 소유자의 삭제권은 **계약으로 무효화되지 않는다.** 고객사가 특정 직원의 삭제를 막아달라고 요구하면 거절한다. 대신 조직에 남는 것(프로세스 집계, 이미 공유된 문서의 수신자 사본)을 설명하고, 필요하면 오프보딩 절차 개선을 제안한다(TRUST.md §5의 응답 스크립트와 동일한 논리).

**예외 하나** — 법령상 보존 의무(감사·소송 홀드)가 걸린 경우. 이때도 문서를 열람 가능 상태로 두는 것이 아니라, **암호화 격리 보관(접근 계정 0)** 후 사유·기간·근거 법령을 소유자에게 통지한다.

## 2.6 파기 절차와 증적

### 파기 삼단계

| 단계 | 시점 | 상태 | 복구 |
|---|---|---|---|
| 논리 삭제 | 즉시 | `deleted_at` 설정, 모든 조회 경로에서 제외, 링크 무효 | 소유자가 30일 내 복구 가능 |
| 물리 삭제 | T+30 일괄 배치 | 행 삭제, S3 오브젝트 삭제, P1 tombstone 반영 완료 | 불가 |
| 백업 소멸 | 최대 T+65 | 스냅샷 보존주기(35일) 경과로 자연 소멸 | 불가 |

**백업에서 개별 레코드를 지우지 않는다.** 스냅샷을 열어 편집하는 행위 자체가 L3 접근이 되기 때문이다. 대신 두 가지로 보완한다.

1. **복원 시 tombstone 재적용 필수** — 백업 복원 절차서에 "복원 직후 tombstone 큐를 재적용하기 전에는 애플리케이션을 기동하지 않는다"를 넣고, 복원 스크립트에 강제 단계로 구현한다. 이게 없으면 **지운 문서가 장애 복구 때 되살아난다** — 신뢰가 죽는 가장 조용한 방식이다.
2. **BYOK 고객은 암호학적 파기**(§4.4) — 조직 전용 키를 파기하면 백업 안의 데이터도 즉시 무의미해진다.

### 파기 증적

파기 대장을 append-only(WORM)로 유지한다. 항목:

```
파기 ID · 대상 범주(L2/L3/L4/P1/첨부) · 대상 식별자 범위(테넌트 ID 또는 pid)
건수 · 파기 방법(물리삭제 | 오브젝트 삭제 | 키 파기) · 요청 근거(소유자 요청 | 보존기간 경과 | 계약 종료)
요청 일시 · 실행 일시 · 실행 주체(배치 잡 ID 또는 담당자) · 승인자
검증 쿼리와 결과(대상 조회 시 0건) · 결과 해시 · 백업 소멸 예정일
```

- 검증은 **자동화된 쿼리 결과를 그대로 첨부**한다. "확인했음" 같은 문장은 증적이 아니다.
- 대장 자체는 3년 보관. 계약 종료 시 파기확인서는 이 대장에서 자동 생성한다.
- 분기 1회, 무작위 표본 20건에 대해 실제 부재를 재검증하고 그 기록도 남긴다.

# 3. 문서 본문의 우발적 민감정보

## 3.1 딜레마를 정면으로

**요구**: 직원이 "고객 김OO 주민번호 880101-1234567로 조회"라고 적으면, 그건 고객사에게 법적 폭탄이다. 발견해서 지워야 한다.

**충돌**: 발견하려면 본문을 읽어야 한다. 그런데 이 제품의 단 하나뿐인 판매 논거는 **"우리도, 당신 회사도 당신 문서를 보지 않습니다"**다.

여기서 흔히 나오는 타협 — "사람이 보는 게 아니라 기계가 보는 거니까 괜찮다" — 은 **틀렸다.** 세 가지 이유로 틀렸다.

1. **스캔은 열람이다.** 서버가 정규식으로 본문을 훑는 코드 경로가 존재하는 순간, "본문을 읽는 서버 코드가 있다"는 사실이 생긴다. 그 코드는 확장된다. 6개월 뒤 "이왕 읽는 김에 프로세스 자동 분류도 하자"가 온다.
2. **탐지 결과 자체가 새로운 최고 등급 데이터다.** "문서 #482에 주민번호 패턴 3건"이라는 메타데이터는 원문보다 위험할 수 있다. 그리고 이 목록이 생기면 **고객사 관리자가 반드시 요구한다.** "위험 문서 목록만 주세요" — 이건 문서 목록을 요구하는 것과 정확히 같다. 원칙 1이 옆문으로 무너진다.
3. **오탐은 사람이 처리해야 한다.** 정규식 오탐률은 0이 아니다. 검토 큐가 생기면 검토자가 생기고, 검토자는 본문을 읽는다.

## 3.2 결론

> **서버는 문서 본문을 스캔하지 않는다. 탐지는 오직 사용자의 브라우저 안에서, 사용자 본인에게만 일어난다.**

이 결정은 협상 대상이 아니며, DPA 제8조(§2.3 #8)로 계약에 못 박아 우리 자신도 나중에 뒤집지 못하게 한다.

## 3.3 클라이언트 사이드 힌트 (P-EDGE)

### 동작 규칙

| 항목 | 규칙 |
|---|---|
| 실행 위치 | 브라우저. 순수 JS/WASM. **네트워크 호출 0** |
| 실행 시점 | ① 입력 중(디바운스 500ms) ② 저장 직전 ③ **공유 링크 발급 직전**(가장 위험한 순간) ④ 소유자가 기존 문서를 열 때(소급, §3.5) |
| 판정 결과 저장 | **어디에도 저장하지 않는다.** 서버 전송 없음, DB 없음, localStorage 없음(세션 메모리만) |
| 차단 여부 | **차단하지 않는다.** 저장도 공유도 그대로 된다 |
| 텔레메트리 | `pii_hint_shown { class }` 단 하나. **`actor_pid` 미부착 스트림**(짜증 플래그와 동일 취급). `doc_pid` 미포함, 원문·길이·위치 미포함 |

마지막 줄이 핵심이다. 우리는 "주민번호 힌트가 이번 주에 전사에서 몇 번 떴는가"는 알 수 있고, **"어느 문서에 있는가"는 원리적으로 알 수 없다.** 제품 개선에 필요한 최소치만 남기고 재식별 경로는 잘라낸다.

### 탐지 패턴

오탐이 신뢰를 깎으므로, **정밀도를 재현율보다 우선한다.**

| 클래스 | 패턴 | 검증 | 비고 |
|---|---|---|---|
| `rrn` 주민등록번호 | `\d{6}[-\s]?[1-4]\d{6}` | **체크섬 검증 통과 시에만** | 검증으로 오탐 대부분 제거 |
| `card` 카드번호 | 13~19자리 숫자 그룹 | **Luhn 통과 시에만** | |
| `account` 계좌번호 | 10자리 이상 숫자 + **동일 줄에 은행명/`계좌`/`입금` 키워드** | 이중 조건 | 단독 숫자만으로는 안 잡는다 |
| `phone` 전화번호 | `01[016789][-\s]?\d{3,4}[-\s]?\d{4}` | — | 대표번호·내선은 제외 |
| `passport` 여권/외국인등록번호 | 여권 `[A-Z]\d{8}` / 외국인등록번호는 rrn 규칙 확장 | 체크섬 | |
| `email` 개인 이메일 | 조직 도메인이 **아닌** 주소 | 도메인 대조 | 사내 이메일은 안 잡는다 |

**의도적으로 탐지하지 않는 것**: 사업자등록번호(개인정보 아님), 사람 이름(한국어 이름 탐지는 오탐 폭발), 금액(거래처 계약금액은 민감하지만 개인정보가 아니고, 잡으면 대부분의 문장에 힌트가 뜬다).

### 힌트 UI 동작

- 해당 줄 왼쪽에 작은 표식. 팝업·모달·토스트 **금지**(작업 흐름을 끊으면 사람들은 그 내용을 아예 안 적게 된다 — 진실 확보가 최우선).
- 클릭하면 두 개의 버튼: `[가리기]` `[그대로 두기]`
- `[가리기]`는 클라이언트에서 치환한다. 치환 사전: 주민번호→`고객 주민번호`, 계좌→`고객 계좌`, 전화→`고객 연락처`, 카드→`카드번호`. **마스킹(`880101-1******`)이 아니라 단어로 치환한다** — 마스킹은 앞자리(생년월일·성별)를 남기는데 그것만으로도 개인정보다.
- `[그대로 두기]`를 누르면 해당 줄에서 다시 묻지 않는다.

## 3.5 이미 저장된 문서 — 소급 처리

**서버 일괄 스캔은 하지 않는다.** 대신 세 가지.

1. **열람 시 검사** — 소유자가 자기 문서를 열면 렌더링 중 클라이언트에서 검사한다. 즉 소급 검사는 "소유자의 브라우저에서, 소유자가 열 때만" 발생한다. 서버는 무엇이 걸렸는지 끝까지 모른다.
2. **분기 1회 훑어보기 유도** — 내 문서 목록 상단에 조용한 줄: `한 번 훑어볼까요. 3개 문서를 아직 안 열어보셨어요.` 강제 아님, 배지·진행률 없음(WRITING.md 게임화 금지).
3. **공유 직전 검사가 실질적 방어선** — 유출은 저장이 아니라 공유에서 난다. 이 지점의 검사만 잘 작동하면 실질 리스크의 대부분이 잡힌다.

## 3.6 고객사가 "우리 문서에 개인정보 있는지 검사해달라"고 하면

이 요구는 온다. 대개 고객사 개인정보보호책임자(CPO)나 감사팀에서, **정당한 법적 동기를 가지고** 온다. 그래서 더 어렵다.

### 답: 거절한다. 세 가지 대체안과 함께.

**거절 스크립트** (TRUST.md §5 형식)

> **요구**: "우리 회사 문서에 주민번호가 들어있는지 저희가 확인해야 합니다. 법적 책임이 저희한테 있어서요."
>
> **답변**: 법적 책임이 고객사에 있다는 말씀이 맞습니다. 그래서 검사 자체를 안 하겠다는 게 아니라, **검사 주체를 바꾸는 방법**을 제안드립니다.
>
> 저희가 전수 검사를 하려면 본문을 읽어야 하는데, 그건 계약서 제8조에서 저희가 하지 않기로 약정한 일입니다. 그리고 그 조항은 고객사가 저희에게 요구하신 게 아니라, **저희가 나중에 유혹에 넘어가지 않으려고 스스로 묶어둔 조항**입니다.
>
> 대신 세 가지를 드립니다. **①** 전사 자가점검 캠페인 — 각 직원 브라우저에서 자기 문서를 검사하고, 조직엔 참여율만 옵니다. **②** 애초에 안 들어가게 하는 예방 설정. **③** 유출 사고 시 저희가 24시간 안에 알려드리고 신고 자료를 만들어 드립니다.
>
> 전수 검사 결과 목록을 드리는 순간, 그 목록은 "누가 무엇을 적었는지"의 목록이 됩니다. 그게 존재한다는 걸 직원들이 알면 다음 달부터 이 도구에는 아무도 진짜 업무를 안 적습니다.

### 대체안 상세

**① 전사 자가점검 캠페인** (제공한다)

- 관리자가 캠페인을 켠다 → 각 직원에게 인앱 안내 → 직원이 자기 문서를 브라우저에서 검사 → 걸린 곳은 **본인만** 본다 → 본인이 가리거나 둔다 → 완료 표시.
- 조직이 받는 것: **`전체 128명 중 94명 확인 완료`** — 참여율뿐. 5인 미만 부서는 부서 단위로 집계되지 않는다.
- 조직이 받지 못하는 것: 문서 목록, 건수, 어떤 클래스가 걸렸는지, 누가 안 했는지의 **명단**(TRUST.md — 미사용자 명단 금지와 동일 논리).
- 미완료자 독촉은 시스템이 개인에게 직접 보낸다. 관리자에게 명단을 넘기지 않는다.

**② 예방 설정** (기본 제공)

- 온보딩 1문장: `실제 고객 이름 대신 "고객"이라고 적어도 충분해요.`
- 시드 콘텐츠·예시 문서 전량 합성 데이터(SEED-CONTENT.md 준수)
- 조직 설정: 공유 링크 생성 시 검사 강제(끄기 불가 옵션), 외부 공유 전면 차단

**③ 사고 대응 약정** (계약)

인지 후 24시간 통지 + 신고서 초안 + 기술 분석 자료 + 신고 대행 지원(§7.2).

### 예외 — 법령상 요구

수사기관 영장·법원 제출명령 등 **법적 강제**가 있는 경우는 별도 절차다.

- 영장의 범위를 법률 검토 후 **최소 범위로만** 이행하고, 범위 밖 요구는 이의를 제기한다.
- 법적으로 금지되지 않는 한 **소유자 본인과 고객사에 통지**한다(통지 금지 명령이 있으면 해제 시 즉시 통지).
- 대응 건수를 **분기 투명성 보고서**에 공개한다(§5.6).

# 4. 암호화 · 키 관리

## 4.1 전송 구간

| 구간 | 조치 |
|---|---|
| 브라우저 ↔ 애플리케이션 | **TLS 1.3만.** TLS 1.2 이하 비활성. HSTS `max-age=63072000; includeSubDomains; preload` |
| 애플리케이션 ↔ Postgres | TLS `sslmode=verify-full` + CA 핀. 평문 접속 불가(파라미터그룹 `rds.force_ssl=1`) |
| 애플리케이션 ↔ PostHog(P1) | VPC 내부 + mTLS |
| 애플리케이션 ↔ WorkOS | TLS 1.3, 인증서 검증, API 키 로테이션 90일 |
| 서버 ↔ S3/KMS | VPC 엔드포인트(인터넷 미경유) |
| 공유 페이지 | 위와 동일 + `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store` |

법정 근거: 「개인정보의 안전성 확보조치 기준」상 **인터넷망을 통해 송·수신하는 개인정보는 전부 암호화** 대상이다. 예외 없이 적용한다.

## 4.2 저장 구간 (at-rest)

| 대상 | 조치 |
|---|---|
| RDS 스토리지·스냅샷 | AWS KMS CMK, AES-256 |
| S3(첨부·내보내기·OG 이미지) | SSE-KMS + 버킷 정책에서 미암호화 PUT 거부 |
| EBS, 임시 볼륨 | KMS |
| CloudWatch 로그 그룹 | KMS |
| 백업(별도 계정) | KMS(교차계정 키) |
| 로컬 개발 환경 | **프로덕션 데이터 복제 금지**(§5.2), 디스크 암호화 + MDM 강제 |

**비밀번호는 우리가 저장하지 않는다.** 인증은 WorkOS AuthKit(SSO/매직링크)에 위임하므로 자격증명 해시 자체가 우리 DB에 없다. 실사 체크리스트의 "비밀번호 일방향 암호화" 항목에는 **"저장하지 않음"**이 가장 강한 답이다.

## 4.3 애플리케이션 레벨 암호화(ALE) — 무엇을 하고 무엇을 안 하는가

### 결정: 문서 본문(L3)은 ALE 하지 않는다. 비공개 노트(L4)만 한다.

**본문을 ALE 하지 않는 이유 — 트레이드오프 분석**

| 관점 | ALE 도입 시 | 판단 |
|---|---|---|
| 제품 기능 | 프로세스 매칭, 불일치 리포트, 자동화 후보 추출, 검색, 붙여넣기 파서 품질 측정, 향후 AI 초안 — **전부 본문 파생에 의존한다.** 암호화하면 이 기능들이 죽거나, 복호화 후 처리하게 되어 암호화가 무의미해진다 | **치명적** |
| 실제 방어 범위 | ALE가 막는 것은 "DB 파일·스냅샷 자체의 유출"(위협 5, 확률 낮음)이다. 우리 위협 1~3(내부자 열람, 인가 결함, 공유 링크)에는 **전혀 무력하다** — 애플리케이션이 키를 갖고 있고, 그 세 경로는 전부 애플리케이션을 통과하기 때문 | **효용 낮음** |
| 정직성 | ALE를 도입하고 "암호화되어 있습니다"라고 말하면, 고객은 종단간 암호화(E2EE)로 오해한다. 실제로는 우리 서버가 복호화 키를 갖고 있다 | **오해 유발** |
| 대안의 강도 | 같은 노력을 "사람용 DB 계정 미발급 + 본문 컬럼 REVOKE + break-glass 2인 승인"(§5)에 쓰면 위협 1을 실제로 막는다 | **대안이 우월** |

**따라서 우리는 이렇게 말한다 — 과장하지 않는다.**

> 문서 본문은 저장 볼륨 단위로 암호화되지만, **종단간 암호화는 아닙니다.** 우리 서버는 기술적으로 본문을 읽을 수 있습니다. 우리가 읽지 않는다는 보장은 암호화가 아니라 **접근 경로를 만들지 않은 것**입니다. 그 경로가 없다는 사실은 §5의 통제와 분기 투명성 보고서로 증명합니다.

이 문단을 보안백서에 그대로 넣는다. **"E2E 암호화"라고 쓰고 싶은 유혹이 영업 과정에서 반드시 오고, 그 한 줄이 나중에 가장 비싼 거짓말이 된다.**

### ALE 대상 (봉투 암호화, AES-256-GCM)

| # | 대상 | 이유 | 키 |
|---|---|---|---|
| 1 | **`attrs.private_note`** (L4 비공개 노트) | 유출 시 개인이 회사로부터 불이익을 받는 유일한 데이터. 집계에 원문이 필요 없음(파생 태그만 사용). 소유자 외 열람 주체가 원천적으로 없음 | org DEK + 문서별 nonce |
| 2 | 통합 자격증명(Slack 토큰, 향후 커넥터) | 시크릿(K) | 서비스 DEK |
| 3 | `org_salt` | 재식별 키 | KMS 직접 암호화, 조직별 |
| 4 | 공유 링크 토큰 | 평문 미저장, **SHA-256 해시만 저장**(§8.1) | — |
| 5 | 반출 파일(계약 종료 시 export) | 조직 밖으로 나가는 순간 | 1회용 키, 고객에 별도 채널 전달 |

**`private_note` 키 설계**

```
KMS CMK (조직별 또는 서비스 공용)
  └─ org DEK (봉투 암호화, DB에 wrapped 상태로 저장)
       └─ AES-256-GCM(plaintext, nonce=doc_id||item_id||rev, aad=org_id||item_id)
```

- 복호화 함수 `decryptPrivateNote()`는 **소유자 세션 컨텍스트를 인자로 강제**하고, 컨텍스트 없이는 컴파일되지 않는다(타입 레벨 brand).
- 이 함수는 **배치·관리자·지원·AI·집계 코드 경로에 임포트되지 않는다.** ESLint `no-restricted-imports`로 경로별 차단하고 CI에서 검증한다.
- 모든 복호화 호출은 감사 로그에 기록된다. 소유자 세션 외의 호출은 **존재할 수 없으므로**, 한 건이라도 나오면 P0 경보다.

**사용자 패스프레이즈 기반 E2E를 채택하지 않은 이유**: SSO 환경에서 사용자에게 별도 비밀번호를 요구하게 되고, 분실 시 복구가 불가능하며(비개발자 대상 제품에서 이건 지원 재앙), 새 기기 로그인마다 키 동기화 문제가 생긴다. 대신 위와 같이 **"복호화 가능한 코드 경로를 물리적으로 좁히는" 방식**을 택한다. 이 선택을 보안백서에 근거와 함께 기재한다.

## 4.4 키 관리

| 키 | 저장 | 회전 | 파기 |
|---|---|---|---|
| CMK(서비스 공용) | AWS KMS | 자동 연 1회 | — |
| **CMK(조직 전용, BYOK 플랜)** | AWS KMS + 고객 정책 | 고객 결정 | **고객이 파기 → 암호학적 파기 성립** |
| org DEK | DB에 wrapped 저장 | 연 1회 + 사고 시 즉시 | 재암호화 후 구 DEK 파기 |
| **`org_salt`** | 조직별 Secrets Manager(KMS 암호화) | **12개월**(MEASUREMENT.md §1) | **회전 즉시 구 salt 파기.** 파기 시각을 대장에 기록 |
| DB 자격증명 | Secrets Manager 자동 회전 | 90일 | |
| 공유 링크 서명키 | Secrets Manager | 180일(중첩 유효기간) | |
| TLS 인증서 | ACM | 자동(90일) | |
| LLM API 키(로드맵) | Secrets Manager | 90일 | |

**조직별 키 분리의 3단계**

| 플랜 | 키 구조 | 의미 |
|---|---|---|
| 기본 | 서비스 공용 CMK + **조직별 DEK** | 논리적 분리. 한 조직 DEK 유출이 다른 조직에 전파되지 않음 |
| 격리 | **조직 전용 CMK** + 전용 DB 인스턴스 | 물리적 분리. 실사에서 요구되는 "테넌트 격리" 답변 |
| BYOK | 고객 계정의 CMK를 우리에게 grant | **고객이 키를 회수하면 우리가 데이터를 읽을 수 없다.** 온프레 요구의 실질적 대체재(§6.5) |

**`org_salt` 회전과 ALE 키의 관계** — 둘은 분리한다. salt는 재식별 방지용(HMAC), DEK는 기밀성용(AES)이다. 같은 키를 쓰면 salt 회전 때마다 전체 재암호화가 필요해져 회전을 미루게 되고, 결국 12개월 회전 약속이 깨진다. **회전 주기가 다른 키는 반드시 분리한다.**

## 4.5 백업과 복구

| 항목 | 값 |
|---|---|
| 자동 스냅샷 | 일 1회 + PITR(트랜잭션 로그) |
| 보존 | 스냅샷 35일, PITR 7일 |
| 저장 위치 | **별도 AWS 계정**(백업 전용), 교차계정 복사, 국내 리전 |
| 암호화 | KMS 교차계정 키 |
| 랜섬웨어 대응 | 백업 계정은 프로덕션 롤에서 삭제 권한 없음. S3 Object Lock(거버넌스 모드) |
| **RTO / RPO** | **4시간 / 15분** |
| 복구 훈련 | **분기 1회**, 실제 복원까지 수행하고 소요시간을 기록. 훈련 보고서는 실사 제출용 자산 |

**복구 절차의 필수 단계** (순서 고정)

1. 격리된 복구 VPC에 복원(프로덕션과 네트워크 분리)
2. **tombstone 재적용** — 복원 시점 이후 삭제된 문서·이벤트를 삭제 큐에서 재적용
3. 무결성 검증(행수·체크섬·테넌트 스코프 샘플링)
4. 애플리케이션 기동
5. **복구 VPC의 복원본은 4시간 내 파기**하고 파기 대장에 기록
6. 소유자 통지 — 복원으로 인해 삭제 요청 처리가 지연된 사용자에게 개별 통지

2번이 없으면 지운 문서가 되살아난다. 절차서에 넣는 데서 끝내지 않고 **복원 스크립트의 강제 단계로 구현**한다.

빠짐없이 세는 것이 이 절의 목적이다. 세지 않은 경로가 사고가 난다.

| 9 | 우리 직원이 공유 링크를 수신 | L3 | 링크는 유효하다. 지원 목적 수신 시 **1회 열람 후 즉시 소유자에게 회수 안내** + 열람 사실이 소유자 로그에 남음 |

## 5.2 로그와 콘텐츠 분리 — 코드로 강제한다

정책 문서로는 반드시 새어나온다. 다음 네 가지를 구현한다.

1. **`items`/`documents` 객체에 `toJSON()` 오버라이드** — 본문 필드는 `"[redacted]"`로 직렬화된다. 실수로 `logger.info({ item })`을 해도 본문이 안 나간다.
2. **로거 미들웨어 레드액션** — 키 이름 기준(`title`, `note`, `text`, `content`, `body`, `paste`) 강제 마스킹.
3. **CI 정적 검사** — 로그 호출 인자에 본문 필드가 들어가는 패턴을 AST로 검출해 빌드 실패.
4. **프로덕션 로그 샘플링 감사** — 주 1회 무작위 1,000줄을 자동 검사해 PII 패턴 검출 시 P0 경보(이 검사는 **우리 로그**를 보는 것이지 고객 문서를 보는 게 아니다 — §3의 원칙과 충돌하지 않는다).

**에러 트래킹 SaaS(Sentry 등)를 쓰지 않는 이유**: 스택 트레이스의 지역 변수, 요청 바디, breadcrumb에 본문이 딸려 나가는 사고가 이 업계에서 가장 흔하다. 그리고 그건 곧 국외이전이다. **자체 호스팅으로 간다.** 국외이전 항목을 하나 늘리지 않는 것이 실사 대응 비용을 크게 줄인다.

## 5.3 최소권한(PoLP)과 승인 절차

| 롤 | 상시 권한 | 상승 가능 범위 | 승인 |
|---|---|---|---|
| `engineer` | 코드 저장소, 스테이징 전체 | 프로덕션 읽기(**본문 컬럼 제외**), 60분 | 1인 승인 |
| `sre` | 인프라 메트릭·알람, 배포 | 프로덕션 DB 구조·통계, 60분 | 1인 승인 |
| `support` | 티켓 시스템, 조직 메타(플랜·좌석) | 사용자 계정 상태(활성/정지) 조회 | 자동 기록 |
| `billing` | 청구 데이터 | — | — |
| **누구도** | **본문(L3) 상시 접근 없음** | break-glass(§5.4) | **2인 승인 + 고객사 동의** |
| **누구도** | **비공개 노트(L4) 접근 불가** | **없음** | — |

공통 요건:

- **SSO + WebAuthn(하드웨어 키) 의무.** SMS·TOTP 불가.
- 회사 관리 기기(MDM 등록 + 디스크 암호화 + 디바이스 인증서)에서만 접근. 개인 기기 차단.
- **모든 권한 상승은 만료된다.** 영구 권한은 존재하지 않는다.
- 상승 요청에는 **사유와 티켓 번호가 필수**이며, 사유 없는 요청은 시스템이 거부한다.
- 퇴사·직무변경 시 권한 회수 **즉시(자동), 최대 1시간 내 검증**. 분기 1회 전수 권한 재인증(access review).
- 개인정보취급자 목록을 유지하고 연 1회 이상 교육(법정 요건)을 실시하며 이수 증적을 보관한다.

## 5.4 "고객 지원을 위한 임시 열람" — 만들 것인가

### 결론: 만들지 않는다.

**근거**

1. **판매 논거의 주어만 바뀐다.** 이 제품의 유일한 차별점은 "관리자도 못 본다"인데, 우리 직원이 볼 수 있으면 그 문장은 "회사 관리자는 못 보고 벤더 직원은 볼 수 있다"가 된다. 직원 입장에서 이건 개선이 아니다.
2. **실사에서 이 질문은 반드시 나오고, "가능하지만 로그가 남습니다"는 최악의 답이다.** "불가능합니다"는 한 문장으로 끝나고, "가능하지만"은 후속 질문 열 개를 부른다.
3. **대부분의 신뢰 사고가 여기서 난다.** 기능이 있으면 쓰이고, 쓰이면 언젠가 사유 없이 쓰인다.
4. **대체 수단이 실제로 충분하다.** 아래.

### 대체 수단

**(a) 소유자 주도 진단 세션** — 핵심 차이는 **시작 권한이 우리에게 없다는 것**이다.

사용자가 `지원팀에 이 문서 보여주기` 버튼을 누르면:

- 단일 문서 · **15분** 유효 · 지정 담당자 **1인** · 화면 전체에 워터마크(담당자 이름 + 시각)
- 소유자 화면에 **진행 중 배너 상시 노출** + 언제든 `[지금 끊기]`
- 종료 시 자동 회수, 열람 기록이 소유자 로그에 남음
- **비공개 노트(L4)는 이 세션에서도 보이지 않는다**
- 구현상 이것은 "impersonation"이 아니라 **소유자가 발급하는 공유 링크의 특수 형태**다. 즉 새로운 권한 경로가 아니라 기존 경로의 파라미터 조정이다 — 이 구현 차이가 감사 시 결정적이다.

**(b) 콘텐츠 없는 진단 번들** — 사용자가 버튼 한 번으로 첨부. 담기는 것:

```
노드 수 · 최대 깊이 · 갈래 수 · 엣지 종류별 카운트 · 에러 키 · 클라이언트 버전
브라우저/OS · 최근 20개 액션의 타입(내용 없음) · 텍스트는 길이와 해시만
```

대부분의 버그는 이것으로 재현된다. 못 하면 (c)로 간다.

**(c) 합성 재현 케이스** — 지원 담당이 사용자와 통화하며 구조만 듣고 합성 문서를 만들어 재현한다. 느리지만 안전하고, 실제로 대부분 성공한다.

**(d) break-glass** — 위 셋으로 불가능하고 **데이터 손상 복구처럼 본문 접근이 불가피한 경우에만**.

| 요건 | 내용 |
|---|---|
| 승인 | **2인 승인**(엔지니어링 책임자 + 보안 책임자). 요청자는 승인자가 될 수 없다 |
| 고객사 동의 | **고객사 CPO의 사전 서면 동의**(이메일 가능). 긴급 시 사후 4시간 내 |
| 소유자 통지 | **24시간 내 개별 통지.** 예외 없음 |
| 범위 | 특정 문서 ID 목록으로 한정. 와일드카드 금지 |
| 시간 | 최대 60분, 자동 만료 |
| 기록 | 세션 프록시를 통해 **실행된 전 쿼리와 반환 행수**를 WORM 로그에 기록 |
| 대상 제외 | **L4(비공개 노트)는 break-glass로도 열 수 없다** |
| 사후 | 7일 내 사후 검토 회의, 재발 방지책 도출, 대장 기록 |

### 무엇을 남기는가

| 대상 | 기록 항목 | 보관 |
|---|---|---|
| 문서 열람 | 문서 ID, 열람자(로그인 시 user_id / 비로그인 시 토큰 ID), 시각, 경로(직접/링크/진단세션), UA 요약 | 1년 |
| 공유 링크 | 생성·열람·만료·회수, 스코프, 만료일 | 1년 |
| 권한 변경 | 롤 부여·회수, 승인자, 사유, 티켓 | 3년 |
| **break-glass** | 세션 전체 쿼리, 반환 행수, 승인자, 고객 동의 증빙 | **3년** |
| 관리자 집계 쿼리 | 뷰 이름, 필터, 기간 프리셋, 반환 셀 수 | 1년 |
| 삭제·복구 | 대상, 방법, 실행 주체, 검증 결과 | 3년 |

| **`private_note` 복호화** | 호출자 세션, 대상 item, 시각 | 3년 |
| SCIM 동기화 | 생성·수정·비활성 건수, 실패 사유 | 1년 |

**법정 최소는 접속기록 1년**(고유식별정보·민감정보를 처리하거나 정보주체 5만명 이상이면 2년)이다. 우리는 위 표대로 1~3년을 적용하고, **문서 본문에 고유식별정보가 우발적으로 포함될 수 있으므로 안전측으로 2년 기준을 준용**한다.

### 누가 보는가

여기가 이 제품의 특이점이다. 일반적인 감사 로그는 관리자가 보지만, **우리는 방향을 뒤집는다**(TRUST.md §2.4).

| 로그 | 소유자 본인 | 고객사 관리자 | 우리 제품팀 |
|---|---|---|---|
| 내 문서 열람 로그 | **볼 수 있다(최근 90일)** | **못 본다** | 못 본다(집계만) |
| 내 공유 링크 활동 | 볼 수 있다 | 못 본다 | 못 본다 |
| 조직 전체 열람 통계 | — | **못 본다** | 못 본다 |
| 관리자 집계 쿼리 로그 | — | 자기 것 | 보안 담당 2인 |
| break-glass | 대상 소유자에게 통지 | **월간 요약 제공** | 보안 담당 2인 |
| 인증·권한 | 자기 것 | 조직 범위 | 보안 담당 2인 |

- **표시 창과 보관 기간이 다르다.** 소유자에게 보이는 열람 로그는 90일(TRUST.md §7)이고, 보안 감사용 원본은 1년 보관 후 파기한다. 이 차이를 신뢰 헌장과 처리방침에 그대로 적는다 — 숨기면 나중에 "90일이라며 왜 1년 있냐"가 된다.
- 열람자 쪽에는 "누가 내 열람 기록을 봤다"가 표시되지 않는다(TRUST.md).
- **관리자에게는 월간 요약을 준다** — 누가 무엇을 봤는지가 아니라, **관리자 뷰가 개인을 조회할 수 없었음을 증명하는 통계**다(MEASUREMENT.md §3). 이 요약을 인사팀에 공개하는 것이 직원 신뢰의 실질적 근거가 된다.

### 무결성

- append-only. S3 Object Lock(거버넌스 모드) 또는 CloudWatch Logs + 불변 아카이브.
- 일 1회 해시 체인 앵커링(전일 로그 해시를 당일 로그 첫 줄에 포함) → 중간 삭제 검출 가능.
- 감사 로그를 지울 수 있는 권한은 **누구에게도 없다**(보존기간 경과 자동 파기만).

# 6. 국내 기업 보안 실사 대응

## 6.1 ISMS-P — 언제 받는가

**의무 대상 여부: 현재 해당 없음.**

의무 대상은 ① 정보통신망서비스 제공자(ISP) ② 집적정보통신시설사업자(IDC) ③ 연간 매출액 또는 세입 1,500억원 이상(조건부) ④ **정보통신서비스 부문 전년도 매출액 100억원 이상** ⑤ **전년도 말 기준 직전 3개월간 일일평균 이용자 수 100만명 이상**. 국내 중견·중소 대상 B2B SaaS 초기 단계는 ④⑤ 어디에도 닿지 않는다.

의무 대상이 되면 **그 다음 해 8월 31일까지 취득**해야 하므로, 매출이 튀는 해에 준비를 시작하면 늦는다.

**착수 트리거 (하나라도 발생하면 준비 시작)**

| # | 트리거 | 근거 |
|---|---|---|
| 1 | 정보통신서비스 부문 매출이 **60억원**(의무선의 60%)에 도달 | 준비 6~12개월 + 심사 소요를 역산하면 여기가 마지노선 |
| 2 | "인증 미보유"가 **실주 사유로 2건 이상** 누적 | 시장이 요구하기 시작한 신호 |
| 3 | 공공·금융·통신 고객사 파이프라인 진입 | 이 시장은 인증이 입장권 |

**그 전까지 무엇으로 버티는가** — 이게 실무의 핵심이다.

> **ISMS-P 인증기준 항목번호를 그대로 따르는 자가점검표 + 근거자료 묶음**을 만든다.

인증기준은 관리체계 수립·운영(16개) + 보호대책 요구사항(64개) + 개인정보 처리단계별 요구사항(21개) 구조다. 각 항목에 대해 `충족 / 부분충족 / 해당없음 / 미충족(계획 있음)`과 증빙 파일명을 매핑한 표를 만들어 두면, **실사 담당자의 90%는 이걸로 통과시킨다.** 인증서가 없다는 사실보다 "항목별로 답할 수 있는가"가 실제 판단 기준이기 때문이다.

**ISMS vs ISMS-P**: 우리는 개인정보 처리가 서비스의 본질이므로 **ISMS-P**다. 정보보호만 인증하는 ISMS로는 이 제품의 실사 질문(§6.4)에 답이 안 된다. 다만 중소기업 대상 간편 인증 제도가 운영되고 있으므로, 조직 규모에 맞는 트랙을 심사기관과 사전 협의한다.

## 6.2 SOC 2 / ISO 27001 — 국내 시장에서 필요한가

| 인증 | 국내 중견기업 실사에서의 위치 | 판단 |
|---|---|---|
| **ISMS-P** | 점검표에 칸이 있다. 사실상 표준 | 의무 대상 도달 시 필수 |
| **ISO 27001** | 다수 점검표가 "ISMS-P **또는 동등 인증**"으로 인정. 해외 확장 겸용 | **먼저 받는다** |
| **ISO 27701** | 개인정보 확장. ISO 27001 보유 시 증분 비용 낮음 | 2단계 |
| **SOC 2 Type II** | 국내 중견 구매팀 인지도 낮음. 외국계 한국법인, 국내 대기업 IT 자회사, 해외 고객에서만 요구 | **실제 요구가 2건 이상 쌓이기 전엔 안 한다** |
| CSAP | 공공 클라우드 조달용 | 공공 진입 결정 전엔 무관 |

**순서: ISO 27001 → (매출 트리거) ISMS-P → (해외/대기업 트리거) SOC 2.**

ISO 27001을 먼저 두는 이유는 비용·기간(6~9개월) 대비 실사 통과율이 가장 좋고, ISMS-P 준비의 8할이 그대로 재사용되며, 나중에 해외 고객이 생겼을 때 다시 만들 필요가 없기 때문이다.

## 6.3 리전 · 망분리 · 온프레미스 요구

**클라우드 리전**

- **AWS 서울(ap-northeast-2) 단일 리전 고정.** DR도 국내 AZ.
- 계약서 문장: *"고객 콘텐츠 및 이용자 개인정보는 대한민국 내 데이터센터에만 저장·처리된다. 유일한 예외는 부속서에 기재된 인증 서비스(WorkOS)이며, 이전 항목은 이용자 신원 정보에 한정되고 문서 본문은 포함되지 않는다."*
- 국외이전 자체가 결격인 고객엔 **국외이전 제로 플랜**(§2.4).

**망분리**

「개인정보의 안전성 확보조치 기준」의 인터넷망 차단 조치는 **2025년 10월 31일 시행 개정으로 위험평가 기반**으로 바뀌었다. 대상도 일일평균 100만명 이상 대규모 처리자 중심이므로 **우리는 의무 대상이 아니다.**

그러나 구매팀 점검표에는 "개인정보취급자 단말 망분리 여부" 칸이 **여전히 남아 있다.** 대응은 "해당 없음"이 아니라 **동등 이상 논증**이다.

| 망분리가 막으려는 위험 | 우리 대체 통제 |
|---|---|
| 취급자 단말에서 개인정보 대량 다운로드 | **사람 롤에 본문 컬럼 SELECT 권한이 없다.** 다운로드할 대상 자체가 없음 |
| 단말 감염을 통한 내부망 침투 | MDM + 디바이스 인증서 + 제로트러스트(모든 접근이 IdP·기기 검증 통과) |
| 상시 접근 권한 오남용 | **상시 프로덕션 권한 0**, JIT 60분 만료 |
| 행위 추적 불가 | 세션 프록시 전 쿼리 기록 + WORM |

이 표를 위험평가 문서와 함께 제출하면 대부분 통과한다. **"다운로드할 권한이 애초에 없다"가 망분리보다 강한 답이다.**

| 11 | 개인정보보호책임자(CPO) 지정·공개 | 법 제31조. 성명·직책·연락처를 처리방침에 공개. 소규모 사업자는 대표가 CPO |
| 12 | 임직원 보안서약서·연 1회 교육 증적 | 입사 시 서약 + 연 1회 교육 이수 기록. **가명정보 재식별 금지 서약 별도** |
| 13 | 인력 퇴사 시 권한 회수 SLA | 즉시 자동 회수, 1시간 내 검증 로그 |
| 14 | 소스코드 보안점검·오픈소스 라이선스 | SAST + SCA를 CI에 통합, SBOM 제공 가능 |
| 15 | **사이버배상책임보험 가입 여부** | 법정 의무는 **전년도 매출 10억원 이상 + 직전 3개월 일일평균 정보주체 1만명 이상**(시행령 제48조의7, 2024.3 상향)이라 초기엔 미대상. 그러나 **점검표에는 자주 있으므로 조기 가입을 권고** — 보험료가 실주 1건보다 싸다 |

## 6.5 자체 호스팅(on-prem) 옵션을 제공할 것인가

### 결론: 제공하지 않는다.

**근거 — 세 번째가 결정적이다.**

1. **운영 비용의 이중화.** 소규모 팀에서 온프레 배포판은 릴리스·보안 패치·마이그레이션·사고 대응이 전부 두 벌이 된다. 고객 환경에서 난 사고도 우리 평판 사고가 된다.
2. **매출 기여가 작다.** 국내 중견·중소 SaaS에서 온프레 요구는 있지만, 실제 계약 전환율과 단가를 감안하면 초기 매출의 5% 미만으로 추정된다.
3. **★ 신뢰 모델이 오히려 나빠진다.** 온프레에서는 고객사 IT팀이 DB에 직접 접근할 수 있다. 즉 **"관리자에게 자동 열람권이 없다"는 절대 원칙 1이 우리 손이 아니라 고객 손에서 깨진다.** 우리가 통제할 수 없는 방식으로 제품 정체성이 무너지는 배포 형태를 팔 수는 없다. 이건 비용 문제가 아니라 정합성 문제다.

**대신 제공하는 것** — 온프레 요구의 실제 동기(데이터 주권 / 격리 / 벤더 종속 우려)를 각각 흡수한다.

| 동기 | 대체 제공물 |
|---|---|
| 데이터 주권 | 국내 리전 고정 + **국외이전 제로 플랜** + 계약서 리전 조항 |
| 테넌트 격리 | **전용 VPC + 전용 DB 인스턴스**(격리 플랜) |
| "벤더가 언제든 볼 수 있다" | **BYOK** — 고객이 키를 회수하면 우리가 읽을 수 없다. 이게 온프레의 심리적 동기를 가장 정확히 대체한다 |
| 벤더 종속 | **상시 데이터 내보내기 API** + 문서화된 스키마 + 계약상 반출 SLA |
| 사업 지속성 | 소스코드 에스크로(제3자 예치) — 우리 폐업 시에만 개방 |

**예외 검토 조건**(사실상 발생하지 않도록 높게 설정): 단일 계약 ARR 3억원 이상 + 3년 이상 계약 + 전담 엔지니어 인건비 고객 부담 + **절대 원칙 4개를 고객사가 자사 정책으로 승계한다는 서면 확약.** 마지막 조건이 핵심이며, 이것 없이는 어떤 금액에도 하지 않는다.

# 7. 사고 대응 (Incident Response)

## 7.1 국내법상 신고·통지 의무

| 항목 | 요건 |
|---|---|
| **신고 시한** | 유출 등을 **알게 된 때로부터 72시간 이내**, 개인정보보호위원회 또는 KISA |
| **신고 대상** | ① 1천명 이상 정보주체의 개인정보 유출 ② **민감정보 또는 고유식별정보가 1건이라도 유출** ③ 개인정보처리시스템 또는 취급자 정보기기에 대한 **외부로부터의 불법적 접근**에 의한 유출 |
| **정보주체 통지** | 알게 된 때로부터 **72시간 이내**, 개별 통지 |
| **통지 항목** | ① 유출된 항목 ② 유출 시점과 그 경위 ③ 피해 최소화를 위해 정보주체가 할 수 있는 방법 ④ 처리자의 대응조치 및 피해 구제절차 ⑤ 신고 접수 담당부서와 연락처 |
| **홈페이지 게시** | 1천명 이상 유출 시 **7일 이상** 게시 |
| **예외** | 천재지변 등 부득이한 사유 시 해소 후 지체 없이. 경로가 확인되어 회수·삭제 등으로 권익 침해 가능성이 현저히 낮아진 경우 신고 생략 가능 |
| **2024년 이후 강화** | 개인정보처리시스템에 대한 **불법적 접근을 알게 된 경우 유출 가능성만으로도** 통지 대상 |
| **제재** | 미신고 3천만원 이하 과태료 |

## 7.2 우리 지위에 따른 절차 — 여기가 핵심 구조

**신고·통지 의무자는 처리자인 고객사다. 우리는 수탁자다.** 그러나 사고를 먼저 아는 쪽은 거의 항상 우리다.

```
T+0     우리가 인지
T+1h    내부 사고 선언(SEV 판정), 봉쇄 시작, 사고 지휘자 지정
T+6h    중대 사고(SEV1)는 고객사 CPO에게 1보 — 불완전해도 보낸다
T+24h   전 사고 유형에 대해 고객사 통지(계약 의무). 영향 범위 초안 제공
T+48h   신고서 초안 + 기술 분석 자료 고객사에 전달
T+72h   고객사가 개인정보위/KISA 신고 및 정보주체 통지 (우리는 자료·대행 지원)
T+7d    상세 사고 보고서(원인·범위·조치·재발방지)
T+30d   재발방지 완료 보고 + 검증 증적
```

**T+24h 통지가 계약 의무인 이유**: 고객사의 72시간은 "고객사가 안 시점"부터 흐르지만, 실무에서 감독기관은 수탁자 인지 시점을 함께 본다. 24시간 안에 알리지 않으면 고객사가 법정 시한을 지킬 수 없고, 그 책임이 우리에게 구상된다.

**등급 판정**

| 등급 | 정의 | 예 |
|---|---|---|
| **SEV1** | L3/L4 유출 또는 타인 문서 노출. 고유식별정보 포함 가능성 있음 | 잘못된 매칭, 대규모 링크 유출, DB 침해 |
| **SEV2** | L2 유출, 또는 노출 범위가 한정된 L3 | 이메일 오발송, 소수 링크 유출 |
| **SEV3** | 집계 결함(k-익명 위반), 권한 오설정(실제 열람 없음) | contributor_n<5 셀 노출 |
| **SEV4** | 잠재 취약점, 미열람 노출 | 스캐너 탐지, 내부 발견 |

**중요**: 문서 본문에 고유식별정보가 우발적으로 포함됐을 **가능성**만으로도 SEV1로 시작한다. §3의 설계상 우리는 무엇이 들어있는지 모르므로, **모른다는 사실이 등급을 낮추는 근거가 될 수 없다.** 이 원칙을 미리 정해두지 않으면 사고 순간에 "아마 없을 것"이라는 낙관이 이긴다.

## 7.3 이 제품 특유의 사고 유형

### A. 공유 링크 유출

**시나리오**: 카톡 단톡방 전달, 이메일 오발송, 외부 사이트에 붙여넣기, 검색엔진 색인.

| 단계 | 조치 |
|---|---|
| 탐지 | 링크별 이례 열람 패턴(고유 IP 급증, 조직 외 ASN, 봇 UA) → **소유자에게 먼저 알림.** 관리자·우리에게 먼저 가지 않는다 |
| 1차 | 소유자에게 `[지금 끊기]` 1클릭 제공 |
| 2차 | 소유자 무응답 24시간 + 열람 급증 지속 → 우리가 링크를 **정지**하고 소유자에게 사후 통지(사유 기록) |
| 조직 단위 | 대량 유출 정황 시 조직 전체 외부 링크 일괄 만료. 실행 시 **소유자 전원에게 개별 통지** |
| 검색엔진 | 색인 확인 시 각 엔진에 제거 요청 + 캐시 삭제 요청. 진행 상황을 소유자에게 공유 |

**소유자에게 보내는 문구** (탓하지 않는다 — WRITING.md)

> `이 링크를 처음 보는 곳에서 여러 번 열었어요.`
> `어제부터 32번, 회사 밖에서요. 지금 끊을까요?`
> `[지금 끊기]` `[그대로 두기]`

"유출되었습니다", "부주의하게 공유하셨습니다" 같은 문장은 쓰지 않는다. 링크를 만든 것은 정상 행위였고, 문제는 우리가 만료 정책을 짧게 못 잡은 것일 수도 있다.

### B. 잘못된 매칭으로 타인 문서 노출 — 최악

**이 스택에서 실제로 가장 흔한 원인**: Next.js App Router의 라우트/데이터 캐시 오염, RSC 페이로드 캐싱, `unstable_cache`를 사용자별 데이터에 사용, `org_id` 조건이 빠진 쿼리, 커넥션 풀에서 RLS 세션 변수 미초기화.

| 단계 | 조치 |
|---|---|
| 즉시 | **해당 기능 킬스위치**(피처 플래그로 즉시 차단). 캐시 전면 무효화 |
| 범위 산정 | 로그로 **"누가 누구 문서를 언제 몇 초"** 정확히 산정. 추정치로 넘어가지 않는다 |
| 통지 | **양쪽 모두에게.** 문서가 보인 사람(소유자)에게는 무엇이 보였는지, 문서를 본 사람에게는 **캡처·전달했다면 삭제 요청**. 본 사람에게 알리는 것을 빠뜨리면 사본이 남는다 |
| 등급 | 무조건 SEV1 |
| 재발 방지 | 아래 예방책의 CI 테스트 추가를 **재발방지 완료 조건**으로 |

**예방 (구현 요구사항)**

- Drizzle 쿼리 래퍼에서 **테넌트 스코프 미지정 쿼리는 타입 에러**로 컴파일 실패
- Postgres RLS + 애플리케이션 레벨 이중 검사(둘 중 하나만 있으면 언젠가 뚫린다)
- 캐시 키에 `org_id + user_id` 강제. 사용자별 데이터에 `unstable_cache`/`fetch` 캐시 **사용 금지**를 ESLint 규칙으로
- 커넥션 반환 시 세션 변수 리셋 검증
- **CI 크로스테넌트 테스트**: 조직 A 세션으로 조직 B의 모든 리소스 ID에 접근 시도 → 전부 404여야 통과. 실패 시 배포 차단

### C. k-익명성 우회

**공격 벡터**: ① 임의 기간 파라미터를 이용한 차분 공격 ② 필터 조합 ③ 신규 입사/퇴사에 의한 시계열 차분 ④ 라운딩 역산 ⑤ 억제된 셀이 하나뿐일 때의 차집합 복원.

방어는 이미 MEASUREMENT.md §3에 구현되어 있다(기간 프리셋 고정, 동시 필터 2개, 2차 억제, 5단위 라운딩, CI 퍼즈 10만건). 사고 시 절차:

| 단계 | 조치 |
|---|---|
| 탐지 | 배포 시 + 매일 검사에서 `contributor_n < 5` 셀 1건이라도 → **P0, 관리자 대시보드 자동 차단** |
| 범위 | 어떤 셀이 언제부터 노출됐는지, 관리자 쿼리 로그로 **실제 조회 여부** 확인 |
| 통지 | 해당 부서 직원에게 통지. **문구가 어렵다** — 아래 |
| 복구 | 뷰 수정 → 퍼즈 테스트 통과 → 단계적 재개방 |

**통지 문구** — "당신 정보가 유출됐다"는 부정확하고 과도한 공포를 만든다. 정확히 쓴다.

> `관리자 화면에서 5명이 안 되는 그룹의 숫자가 계산돼 나갔어요.`
> `3월 12일부터 14일까지, 총 2개 항목이었어요. 이름이나 문서는 들어 있지 않았고, 평균 소요시간 숫자였어요.`
> `사람 수가 적으면 평균만으로도 누구인지 짐작될 수 있어서, 원래는 계산 자체를 안 하도록 되어 있어요. 그 부분이 작동하지 않았어요.`
> `지금은 막았고, 같은 일이 안 생기게 자동 검사를 추가했어요.`

### D. 관리자 뷰 결함

**유형**: 드릴다운 파라미터가 살아 있음 / export CSV에 `owner_id` 컬럼이 포함됨 / 에러 메시지에 실명 노출 / 툴팁에 원본 부서명 노출 / 신규 위젯이 base 테이블을 조회.

- 탐지: `admin_reader` 롤의 base 테이블 접근 시도 1건 → P0(MEASUREMENT.md §9)
- 대응: 위젯 단위 차단 → 노출 범위 산정 → 조직 통지 + **직원 통지**(관리자에게만 알리고 끝내면 안 된다)
- 예방: 관리자 화면 코드에서 `actor_pid` 컬럼 보유 테이블과 PostHog 클라이언트에 대한 임포트를 아키텍처 테스트로 금지

### E. 퇴사자 인계 오류 / SCIM 동기화 오류

- 후임자 오지정으로 타인에게 문서 소유권 이전 → **수락 전에는 열람 불가**한 설계(§9.2)가 1차 방어. 그래도 발생 시 즉시 회수 + 양쪽 통지.
- SCIM 부서 오배정으로 잘못된 부서 집계 → 집계 재계산 대신 해당 기간 셀 **억제**(재계산은 차분을 만든다).

## 7.4 커뮤니케이션 원칙

1. **직원에게 직접 알린다.** 법적 통지 주체는 고객사지만, 고객사 명의 공문만으로 끝내지 않는다. **고객사 명의 통지 + 우리가 제공한 문안 + 제품 내 개인 배너**를 병행한다. 자기 문서가 걸린 사람이 인사팀 공지로 처음 아는 상황은 만들지 않는다.
2. **불완전해도 24시간 안에 1보.** "조사 완료 후 알리겠다"는 신뢰를 더 깎는다.
3. **정확히 무엇이 보였는지 쓴다.** "일부 데이터"가 아니라 "3월 12일 14:02~14:09, 문서 2개의 단계 제목".
4. **원인을 사용자·직원 탓으로 돌리는 문장 금지.** 수동태로 책임을 지우는 것도 금지("노출이 발생하였습니다" → "저희 코드가 다른 사람 문서를 보여줬어요").
5. **다음에 무엇을 할지와 기한을 쓴다.** "재발 방지에 만전을 기하겠습니다" 금지 — 구체 조치와 날짜.
6. WRITING.md 준수. 사고 문안이라고 하십시오체로 돌아가지 않는다(인사팀 명의 공지문만 합니다체).

## 7.5 사고 후 신뢰 복구

이 제품은 **한 번의 사고로 조직 전체 채택이 0이 될 수 있다.** 복구는 보상이 아니라 증명으로 한다.

| # | 조치 | 이유 |
|---|---|---|
| 1 | **TRUST.md §8 기록표에 사고를 그대로 등재하고 공개** | 헌장을 어길 뻔한 순간을 기록하겠다는 약속의 이행. 숨기는 순간 문서 전체가 거짓이 된다 |
| 2 | **해당 조직의 관리자 집계를 30일간 우리가 먼저 중단 제안** | 우리가 손해를 감수하는 신호. 요구받아서 하는 것과 먼저 하는 것은 다르다 |
| 3 | 외부 검증 — 3자 침투테스트/코드 감사 결과 요약 공개 | 자기 진단은 신뢰를 못 만든다 |
| 4 | 재발방지책을 **코드 레벨로 제시** — 추가된 테스트 목록과 통과 결과 | "프로세스를 강화했다"는 검증 불가 |
| 5 | **영향받은 개인에게 전량 삭제 + 계정 탈퇴 옵션 제공** | 조직이 아니라 개인이 선택권을 갖게 |
| 6 | 30일 후 후속 보고 1회 더 | 잊혔다고 생각할 때 한 번 더 오는 것이 신뢰를 만든다 |

**하지 않는 것: 무료 이용 기간 연장.** 보상은 조직이 받고 피해는 개인이 봤는데, 조직에 할인을 주면 개인 입장에선 자기 피해가 회사 예산으로 정산된 것이 된다. **개인에게 직접 가는 조치만 보상으로 친다.**

# 8. 공유 링크 보안

## 8.1 토큰 설계

| 항목 | 값 | 근거 |
|---|---|---|
| 엔트로피 | **192비트**(`crypto.randomBytes(24)`) | 활성 링크 10^7개, 초당 10^6 추측 가정 시에도 예상 발견 시간이 우주 나이를 넘는다. 128비트로도 충분하지만 여유를 둔다 |
| 인코딩 | base64url 32자 | URL 안전, 대소문자 구분 |
| URL 형태 | `/s/{token}` | **문서 ID를 URL에 넣지 않는다** — 열거 공격 표면 제거 |
| DB 저장 | **SHA-256 해시만.** 평문 미저장 | DB가 유출돼도 링크를 사용할 수 없다. 생성 직후 1회만 평문을 사용자에게 보여준다 |
| 조회 | 해시 인덱스 조회. 상수 시간 비교 | 타이밍 공격 차단 |
| 무효화 | 해시 행 삭제(soft delete 아님) | |
| 속도 제한 | 잘못된 토큰 IP당 분당 10회 → 차단 | 브루트포스 탐지 |

**토큰을 로그에 남기지 않는다.** 액세스 로그의 URL 경로에서 `/s/` 뒤를 마스킹하고, Referer 헤더 기록도 끈다. 이걸 안 하면 링크가 로그에 평문으로 쌓인다.

## 8.2 만료 정책 — 현재 30일 기본값 평가

**평가: 단일 기본값 30일은 두 용도에 동시에 나쁘다.** 인계·휴가 안내 용도엔 짧고(휴가는 2주, 인계는 한 달 이상 이어진다), 외부 유출 관점에선 길다.

**결정: 용도별로 나눈다.**

| 링크 종류 | 기본 만료 | 상한 | 근거 |
|---|---|---|---|
| 조직 내 공유(로그인 필요) | **30일** | 180일 | 현행 유지. 위험이 낮다 |
| 인계용 링크 | **14일** | 60일 | 목적이 끝나면 링크도 끝나야 한다 |
| **조직 외부 공개 링크** | **7일** | **30일** | 최대 유출 경로. 기본값을 짧게 |
| 지원 진단 세션(§5.4) | **15분** | 15분 | 연장 불가 |

**추가 안전장치**

- **미열람 링크 7일 자동 만료.** 만들고 안 보낸 링크가 가장 위험하다 — 잊히고, 아무도 회수를 생각하지 않는다.
- 만료 3일 전 소유자에게 알림 + 1클릭 연장. **자동 연장은 없다.**
- 링크당 최대 열람 횟수 상한(선택). 인계용은 기본 50회.
- 조직 정책으로 **상한만** 강제 가능. 관리자는 만료 상한과 외부 공유 허용 여부를 정할 수 있고, **링크 내용은 볼 수 없다.** 이 구분이 원칙 1을 지키면서 조직 통제 요구를 흡수하는 지점이다.

## 8.3 조직 외부 공유를 허용할 것인가

**허용한다. 기본값은 차단, 조직이 켤 수 있고, 켜도 링크 단위로 소유자가 선택한다.**

없애지 않는 이유: 실제 수요가 있다. 회계법인·세무사에게 정산 흐름 공유, 외주 업체 인계, 관계사 담당자와의 프로세스 조율. 없애면 사람들은 PDF로 내보내 카톡으로 보낸다 — **우리가 통제할 수 없는 형태로 유출된다.** 링크는 회수라도 가능하다.

**3단계 스코프**

| 스코프 | 접근 조건 | 기본값 |
|---|---|---|
| `org_member` | 로그인 + 같은 조직 | **기본값** |
| `org_guest` | 지정 이메일로 OTP 발송 후 열람. 이메일당 개별 추적 | 선택 |
| `public_link` | 토큰만 있으면 열람 | 조직이 허용한 경우만 |

**외부 링크에 부여하는 마찰** (막지 않고 느리게 한다)

1. 생성 시 클라이언트 PII 힌트 재검사 → `[가리고 공유]` 제안(§3.4)
2. 확인 1스텝: `이 링크는 회사 밖에서도 열려요.`
3. 7일 기본 만료
4. 열람 페이지 하단에 옅은 워터마크(토큰 앞 6자 + 열람 시각) — 스크린샷이 돌 때 출처 추적 가능
5. 내보내기(PDF) 버튼 숨김(원하면 소유자가 직접 내보내기)

## 8.4 열람 로그의 개인정보 이슈

**있다.** 열람자 입장에서는 자신의 행동이 타인에게 기록·표시되는 것이고, 그건 그 사람의 개인정보다.

| 열람자 유형 | 소유자에게 표시 | 필수 조건 |
|---|---|---|
| 같은 조직 로그인 사용자 | **실명 + 시각** | **열람 전 고지 필수**(아래) |
| `org_guest`(OTP) | 이메일 + 시각 | 초대 메일에 고지 |
| 비로그인 외부 | **`외부에서 3회 열람`** — 신원 없음 | IP 원본 미저장(해시 30일, 국가/ASN만 통계) |
| 링크 프리뷰 봇(카톡·슬랙) | **로그에서 제외** | 봇 열람을 사람 열람으로 세면 로그가 거짓이 된다 |

**고지 문구 — 공유 페이지 상단에 상시 노출**

> `이 문서를 열면 만든 사람에게 표시돼요.`

이 한 줄이 없으면 열람 로그는 **몰래 추적**이 된다. 있으면 대칭적 투명성이 된다. 소유자가 열람자를 아는 것과 열람자가 그 사실을 아는 것은 세트여야 한다.

**금지 사항**

- 조직 관리자는 **어떤 열람 로그도 보지 못한다.**
- 열람 로그 기반의 조직 통계를 만들지 않는다("가장 많이 읽힌 문서", "가장 많이 읽는 사람" 전부 금지 — 후자는 명백히 감시다).
- 열람자에게 "누가 내 열람 기록을 봤다"는 표시하지 않는다(TRUST.md).

## 8.5 크롤링 · 리퍼러 · 회수

| 위험 | 조치 |
|---|---|
| 검색엔진 색인 | `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` (헤더) + `<meta name="robots">` 이중. robots.txt에 `Disallow: /s/`(경로만, 토큰 노출 없음) |
| 리퍼러 유출 | 공유 페이지 전체 `Referrer-Policy: no-referrer`. 본문 내 외부 링크는 `rel="noopener noreferrer"` |
| **OG 미리보기 유출** | **OG 이미지에 본문 텍스트를 렌더링하지 않는다.** 제목 + 단계 수 + 브랜드만. 카톡·슬랙 미리보기 캐시는 우리가 회수할 수 없고 **링크를 끊어도 남는다** |
| CDN 캐시 | 공유 페이지 `Cache-Control: private, no-store`. CDN 캐시 비활성 |
| 내보내기 파일 | S3 서명 URL **5분** 유효, 1회성 |
| 브라우저 히스토리·자동완성 | 토큰이 주소창에 남는 건 불가피 → 만료 정책으로 흡수 |
| **회수** | 1클릭 즉시 무효(해시 삭제). 회수 후 접근 시 `이 링크는 끊겼어요.` + `[만든 사람에게 다시 요청하기]` |
| 일괄 회수 | 설정에서 `내가 만든 링크 모두 끊기` |
| 조직 단위 일괄 만료 | 사고 대응용으로만. **관리자는 만료만 가능, 열람 불가.** 실행 시 소유자 전원 통지 + 사유 기록 |

# 9. 퇴사자 · 조직 변경 처리

## 9.1 기본 입장 — 소유권을 두 겹으로 나눈다

이 문제가 법적·정책적으로 애매한 이유는 "문서"를 하나의 덩어리로 보기 때문이다. **쪼개면 답이 나온다.**

| 층 | 내용 | 귀속 | 근거 |
|---|---|---|---|
| **프로세스 지식** | 단계 목록, 순서, 갈래, 도구, 인계 관계, 소요시간 버킷 | **회사** | 재직 중 직무상 작성한 업무 산출물. 회사가 대가를 지급하고 얻은 결과물 |
| **개인의 서술과 주석** | 비공개 노트, 짜증 플래그, 본인 코멘트, 인앱 설문 자유응답 (L4) | **개인** | **"소유자만 본다"는 약속 하에서만 존재하는 데이터.** 약속이 없었으면 수집 자체가 불가능했다 |
| **신원 표시** | 작성자 이름, 담당자 표시 | **개인** | 개인정보. 분리·가명화 가능 |

**L4가 개인에게 귀속되는 논거를 한 문장으로**: 이 데이터는 목적 구속적으로 수집됐다. 수집 시점의 목적이 "소유자 본인의 기록"이었으므로, 이를 회사에 이전하는 것은 **수집 목적 외 이용**(법 제18조)에 해당한다. 계약으로 뒤집을 수 있는 성질이 아니다.

**이 비대칭을 언제 알리는가 — 입사 온보딩 첫 화면과 이용약관.** 나중에 알리면 배신이고, 지금 알리면 규칙이다.

> `퇴사하실 때 흐름 문서는 회사에 남고, 비공개 메모는 함께 지워져요.`

## 9.2 퇴사 처리 절차

**트리거**: SCIM `active=false`. 인사시스템이 원천이므로 별도 신청 절차가 없다.

| 시점 | 조치 |
|---|---|
| **퇴사 확정 시점**(재직 중) | 본인에게 안내: `내 데이터 내보내기`, `비공개 메모 정리하기`. **재직 중에만 가능** |
| **D-day** | 로그인 차단. 문서는 그대로 유지. **본인이 만든 공유 링크 전부 즉시 만료** ← 퇴사자의 살아있는 외부 링크가 최대 리스크 |
| **D-day** | **비공개 노트(L4) 즉시 파기.** 암호키 슬롯 파기까지 포함. 복구 불가 |
| D+0~30 | 소유권 이전 대기 기간. 이 기간 동안 문서는 **누구도 열 수 없다** |
| D+30 | 이전 미완료 시 부서 보관함으로 이동 |

**소유권 이전은 강제인가 선택인가 — 강제다. 단, 받는 쪽은 선택이다.**

- 관리자가 후임자를 **지정**한다(강제 트리거).
- **후임자가 수락해야 이전이 완료된다.** 수락 전에는 후임자도 문서를 열 수 없다. 강제 배정으로 남의 문서가 자동으로 열리는 경로를 만들지 않는다.
- 이전 완료 시 후임자 화면에 표시:

> `비공개 메모 3개는 함께 넘어오지 않았어요.`

**존재 사실만 알리고 내용은 주지 않는다.** 이 한 줄이 이 정책의 핵심이다. 후임자는 "뭔가 더 있었구나"를 알고 전임자에게 물어볼 수 있고(사람 대 사람의 인계), 우리는 약속을 지킨다.

## 9.3 이전받을 사람이 없을 때

| 순서 | 처리 |
|---|---|
| 1 | **부서 보관함**으로 이동. 부서장이 아니라 `dept_archive` 롤 |
| 2 | 보관함 문서는 열람 시 **로그가 남고**, 열람 사실이 조직 월간 감사 요약에 건수로 집계된다 |
| 3 | 보관함 이동 전 L4 파기(이미 D-day에 완료) |
| 4 | 12개월 후 자동 삭제(조직 설정으로 24개월까지 연장 가능) |
| 5 | 부서 자체가 없어졌으면 조직 아카이브 → 24개월 후 삭제 |

**부서장에게 자동으로 주지 않는 이유**: 부서장은 사람이고, "부서장이면 볼 수 있다"는 규칙이 생기는 순간 재직 중인 사람들도 "내 부서장은 언제든 볼 수 있다"고 추론한다. 별도 롤을 두고 열람에 로그를 붙이면, 접근은 가능하되 **일상적 권한이 아니라 예외적 행위**가 된다.

## 9.4 퇴사자가 "내 문서 다 지워주세요"라고 하면 — 명확한 입장

### 답

> **비공개 메모·짜증 플래그·본인 코멘트·행동 이벤트는 지웁니다(이미 퇴사일에 자동 파기됨). 업무 흐름 문서 본체는 지우지 않습니다. 대신 문서에서 당신의 이름을 뗍니다.**

### 법적 근거

- 법 제36조의 삭제 요구권은 **"개인정보"**를 대상으로 한다. 업무 흐름 문서의 단계 목록·순서·도구는 그 자체로 특정 개인을 알아볼 수 있는 정보가 아니다.
- 문서를 개인정보로 만드는 것은 **작성자·담당자 식별 정보**다. 따라서 삭제 요구에 대한 정당한 이행은 **식별 정보의 분리·삭제**다.
- 구현: `documents.created_by` → `former_member_{pid}`, 표시명 `퇴사한 구성원`, `items.assignee_id` → 직위/역할 표시로 치환. **본문 안에 본인 이름이 텍스트로 적혀 있다면 그 문자열도 함께 치환**한다(SCIM 유래 이름 문자열 정확 일치만, 추측 매칭 금지).
- 법 제36조 제1항 단서: 다른 법령에서 그 개인정보가 수집 대상으로 명시된 경우 삭제 요구 불가. 우리 사안은 여기 해당하지 않지만, **회사의 업무 산출물 보유는 삭제 요구의 대상이 아니라는 점**을 위 논리로 설명한다.

### 재직 중과의 비대칭, 그리고 그것을 정당화하는 것

| 시점 | 문서 본체 통째 삭제 | 근거 |
|---|---|---|
| 재직 중 | **가능. 승인 없음** | 소유자는 본인. 회사도 이를 막을 수 없다(§2.5) |
| 퇴사 후 | **불가** | 소유권이 이미 조직으로 이전됨 |

이 비대칭이 정당한 유일한 조건은 **사전 고지**다. 온보딩 첫 화면, 이용약관, 인사팀 공지문 세 곳에 모두 넣는다. 사후에 이 규칙을 만들면 그건 규칙이 아니라 배신이다.

**반대 케이스** — 회사가 "퇴사자 문서를 전부 삭제해달라"고 하면: 수탁자로서 고객사 지시를 이행한다. 소유자에게 통지할 수 없으므로(이미 퇴사), 지시 근거를 대장에 기록하고 파기확인서를 발급한다.

## 9.5 부서 이동 · 조직 개편

| 상황 | 처리 | 이유 |
|---|---|---|
| 부서 이동 | 문서 소유권은 **사람을 따라간다** | 소유자가 바뀌지 않았다 |
| 집계 귀속 | **작성 시점 부서로 고정.** 소급 재계산 금지 | 재계산하면 이동 전후 차분으로 개인 기여분이 드러난다 |
| P1 `dept_bucket` | **다음 이벤트부터** 새 부서 반영. 과거 이벤트 수정 없음 | 위와 동일 |
| 부서 폐지 | 부서 ID를 삭제하지 않고 `closed` 표시. 과거 집계 유지 | ID 재사용은 데이터 오염 |
| 폐지 부서가 5인 미만으로 축소 | **과거 셀도 억제 대상으로 전환** | 시계열 차분 방어 |
| 부서 분할·병합 | 새 부서 ID 발급. 과거 집계는 구 부서 ID로 남김 | 매핑 테이블로 조회 |

## 9.6 인수합병

**(a) 고객사가 합병하는 경우**

- **테넌트 자동 병합 금지.** 새 테넌트로 마이그레이션한다.
- 각 직원에게 **개별 통지 + 30일 이의제기 기간**. 새 조직의 관리자 구성이 달라지므로 사실상 새로운 처리 환경이다.
- **L4는 이관 대상이 아니다.** 직원이 원하면 개별 선택으로 남길 수 있으나 기본값은 파기.
- 통지 문안은 우리가 제공하고, 발송 주체는 고객사(인사팀 명의).

**(b) 우리 회사가 인수되는 경우** — 이 조항을 지금 넣어두는 것이 핵심이다.

| 조항 | 내용 |
|---|---|
| 통지 | 지배권 변동 시 고객사에 **30일 전 통지** |
| 해지권 | 고객사는 **90일간 위약금 없이 해지**하고 데이터 반환·파기를 요구할 수 있다 |
| **원칙 승계** | 인수자는 TRUST.md 절대 원칙 4개를 승계한다. 승계하지 않으면 위 해지권이 즉시 발동 |
| 데이터 처분 | 인수 과정의 실사에서 고객 콘텐츠(L3/L4)는 **제공 대상에서 제외**. 제공 가능한 것은 집계·계약 정보뿐 |

## 9.7 계정 정지 · 복구

| 상황 | 처리 |
|---|---|
| 휴직·장기 부재 | 계정 정지. 문서 유지, **공유 링크는 유지**(조직 설정으로 만료 선택 가능) |
| 징계·조사 목적 정지 | 로그인 차단. **문서 열람권은 여전히 아무에게도 없다** — 조사를 이유로 관리자 열람을 열지 않는다 |
| 복구 | SCIM `active=true`로 자동 복구. 30일 초과 비활성은 퇴사자 절차로 전환 |
| **SCIM 오류로 잘못 비활성화** | **7일 유예** — 이 기간에는 링크 만료·L4 파기를 실행하지 않고 보류 상태로 둔다 |

마지막 항목이 중요하다. SCIM 동기화 오류는 실제로 발생하며, L4 파기는 되돌릴 수 없다. **되돌릴 수 없는 조치에는 항상 유예를 둔다.**

# 10. 계약 종료와 데이터 반출

## 10.1 타임라인

| 시점 | 상태 |
|---|---|
| **T+0** 해지 통보 | 서비스 정상 이용. 반출 준비 시작. 각 직원에게 개별 안내 발송 |
| **T+0 ~ T+30** | **읽기 전용 유예.** 로그인 가능, 편집 불가, 개인 내보내기 가능. **모든 공유 링크 즉시 만료** |
| **T+30** | 접근 전면 차단. 데이터 격리 보관(접근 계정 0) |
| **T+60** | 물리 삭제 실행. 파기확인서 발급 |
| **T+95(최대)** | 백업 스냅샷 보존주기(35일) 경과로 소멸 |

## 10.2 반출 — 가장 중요한 결정

### 조직 관리자에게 문서 본문을 일괄 덤프하지 않는다.

계약 종료가 원칙 1을 뒤집는 사유가 될 수 없다. 수집 시점의 약속이 "내가 링크를 만들기 전에는 아무도 못 본다"였다면, 계약이 끝난다고 그 약속이 소멸하지 않는다.

**두 갈래로 반출한다.**

| 대상 | 받는 사람 | 포맷 | 기한 |
|---|---|---|---|
| **조직 프로세스 자산** — 집계, 프로세스 맵, 불일치 리포트, 자동화 후보 목록, 도구 카탈로그, 부서 구조 | 조직 관리자 | JSON + CSV + PDF 리포트 | **5영업일** |
| **개인 문서 본문**(L3) | **각 소유자 본인** | JSON + Markdown(+Mermaid) + PDF | 즉시(셀프서비스) |
| **소유자가 조직 이관에 동의한 문서** | 조직 관리자 | 위와 동일 | T+30 이후 5영업일 |
| L4 비공개 노트 | **본인만.** 조직 이관 불가 | Markdown | 즉시 |
| 감사 로그(본인 것) | 본인 | CSV | 즉시 |

**소유자 동의는 opt-in이고 기본값은 "이관하지 않음"이다.**

T+0에 각 직원에게 개별 안내가 간다:

> `회사가 이 서비스를 그만 쓰기로 했어요.`
> `30일 뒤에 문서가 사라져요. 지금 내 것으로 내려받을 수 있어요.`
> `회사 보관함에 남기고 싶은 문서가 있으면 골라주세요. 고르지 않으면 남지 않아요.`
> `[내려받기]` `[회사에 남길 문서 고르기]`

### 이 결정에 대한 고객사 반발 — 응답 스크립트

> **요구**: "우리가 돈 내고 쓴 건데 왜 우리 데이터를 못 가져갑니까?"
>
> **답변**: 프로세스 지식은 전부 가져가십니다. 프로세스 맵, 집계, 불일치 리포트, 자동화 후보 — 이건 계약 다음 날 바로 드립니다. **회사가 이 도구로 얻으려던 것은 전부 그 안에 있습니다.**
>
> 못 드리는 건 개인이 자기 관점에서 적은 서술입니다. 그건 "아무도 안 본다"는 조건에서 수집된 것이라, 조건을 지우면 데이터의 근거 자체가 없어집니다.
>
> 그리고 실무적으로 — **재직 중인 직원 대상 opt-in 비율은 실제로 높습니다.** 퇴사와 달리 다들 회사에 있고, 자기가 만든 인계 문서가 남는 걸 대부분 원합니다. 이 조항은 계약서 제N조에 처음부터 있었고, 그래서 직원들이 사실대로 적었고, 그래서 지금 가져가시는 집계에 값어치가 있는 겁니다.

**이 조항을 계약 체결 시점에 명시**해 종료 시점에 분쟁이 되지 않게 한다.

## 10.3 삭제 증적

**파기확인서**(PDF, 대표자 또는 CPO 서명) 필수 항목:

```
1. 대상 테넌트 ID / 조직명 / 계약 번호
2. 데이터 범주별 삭제 건수
   - 문서 N건 / 단계 N건 / 첨부 N건 / 이용자 계정 N건
   - P1 이벤트 N건 / 공유 링크 N건 / 내보내기 파일 N건
3. 파기 방법 (물리 삭제 | 오브젝트 삭제 | 암호키 파기)
4. 파기 일시 / 실행 주체(배치 잡 ID) / 승인자
5. 검증 방법과 결과 — 테넌트 ID 조회 결과 0건임을 보이는 쿼리와 출력, 결과 해시
6. 백업 소멸 예정일 (최대 T+95)
7. 잔존 데이터와 그 근거
   - 접속기록: 법정 보존(1~2년) 대상이므로 미삭제. 보존 만료 시점 명기
   - 청구·세무 자료: 관련 법령 보존기간
8. 문의처 (CPO 성명·연락처)
```

**BYOK 고객은 여기에 한 줄이 추가된다** — `조직 전용 CMK 파기 완료(KMS 키 ID, 파기 일시)`. 이 경우 백업 소멸을 기다릴 필요가 없다. **암호학적 파기가 유일하게 깔끔한 답이고, BYOK 플랜의 실질적 가치가 여기서 나온다.**

## 10.4 재계약 대비 유예

- **자동 유예 없음.** 요청 없으면 T+60 삭제가 기본이다.
- 고객사가 **서면 요청** 시 **90일 동결 보관** 옵션(유료). 조건:
  - 데이터는 암호화 상태로 격리 저장, **접근 계정 0**
  - 애플리케이션에서 조회 불가(복원 절차를 거쳐야만 접근)
  - 동결 기간 중에도 개인의 삭제 요구는 이행한다
  - 90일 경과 시 자동 삭제 + 파기확인서 자동 발급
- 동결을 요청하려면 **각 직원에게 통지**해야 한다(우리가 문안 제공). 통지 없는 동결은 받지 않는다.

# 11. AI 도입 시 미리 그어야 할 선

> 지금 정하지 않으면 나중에 못 정한다. MEASUREMENT.md의 마지막 문단과 같은 구조다 — **거절을 가능하게 만드는 것은 정책이 아니라 그 경로가 애초에 존재하지 않는다는 사실이다.**

## 11.1 고객 문서를 LLM에 보낼 것인가

**보낼 수 있다. 단, 네 개의 문이 전부 열려 있을 때만.**

| # | 문 | 기본값 | 누가 여는가 |
|---|---|---|---|
| 1 | 조직 단위 AI 기능 활성화 | **꺼짐** | 고객사 관리자 |
| 2 | 개인 단위 활성화 | **꺼짐** | 사용자 본인 |
| 3 | 해당 요청에 대한 명시적 실행 | — | 사용자가 버튼을 누를 때만 |
| 4 | 전송 내용 확인 | — | 사용자가 미리보기를 보고 확인 |

**조직이 켜도 개인이 끄면 전송되지 않는다.** 문서 소유자는 개인이므로, 조직 동의만으로 개인 문서를 외부 모델에 보내는 것은 원칙 1 위반이다. 이 우선순위를 뒤집을 수 있는 관리자 설정은 만들지 않는다.

## 11.2 범위 최소화 — 되돌리기 가장 비싼 결정

| 전송 대상 | 여부 |
|---|---|
| 사용자가 **지금 이 세션에서 입력한 텍스트** | **전송** |
| 현재 편집 중인 문서의 다른 단계 | 사용자가 범위를 선택한 경우만 |
| 저장된 다른 문서 | **전송하지 않음** |
| 조직의 다른 사람 문서 | **전송하지 않음** |
| **비공개 노트(L4)** | **전송하지 않음.** 복호화 함수가 AI 코드 경로에 임포트되지 않는다(§4.3) |
| 실명·이메일·부서 | **전송하지 않음.** 담당자는 역할 표시로 치환 |
| 조직 식별자 | **전송하지 않음** |

### 조직 전체 문서를 색인하는 RAG를 만들지 않는다

이게 가장 중요한 한 줄이다.

"조직 지식 검색" 기능은 상업적으로 매력적이고, 반드시 요청이 온다. 그러나 그것은 **정의상 "조직의 모든 문서를 하나의 인덱스에 모아 누군가가 질의할 수 있게 하는 것"**이며, 그 순간 관리자 열람권의 우회로가 완성된다. 질의자가 관리자이고 인덱스가 전 직원 문서라면, 원칙 1은 검색창 하나로 무력화된다.

**따라서 벡터 인덱스는 소유자 단위로만 만든다.** 조직 단위 인덱스는 스키마에 존재하지 않는다.

## 11.3 학습 미사용 보증 — 문구가 아니라 증명으로

| # | 수단 | 내용 |
|---|---|---|
| 1 | **계약** | 모델 제공사와 **학습·미세조정·평가셋 사용 금지 + zero data retention** 계약. **계약서 해당 조항 발췌를 고객사에 제공** |
| 2 | **기술** | 제로 보존 승인을 **받은 뒤에만** 기능을 켠다. 승인 전에는 릴리스하지 않는다 |
| 3 | **감사** | 전송 건수·모델·리전·시각을 로그로 남기고, **소유자 본인이 볼 수 있게 한다**(§11.5) |
| 4 | **위약** | 하위처리자 위반 시 위약벌 조항 + 즉시 전환 계획 |
| 5 | **우리 자신에게도 적용** | 우리 자체 모델 학습·프롬프트 개선에 고객 콘텐츠를 사용하지 않는다. 품질 개선용 샘플 수집은 **건별 명시 동의 + 본문 미저장**(수락/거절 신호와 편집 거리만) |

**5번을 빠뜨리면 안 된다.** "외부 모델은 학습에 안 씁니다"라고 말하면서 우리가 프롬프트 로그를 쌓고 있으면, 그게 밝혀지는 날 다른 모든 약속의 신뢰도가 0이 된다.

## 11.4 리전·온프레 제약이 있는 고객

| 요구 | 대응 |
|---|---|
| AI 기능 자체를 쓰지 않겠다 | **조직 단위 완전 비활성.** 이 경우 UI에서 **버튼 자체가 사라진다**(비활성화된 회색 버튼도 남기지 않는다 — 존재하면 언젠가 켜진다) |
| 국내 리전에서만 처리 | **국내 리전 모델 옵션**(예: AWS Bedrock 서울 리전) 또는 국내 LLM 사업자. 리전 선택을 조직 설정 항목으로 |
| 특정 모델 제공사 불가 | 조직별 모델 선택 |
| 어떤 외부 전송도 불가 | AI 없이 전 기능 사용 가능 |

**마지막 줄이 정책이다.** AI를 끈 고객이 반쪽짜리 제품을 쓰게 되면, 그 고객은 결국 AI를 켜도록 압박받는다. PRD의 "AI 없이 80% 커버" 방침(규칙 기반 파서·파생 그래프)을 유지하는 것이 **보안 정책의 일부**다.

## 11.5 계약서와 제품 UI에 어떻게 명시하는가

**계약서(DPA 부속서)**

- AI 하위처리자 별도 섹션: 제공사명, 처리 국가, 보존 정책(0), 학습 미사용 조항 참조
- 국외이전 부속서 갱신(§2.4) — 리전에 따라 국외이전이 새로 발생할 수 있다
- opt-in 증적 보관 의무(조직 관리자의 활성화 기록, IP·시각)
- **"기능 릴리스 시 기본값은 항상 비활성이며, 수탁자는 위탁자의 동의 없이 활성화할 수 없다"** — 우리가 나중에 조용히 켜는 것을 계약으로 막는다

**제품 UI**

| 위치 | 내용 |
|---|---|
| 최초 1회 전체 화면 고지 | 모델 제공사명, 처리 리전, 보존 기간 0, 학습 미사용, 끄는 방법. 스크롤 끝까지 내려야 동의 활성화 |
| AI 버튼 옆 상시 라벨 | `보내기 전에 무엇이 나가는지 보여드려요.` |
| 전송 직전 미리보기 | 실제로 나가는 문자열을 **그대로** 보여준다. 요약·생략 없음. `[보내기]` `[그만두기]` |
| 설정 > 내 데이터 | **`AI에 보낸 기록`** — 언제, 어느 모델에, 몇 글자를 보냈는지(본문은 저장하지 않으므로 길이와 시각만). 본인만 |
| 끄기 | 설정 최상단. 확인 절차 없이 한 번에 꺼진다 |

**문구는 WRITING.md를 따른다.** `AI가 도와드릴게요` 같은 문장은 쓰지 않는다(비서 화법 금지). 대신:

> `지금 적으신 문장을 OO에 보내서 초안을 받아와요.`
> `보낸 내용은 저장되지 않아요. 학습에도 쓰이지 않아요.`
