# 10분 요약

> 문서 25개 37,000줄을 다 읽을 필요는 없다. 이 한 장이면 무슨 제품인지, 왜 이렇게 만들었는지 알 수 있다.

---

## 한 문장

**직원은 "설명하지 않아도 되는 업무 문서"를 얻고, 회사는 "직원이 직접 만든 자동화 백로그"를 얻는다.**

같은 데이터, 두 개의 제품 표면. 이 이중성이 제품 구조의 전부다.

---

## 왜 만드는가

n8n·Zapier를 도입해도 **무엇을 자동화할지** 아는 조직이 없다. 기존 해법은 전부 사각지대가 있다.

| | 못 보는 것 |
|---|---|
| 프로세스 마이닝 (Celonis) | 시스템 로그가 없는 업무 |
| 태스크 마이닝 (Scribe) | 브라우저 밖 — 전화, 오프라인 승인, 카톡, 부서 간 대기 |
| 다이어그램 툴 (Miro) | 그림만 남고 데이터가 안 쌓임 |
| 컨설팅 | 1회성. 끝나는 날이 문서 사망일 |

**시장 공백**: 로그에도 화면에도 남지 않는 업무. 유일한 데이터 소스는 **당사자의 기억**이다.

### 단, 문제의 주인을 혼동하면 안 된다

"내 일이 뭔지 알아야 한다"는 문제의식의 주인은 **자동화를 도입하려는 쪽**이다.
영업팀 김대리는 자기 일을 안다 — 몸으로. 문서로 없을 뿐이다.

> 그에게 "당신 일이 뭔지 알아야 합니다"는 문제 제기가 아니라 잔소리다.

**그래서 직원에게 파는 것은 자동화가 아니다.** 직원 화면에서 "자동화"라는 단어를 지운다.

## 어떻게 동작하는가

```
① 붙여넣기          기존 워드 매뉴얼 · 카톡 인수인계 · 메일을 붙여넣으면
                    한국어 연결어미·번호·동사 패턴으로 단계 분해 (AI 없이)
                            ↓ (없으면)
② 질문 연쇄          한 번에 한 질문. 계층 없음. 실패 불가능.
                    "먼저 무슨 일이 시작되나요?" → "그다음엔요?" → 5~6개
                            ↓ 자동 전환
③ 아웃라인 + 다이어그램   왼쪽에 글을 적으면 오른쪽에 그림이 자동 생성
                            ↓ 다 쓰고 나서
④ 메타데이터 카드      한 화면 한 질문. "모르겠어요"가 정답과 같은 크기
                            ↓
⑤ 인수인계 문서 / 요약 / 자동화 후보
```

**사용자는 선을 단 한 번도 직접 긋지 않는다.**

## 핵심 설계 결정 8개

읽는 순서대로 중요도가 높다.

### 1. 관리자에게 개인 데이터를 보여주지 않는다

이 제품은 **직원이 자발적으로 진실을 적어야만 작동한다.** 부풀린 시간, 이상적인 해피패스, 정치적으로 선택된 짜증 플래그로 채워진 데이터는 쓸모가 없다.

> 진실을 얻는 유일한 방법은 그 진실이 자신에게 불리하게 쓰이지 않는다는 확신이고,
> 그 확신은 처리방침 문구가 아니라 **"만들 수 있는데 안 만들었다"는 증명**에서 나온다.

정책이 아니라 **구조**로 강제한다:
- `resolveDocumentAccess()`가 `org_members`를 **인자로도 받지 않는다**
- 5인 미만 집계는 **DB 뷰가 행을 반환하지 않는다**
- 조직 전체 RAG 인덱스를 **스키마에 만들지 않는다**(관리자 열람권의 검색창 우회로)
- `P1(행동) → P2(집계)` 파이프라인이 **존재하지 않는다**

> 경영진은 "부서별로 좀 보면 안 되나"를 **6개월 안에 반드시 요구한다.**
> 그때 거절할 근거를 지금 만들어 두는 것이 이 프로젝트에서 할 수 있는 가장 가치 있는 일이다.

→ [TRUST.md](./TRUST.md) · [POLICY.md](./POLICY.md)

### 2. Tab 들여쓰기를 분기 문법에서 뺀다

Tab으로 계층을 만드는 개념을 즉시 이해 못 할 사용자가 **30~50%**. 더 나쁜 건 **실패 모드가 조용하다**는 것 — 잘못 넣어도 화면은 멀쩡히 그려지고, 사용자는 나중에 "이 도구 이상하다"고 결론낸다.

대신 자연어 껍데기를 **UI에 인쇄**한다:

```
◇ 어떤 기준으로 갈리나요?   [ 내용 분류 ]
  ┃ 만약   [ 단순 문의 ] 라면
  ┃    → 여기에 무엇을 하는지 쓰세요
  ┃ 아니면 [ 복잡 문의 ] 라면
  [+ 경우 추가]  [갈래 끝내기 ↵]   ○ 이어짐  ● 여기서 끝
```

→ [PRD §4.2](./PRD.md) · [EDITOR.md](./EDITOR.md)

### 3. 노드 타입은 3개, 표현력은 속성으로 확장

| 타입 | 속성 | 커버 |
|---|---|---|
| **작업** | 반려율, 반송 대상 | 재작업 루프 (자동화 ROI 1위) |
| **분기** | `택1 / 동시 / 조건스킵` | **AND/XOR 구분** — 없으면 리드타임이 과대 계산된다 |
| **기다림** | `승인 / 응답 / 시각 / 자원` + 타임아웃 | 승인 루프, 에스컬레이션 |

타입을 늘리면 학습 부담이 늘고, 안 늘리면 실무를 못 그린다. **문법이 아니라 속성으로 흡수**하면 커버리지가 55~65% → **85%**로 오른다.

AND/XOR 미구분은 시각화만 어긋나는 게 아니라 **숫자가 틀린다**. 실측: 같은 그림에서 AND 4h · XOR 2.5h · 미구분 합산 5h → **25% / 100% 과대**.

→ [PRD §4.3](./PRD.md) · [GRAPH-CORE.md](./GRAPH-CORE.md)

### 4. 작성 중에는 메타데이터를 묻지 않는다

작성 흐름에 6개 필드를 노출하면 담당자 외에는 **20% 미만** 채워진다. 게으름이 아니라 (a) 인지 전환 비용 (b) 정확도 불안 (c) 보상 부재 때문이다.

→ 흐름을 다 쓰면 → 완료 → **전체화면 카드 스택**(한 화면 한 질문). **"모르겠어요"를 정답 선택지와 같은 크기로.**

그리고 **입력이 아니라 확인**으로 만든다 — "엑셀에 정리"라고 쓰면 줄 끝에 `Excel?` 배지가 뜨고 클릭 한 번.

→ [PRD §4.5](./PRD.md) · [SCREENS.md §4](./SCREENS.md)

### 5. 자기보고 데이터의 왜곡을 설계로 보정한다

**빈도 왜곡이 시간 왜곡보다 치명적이다** — 시간 × 빈도 곱셈이라 오차가 곱해져 랭킹 상위가 통째로 뒤집힌다.

| 장치 | 내용 |
|---|---|
| 로그 스케일 버킷 | 정밀도를 포기하고 순위 정확도를 산다 |
| 회상 기간 고정 | "평소 얼마나 자주"가 아니라 **"지난 7일 동안 몇 번"** |
| **총량 정산** | *"합계 240시간 / 근무 160시간"* → 본인이 재배분. **개별 추정을 백 번 다듬는 것보다 효과가 크다** |
| 신뢰도 등급 | 자가추정 0.5 / 동료합의 0.75 / 실측 1.0 |

단, **시간 실측에 스톱워치를 만들지 않는다** — 타이머를 붙이는 순간 감시 도구가 된다.

→ [PRD §4.7](./PRD.md) · [ANALYTICS-ENGINE.md](./ANALYTICS-ENGINE.md)

### 6. 자동화보다 제거가 먼저

랭킹 이전에 **ECRS 필터**를 둔다. *"자동화하기 전에 없앨 수 있는가?"*

승인 3단계 중 **반려율 0%인 단계는 자동화 대상이 아니라 제거 대상**이다.

> 제거 후보 리스트가 자동화 후보 리스트보다 **훨씬 희소하고 경영진에게 잘 팔린다.**

실제 시드 데이터에서 도출된 것:
- 구매 팀장 결재(10~300만원) — 6개월 **반려 0건**, 평균 대기 3일 → 기준선 상향으로 **리드타임 −3일, 연 62시간 회수. 개발 0줄**

→ [PRD §4.8](./PRD.md) · [SEED-CONTENT.md §D](./SEED-CONTENT.md)

### 7. 조인 키는 "프로세스 이름"이 아니라 핸드오프

전 직원이 각자 적으면 "구매 요청" 하나가 4개 조각으로 흩어진다. 이걸 잇는 것이 개인 도구로는 만들 수 없는 가치다.

**불일치는 버그가 아니라 최고의 산출물**:
> "요청자는 2일 걸린다 하고 구매팀은 5일이라 한다"

단, **상대에 대한 평가를 수집하지 않는다.** 자기 관점의 사실만 모으고 불일치는 시스템이 발견한다.

> **"저쪽이 얼마나 늦나요"를 한 번이라도 물으면, 이후 어떤 노출 정책으로도 정치를 막을 수 없다.**
> 정치를 막는 건 노출 통제가 아니라 **질문 설계**다.

→ [ASSEMBLY.md](./ASSEMBLY.md)

### 8. 디자인은 마감이 아니라 기능

1. **"회사가 시킨 시스템"처럼 보이면 그 순간 끝난다.** 감시 도구 낙인은 카피가 아니라 시각적 톤에서 먼저 결정된다
2. **결과물이 남에게 공유된다.** 예뻐야 공유하고, 공유돼야 확산된다 — **디자인이 곧 바이럴 계수**

구체적 금지: % 게이지·도넛·진행률 바·리더보드·팀 평균(**집계는 그리지 않는다**), 신호등 색(**색은 판단하지 않고 분류만**), confetti(**실직 공포를 정확히 자극한다**), 파랑(**"회사 시스템" 인상**).

→ [DESIGN.md](./DESIGN.md)

## 이 제품이 죽는 방법

기능이 부족해서가 아니다. 순서대로 위험하다.

| # | 사망 원인 | 방어 |
|---|---|---|
| 1 | **효용 미증명** — 직원이 불편함을 적었는데 6개월간 아무것도 안 바뀜 | **자동화 실행 예산과 담당 인력 없이 오픈하지 않는다.** 도구보다 "발굴된 것을 처리하는 팀"이 먼저 |
| 2 | **감시 도구 낙인** | 설계 결정 1번 전체 |
| 3 | **입력 절벽** — 첫 문서를 끝까지 쓰는 사람 20% 미만 | 시드 콘텐츠 · 붙여넣기 파싱 · 질문 연쇄 |
| 4 | **죽은 문서 무덤** | 체크리스트 재사용 · 단계 단위 신선도 · 읽히는 자리에 심기 |
| 5 | **레이아웃 점프** | 타이핑 중 재배치 금지 · 구조 diff 게이트 · 앵커링 |

**D14 재편집률이 5% 아래면 이 제품은 "죽은 문서 생성기"다.**

## 숫자로 보는 목표

**North Star**: 최근 30일 내 프로세스를 1개 이상 완성했고, **그 문서가 타인에게 1회 이상 열람된** 직원의 비율

| 지표 | 목표 |
|---|---|
| 첫 다이어그램까지 시간 (중앙값) | ≤ 8분 |
| 작성 완료율 (5단계 이상 저장) | 60% |
| **레이아웃 수용률** (세션당 노드 드래그 시도) | < 1회 |
| 공유율 | 30% |
| **열람자/작성자 비율** | ≥ 3:1 |
| **D14 재편집률** | 25% |
| 90일 부서 커버리지 | 30~40% |

현실적 예측: 잘해야 전사 40%가 최소 1개 문서, 그중 20%만 살아있는 문서. **그 정도로 충분하다** — 자동화 후보 발굴은 전수조사가 필요 없고, 40%면 반복업무 지형도의 80%가 드러난다.
